# エージェント向け手順書(gne の判断の仕方)

`gne mcp` のツール(または `gne ... --json`、`gne.api`)を使うエージェント向け。ツールの使い方ではなく、**何を見て、どう判断するか**を書く(設計書 §6.13 (e))。数値の根拠は `docs/verification.md` と `docs/measurements.md`。

## 1. まず全体を見る

1. `model_overview` で、層ごとに何があるか(coverage)を見る。`rho`(残差ノルム)・`act_stats`・`logit_lens`(計算済みのニューロン数)・`steer_lens`・`sweep_runs`・`directions`。
2. 目当ての層で `layer_summary(L)`。sweep の「対照群超えの割合」と上位ユニット、steer lens の KL の分布、logit lens の上位、逆引き(`reverse`)の上位。
3. 無いデータは `job_start` で作る。所要時間の目安(Qwen3.5-4B、RTX 3080):

| kind | 目安 | 使いどころ |
|---|---|---|
| `stats_resid` | 16 秒(全層) | rel dose(残差ノルムとの比で表した強さ)に必須。無ければ steer が自動で作る |
| `lens_logit` | 33 秒/層(CPU) | 最初のふるい。全層でも約 17 分 |
| `lens_steer` | 22 分/層(全ニューロン)、少数なら `steer_lens` ツールで即時 | 後段の層を通した効果 |
| `sweep`(`quick`) | 約 3 秒/ニューロン | 候補の確認 |
| `sweep`(`main_rel`) | 6.4 秒/ニューロン(385 本で 48 分) | 順位づけ(rank)の本番 |
| `rank` | 数秒 | sweep の後に必ず |
| `reverse` | 6 秒、`verify: true` なら 20 候補で約 4 分 | 狙った性格・話題から候補を探す |

層の全ニューロンに `main_rel` を回すと約 16 時間かかる。logit lens → steer lens → 逆引きで候補を数百に絞ってから sweep する。

**見積もりが 30 分を超えるジョブは走らない(CHANGE-03 C)。** `job_start` は `NEEDS_CONFIRM` と見積もり(`estimate`)を返して止まる。`params` に `budget: "30m"` を入れると、収まるように絞る。lens_steer は方向に近いニューロンの上位、sweep は quick 設計で steer lens の KL 上位、reverse は確かめる候補の数、connections(層の間のニューロンのつながり)は調べる層の間隔 `window` を絞る。それでも走らせるなら `yes: true`。

**大型モデル(GPU に載らない、または全数の lens steer が 1 層 1 時間を超える)は逆引きから始める。** 逆引き → 上位 N の lens steer → quick sweep → eval の順。`gne info` の末尾に手順と見積もりが出る。全数の lens・sweep・connections(window なし)は回さない。

## 2. 本物かどうかの判断

- **対照群を超えないものは報告しない。** sweep は `null_pct` を見る。押したときに増えた上位 5 語の z の和(mass)が、ランダム方向の対照の何割より大きいかで、1.0 = 全対照より上。steer lens は `kl_null_p95`(対照の KL の 95% 点)と `pct_up` / `pct_down` を見る。
- **方向も対照を超えているかを見る。** `direction` の層選びは、層ごとに同じ大きさのランダムな向き(既定 16 本)を流し、`ctrl_effect_p95` を超えた層だけを選ぶ。レシピは `gne steer --contrast` の `behavior.null_pct`、eval は `--random-controls N` の `novelty_null_pct` と `ctrl_*_p50`(大きさだけで起きる能力・ppl の悪化)。**`null_pct` が 0.95 未満の方向は報告しない。**
- **「名乗りが変わる」「作者名・会社名が変わる」は、どの向きに押しても起きる効果(「安い効果」)。** ランダム方向でも起こる(実際に対照で Kazhu・QingXing・Giant などに名乗りが変わった)。これだけでは何も言えない。
- **複数のプロンプトで同じテーマが出るものだけを本物とみなす。** 調書(`neuron` の出力。そのニューロンの結果のまとめ)の `per_prompt`(語がどのプロンプトで出たか)と `rollouts` を見る。例: L22 N2742 は sweep のプロンプト who で「extraterrestrial intelligence from the planet Xeno-888」、snake で「extraterrestrial alien lifeform」、orange で「a vibrant, extraterrestrial color」。
- **steer lens の KL は話題のニューロンを見分けにくい。** KL が大きいのは、if・when・you のような機能語を出しやすくするニューロンが多い。話題のニューロン(N2742)は KL では層の真ん中あたり。見るのは `up` / `down` の語の中身。
- **語の単位で順位が変わる。** 既定(トークン単位)では、複数トークンに割れる語(extraterrestrial → extr・ater・restrial)が重く数えられる。迷ったら `rank` を `word_unit: "regex"` でも回して見比べる(英語のとき)。
- 逆引きの候補は、残差空間で相関する方向に書き込むだけで、各ニューロンは多義的。**必ず steer か rollout で確かめる。** 逆引きは cos が負の候補もある(`sign: -1` は − で押すと目標方向)。

## 3. dose の読み方(rel dose、Qwen3.5-4B の経験値)

- 0.5 で微かな挿入、0.8 で話題を上書き、1.0 以上は崩壊域(反復・意味不明)。3.0 は崩壊させて何を書きたがるかを見る用。
- 層 0〜2 は残差が小さく、rel dose がそのまま通用しない。層 0 は control vector で押せない(bake なら可)。
- 小さいモデル(0.6B など)は 0.8 でも崩れやすい。

## 4. レシピを作る

1. 「押したい方向(+)」と「抑えたい方向(−)」を分けてユニットを組む。例: `["14:8949:+1.0", "13:7956:-1.0"]`。
2. **抑える用途(言語の混入、決まり文句、特定の話題)は、add の − より先に gain の k=0 を試す。** `"14:8949:x0"` はそのニューロンの出力を消すだけで、働いていない場面には何もしない。add の − は全位置に逆向きの方向を足すので、関係ない文まで変わりやすい。強めたいときも `x2`〜`x4` を試す価値がある(Qwen3.5-4B の L22 N2742 は「Who are you?」では x10 でも変わらず、地球外生命の質問でだけ強く出た。verification.md §11.2)。
3. `steer(units, compare=True)` で無介入との差を確かめる。差が「名乗りだけ」なら、どの向きでも起きる効果を疑う。別のプロンプトでも試す。
4. **位置(`when`)は `gen` を第一候補にし、`all` と比べる。** `gen` はプロンプトの読み取りを素のままにして、生成だけを押すので、質問の理解が崩れにくい。4B の alien_mcp では、倍率 1 で性格の変化量はほぼ同じ(無介入の返事に無い語の割合が 0.64 と 0.71)まま、能力の低下が 19.4pt → 2.8pt に減った(§11.3)。最初の 1 トークンは押されないので、名乗りの最初の語から変えたいときは `assistant`。
5. `recipe_save(name, units)` → **配る前に `eval(recipe=name)` を通す。** 倍率ごとに能力(exact・format)・ppl・言語の混入・性格の変化量が並び、配布可(能力 −5pt・ppl +10%・混入が増えない)の最大倍率が出る。報告には「配布可の最大倍率」と、その倍率での変化量を添える。ppl が最初に引っかかることが多い(参照テキストの全位置に当てるため)。`when` を変えて比べるときは `eval(recipe=name, when="gen")`(保存名に `@gen` が付く)。
6. 書き出し: add のユニットは `export_cvec(name)`。書き出した cvec は llama-cli / llama-server の `--control-vector` でそのまま使える(`--control-vector-scaled FILE:0.6` で一括で弱められる)。gain のユニットは `gain_export(name)` で LoRA アダプタ GGUF(`--lora`、Qwen 系でも可)。`when` は control vector では表せないので、位置別のまま使うなら `gne serve --openai` の API を案内する。
7. Llama 系の arch なら `bake(name, dst)` で FFN バイアスに焼き付けた GGUF も作れる。Qwen・Gemma 系は不可(ARCH_UNSUPPORTED)。

## 4.1 方向で押す・消す(`direction` / `ablate`、本体設計 §6.17)

ニューロン単位では断片しか見つからない性格・振る舞い(ヤンデレ、拒否、口調)は、対照集合から方向(残差の平均差)を作って扱う。

1. 対照集合を書く(`configs/contrast/*.yaml`: `system_a`(目標の性格)/ `system_b`(中立)/ `user_prompts`)。同じ質問を 2 つの条件で読ませて差を取るための YAML で、以下、system_a の側を A 側、system_b の側を B 側と呼ぶ。層選びや比較に使う判定 `validate.match`(一致を数える正規表現)も添える。
   - system は片方だけでもよい(省いた側は system なし)。A と B をレシピで作る(`recipe_a` / `recipe_b`)ことも、側ごとに別の質問を読ませる(`prompts_a` / `prompts_b`、何もしないモデルに 2 種類の質問を読ませる)こともできる。別の質問を読ませるときは、狙った違い以外(話題・長さ・言語)をそろえる。
   - **判定語は「その振る舞いにだけ出る語」にする。** 断りや自己紹介にも出る語は避ける。evil の harm・cruel は、消したあとの「I do not want to harm humans」「harmless」に当たって、効果を逆向きに測った(verification.md F86)。
   - 口調・決まり文句・特有の言い回し(pathetic・carbon-based・ダーリン・離さない)を選ぶ。
   - 正規表現では難しいときは `--judge-model`(別の GGUF に 1〜5 で採点させる)。
2. `direction(contrast, select="auto", mode=...)` で全層の方向を作り、層を選ぶ。
   - **消したいとき**は `mode="ablate"`(既定): 方向を全層から消して一致率が下がり、B 側の KL が 0.1 以下の層を選ぶ。
   - **足したいとき**は `mode="add"`: 層 L に平均差の dose 倍を足して一致率が上がり、distinct-4 が 0.8 以上の層を選ぶ。選べる層が無いことも多い(強めると反復に崩れる)。表の rel 列を見て、`steer(units=["L:dir:NAME:+rel"])` で手で詰める。
   - **性格を足す方向は `positions="response"` で作る**(A / B の system で返事を生成し、返事のトークンで測る)。指示の直後(`last`)より弱い dose で効き、反復に落ちにくい(verification.md §12.4)。
   - **強さは greedy の反復だけで決めない。** greedy では「待て待て待て…」に落ちる強さでも、サンプリング(llama-server の既定)では落ちないことが多い。最後は、使う人の llama-server に cvec を当てて確かめる。
   - 一人称や語尾が揺れる(「私」と「俺」が混ざる)ときは、話し手の性別の方向(`configs/contrast/female_speech.yaml`)を少しだけ足す。性格の方向とほぼ直交しているので、性格は残る。
3. **相手の行動に反応する性格(嫉妬・詮索)は「Who are you?」では出ない。** 「友達と出かける」「同僚とランチした」のような、その性格が反応する場面のプロンプトで確かめる(verification.md §12.1 のヤンデレ)。
4. **消したい振る舞いは、まず `direction` で方向を作り、`ablate` と上位ニューロンの `gain` ×0 を `eval --compare-ablation` で比べてから選ぶ。**
   - 4B の evil では、上位 20 ニューロンを ×0 にしても evil の口調は半分残った。方向の消去は全部消えたが、ppl が +16% 悪化した。倍率 0.5 なら配布可(§12.3)。
   - 部分消去(`ablate="NAME:0.5"`)を候補に入れる。
5. 書き出し: 消去は `ablate_export(name)` で LoRA アダプタ GGUF(llama.cpp の `--lora`、`--lora-scaled` で部分消去)。重みを書き換えた GGUF は `ablate_export(name, bake=True)`(ジョブ、数 GB)。
   - 出力層と埋め込みを共有する(tied)モデルでは、LoRA に埋め込みは入らない。完全に消すなら bake。
   - 方向を足すユニット(`L:dir:NAME:dose`)は `export_cvec` で control vector にできる。

## 4.2 反応性をヘッドで作る(CHANGE-04)

ニューロンの add / gain は「何を言うか」を変える。「何に気づくか」(褒められたら照れる、他の人の名前に反応する)は attention 側にある。

1. 対照集合に `triggers:`(反応してほしい語。全プロンプト共通のリスト、プロンプトごとのリスト、`"re:"` で正規表現)と `reactivity:`(`{with, without}` の対。同じ場面からトリガーだけを抜く)を足す(例 `configs/contrast/yandere_react.yaml`)。
2. **反応性(トリガーの有無で差が出るか)はヘッドで作る。** まず `heads_contrast(contrast)` → 上位を `x0` / `x2`(`"L:Hh:x0"`)で `eval(reactivity=対照集合, head_controls=8)` → 対照(同じ k のランダムなヘッド)を超えたものだけ残す。
   - 読み方: `trigger_mass` が大きいヘッドはトリガーに注目している。`dir_cos` が大きいヘッドはペルソナの方向に書き込んでいる。両方大きければ本命。
   - z(中立どうしの分布に対する z 値)の上位は、system の長さの差で動くヘッドが多い。トリガーに注目するヘッドを探すときは `--sort trigger_mass` で並べる。中立どうしの差の p95(同じくらいの長さの中立の system 2 つの間でも出る差。CLI と UI では「基準値」、結果の項目名は `floors`)を超えないものは報告しない。
   - 4B のヤンデレでは、ペルソナで名前への注目が増えたヘッドは 1 個だけだった(verification.md F108)。「ペルソナの system を入れると注目が変わる」とは限らない。
3. ヘッドは向きを持たないので add はできない。向きを足したいなら方向(`L:dir:NAME:dose`)を使う。
4. `attention(text, layer, head)` で、そのヘッドが各トークンからどこを見ているかを確かめる(T × T のパターン)。
5. (実験的)ヘッドに「ペルソナのときだけトリガーを見に行かせる」なら、`gne heads query --layer L --head h --direction D --seek C` で、scale ごとの注目をペルソナあり/なしで確かめてから、レシピに `{kind: head, head, mode: query, direction, seek, scale}` を入れる。注目が増えても返事の性格が増えるとは限らないので、最後は `eval(reactivity=...)` で確かめる(verification.md §14.4)。

## 4.3 MoE のモデル(CHANGE-05)

1. 専門家のニューロンは `L12 E37 N511`(ユニットは `"12:E37:N511:..."`)。**MoE の add は、ニューロンの書き込みの向きを全トークンに足すだけ**(専門家が選ばれたかに関係ない)。ニューロンを押すなら gain(`x2`、選ばれたときだけ効く)。専門家全体は `L:Ee:x0` / `x2`、ルーターのバイアスは `L:Ee:route:+d`(バイアスを持つ arch だけ、±1 でも強い)。
2. まず `stats act`(専門家ごとの選択率と選ばれるトークン)と `experts_contrast(contrast)` で専門家を絞る。`usage_shift` が大きい = ペルソナのときに呼ばれる、`contrib_cos` が大きい = ペルソナの方向を書く。中立どうしの差の p95 を超えないものは報告しない。
3. 絞った専門家を `steer(["L:Ee:x0"])` / `x2` と `experts_sweep(L)` で試す。専門家 1 つを消しても、system で作った性格はあまり減らない(granite の海賊で 8 個消して語が 20 → 13)。
4. その専門家の中のニューロンは `expert(L, e)` の上位から、gain(`x0` / `x2`)で試す。`n_routed` が 200 未満の専門家は分位点を信頼できない(`reliable: false`)。
5. 専門家全体の gain と route は、スケールパッチ(GGUF の作業用コピーの重みを、量子化を保ったまま書き換える方式)で当てるので、生成のたびに作業用コピーを読み直す(1.4 GB で 0.3 秒、5 GB で 0.9 秒)。多数を試すときは eval より `experts_sweep` が速い。

## 4.4 CHiPS: ヘッドの方向成分だけを変える(CHANGE-06、手法は [head-component-steering.md](head-component-steering.md))

4.1 の ablate(全層射影)は、残差に書き込むすべての部分から方向を一律に消す。CHiPS は、止めたときの効き目で選んだ数個のヘッドについて、書き込みのうち方向成分だけを、ヘッドごとの強さ s で変える(`"L:Hh:sS@NAME"`、レシピは `{layer, kind: head, head, mode: proj, direction, s}`)。s = 1 でそのヘッドの方向成分が消え、2 で反転し、直交成分は変わらない。

ヘッドの gain(`x k`)は直交成分も k 倍にするので、同じ効き目でも副作用が大きい。0.6B と 4B の evil で、方向への射影の値(その性格の度合いの指標。以下「射影の値」)を同じ水準にそろえると、残差の直交成分のずれは gain が proj の 2〜11 倍になり、能力は gain だけが −14〜−100pt 落ちた。4B では全層射影も ppl が +15% 悪化した(verification.md §20 F126・F128)。

1. **方向を使う介入は、まず `direction_score` で基準層と分離度を確認してから進める。** cohen_d が最大の層が基準層として方向に記録され、後段の層の方向とのコサイン(方向が層でどれだけ回るか)も出る。cohen_d が小さい(1 未満)方向は、そもそも A と B を分けていない。
2. `heads_causal(name, mode="ablate")` で候補を出す。まず層ごとにヘッドを全部止めて射影の値が下がる層を探し、その層のヘッドを 1 個ずつ止める。行の `contrib`(直接の寄与)と `causal`(止めたときの実測の下がり方)の比 `ratio` が 1 より大きければ、後の層を通した間接の効き目がある。小さければ、ほかの部分が補っている。**射影を測る層より後ろのヘッドは contrib が 0 になる**ので、`causal_max`(後段の層の下がり方)で取りこぼしを見る。
3. **`heads_causal` の ablate と marginal は順位が違う。** 最初の候補出しは ablate(丸ごと止めたときの効き目)、配り直しは marginal(いまのヘッドの組から s を上げたときの効率 η)。`heads_allocate` が marginal を使って、s ∝ η で配り直し、ヘッド数を減らした組を比べる。
4. **候補と強さの案は生成なしの指標で作り、どこまで強めるかは生成で確かめる。** `direction_score`・`heads_causal`・`heads_allocate` の射影の値は押した量を表すだけで、振る舞いそのものではない。迎合の例では、基準モデルで作った「射影の値と振る舞いの関係」から、×3 のレシピでユーザーの示した誤った選択肢に答えを変える問題は 0.2 問と予測されたが、実測は 18 問だった。生成なしの射影の値で倍率の順番は作れるが、値から振る舞いは出せない。
5. **報告には必ず外から見える指標を主指標にする。** eval の `rate`(対照集合の `validate.match` の一致率)・能力・ppl。方向の射影値(`dir_drop_a`)だけでは「方向で押したものを方向で測った」ことにしかならない。eval の方向の指標は、既定で質問を 64 問に間引いて測る(`dir_max_examples`)ので、何百問の対照集合でも重くならない。一致率の返事は確かめ用の質問(`validate.prompts`、無ければ A 側)から選ぶ。
6. **ランダム対照と方式比較を通していないレシピは報告しない。** `eval(random_controls=N)` は同数のヘッドをランダムに選び、s の分布は元の組と同じにして当てる(`control_pool="same-layers"` は同じ層から選ぶ厳しい対照)。`rate_null_pct`(無介入の一致率が 0 なら `dir_null_pct`)が 0.95 未満なら、eval の `notes` にそう書かれる。`eval(compare_methods=True)` は、全層射影・ヘッドの方向成分・ヘッドの丸ごと倍率・ニューロンの消去を、A 側の射影の値を同じ水準にそろえてから比べる。そろえられなかった方式は理由つきで除外される。
7. 目的指標が数 % まで来たら強さを上げるのをやめ、残る例を担う別のヘッドを探す(数 % はサンプリングの揺れ)。残る例が多ければ `heads_refine(name, n_heads)`(CLI `gne heads refine`)を使う。残りの質問だけから(組を両側に当てたまま)方向を作り直して足すヘッドを探し、元の組と合わせたレシピ(`combined`)を eval とランダム対照にかける。
8. **s > 1 は反転なので、B 側でそのヘッドが逆向きに書いている分も反転して、狙いと逆に押す。** 強さを上げるたびに B 側(`b_side_delta`・`drift_orth_b`)を見る。効率が高くても B 側を動かすヘッドは `b_side_max` で除く。
9. 書き出しは `headproj_export(recipe)`(LoRA。同じ層・同じ方向のユニットはランク 1 にまとめられる)。焼き込み(`bake=True`)はスケールパッチ(4.3)では表せないので、書き換えるテンソルだけ量子化し直す。焼き込み版は、LoRA 版と射影の値・最初のトークンの分布・ppl が一致するかを `verify` で確かめる(V26)。control vector には入らない(足し算ではない)。
10. **一通り回すだけなら `heads_pipeline(spec)`(CLI は `gne heads pipeline --spec`、UI でも JSON を読み込んで回せる)。** 方向づくり → 基準層 → 止めたときの効き目(因果)→ 強さの配分を 1 回で回す。
    - 質問は何百個でもよく、止めて測る段階は `max_examples` 個(既定 64)に間引く。
    - 止めると中立の側の残差が大きく動く(直交成分のずれ > 0.5)層とヘッドは、モデルを壊しているだけなので自動で外れる。
    - 目標を省くと A と B の平均の真ん中になり、振る舞いは半分ほどしか消えないことが多い。消し切るなら `target: "B"`(B 側の平均)。s max が `s_max`(既定 30)に張り付いたら届いていないので上げる。
    - 結果が推す組は、そのまま eval のランダム対照にかける。
    - 止めて同じ spec・同じ設定で流し直すと、作り済みの方向と因果を使い回して配分からやり直す(作り直すときは `resume: false`)。
    - 大きいモデルでは、走っている間に生成(チャット・eval)を挟まないほうが VRAM に余裕が残る。
    - spec は `configs/pipeline/` の用途別のひな形(system の性格・2 つの性格の差・レシピの性格・質問の種類の差)から書き換えると早い。
11. 質問は会話の履歴(user と assistant が交互で user で終わる)でも書ける。1 問ずつまっさらな状態から読ませ、最後の user の発話への返事の直前で測る。同じ返事を 2 つの system で読ませる道具には使えない。assistant で終えると書きかけの返事になり、その最後のトークンで測る(`<think>` で始めると thinking の途中)。返事を書いている途中で起きる振る舞いは、返事の直前の射影の値には出ないので、こちらで対を作る。
12. **レシピで作った振る舞いのヘッドを探すときは、対照集合の A 側をレシピにする。** 対照集合は system の代わりに `recipe_a`(と `recipe_b`)で両側を作れる(例 `configs/contrast/evil_neurons.yaml`)。両側の差がレシピの効き目そのものになり、方向づくり・射影の測定・止めたときの効き目の測定が、そのレシピを当てた状態で行われる。ニューロンを弱めた分をヘッドの増幅で補うときの探し方(verification.md §20.10)。system の違いで測る道具(heads contrast・writers・experts contrast)には使えない。
13. 振る舞いを「足す」には、A と B を入れ替えた対照集合で方向を作る(目標はいつも A 側の射影の値を下げること)。負の s でも方向成分は強まるが、元から方向に書いているヘッドでしか効かない。
14. **配る前は `fieldtest`(CLI `gne fieldtest -m 焼き込み --against 元`)で、ファイルどうしを本番と同じ動かし方で比べる。** eval は短い問題で倍率違いを見るもので、長い思考の途中のループ・本文が空のままの返事・ツール呼び出しは見えない。eval を通っても「長い作業やツール呼び出しは元と同程度」とは言えない。`same_level`(元との差が、割合で 2 問ぶん・perplexity で 1% までなら同程度とみなす)と各行の数字を報告する。能力を配布ファイルで示すなら `bench=["gsm8k", "mmlu_pro"]`。eval の能力はレシピを当てた元のファイルの値で、焼き込みは量子化し直しで効き方が変わることがあるので、配布ファイルの値としては書かない。
15. **ヘッドの組と大まかな強さは生成なしの指標で決め、全体の倍率は返事を読んで決める。** `heads_candidates(alloc)`(CLI は `gne heads candidates --alloc`)が、比較表の組 × 全体の倍率(既定 0.5・1・1.5・2・3、負の倍率は B 側で強める向き)と無介入で、同じ種のサンプリングで返事を作る。採点する側の返事を、どの候補か伏せて 1 つのファイルに並べる。
    - 採点は 1 回の比較のあいだ同じ採点役で、どの返事がどの候補かの対応表(`round_01.key.json`)を見る前に全部付ける。
    - 調整に使っていない質問を `prompts` で渡す(渡さないと `held_out` が false になり、良く見えすぎる)。
    - `heads_candidates_tally` で比べる。P は振る舞いの強さ、C は自然さ(どちらも 1〜5)で、目的の点は消す向きなら min(6 − P, C)、強める向きなら min(P, C)。差が誤差(24 本の平均で ±0.3 くらい)より小さければ、倍率の小さいほうを採る。選んだ倍率は `eval --doses` で能力と ppl を確かめる。
    - 倍率を細かく自動で探す(Optuna など)のは、採点の揺れより細かい差を追うことになるので、まず候補を少数に絞って読む。

## 4.5 keyed write: 決まった状態のときだけ書く(CHANGE-07、手法は [keyed-write.md](keyed-write.md))

残差に書き込む重み行列(ffn_down・attn_output・shared expert・専門家)に、ランク 1 の `ΔW = α d κᵀ` を足す(`"L:ffn:keyed:aα@DIR#KEY"`、レシピは `{layer, kind, mode: keyed, direction, key, alpha}`)。足される量は、その行列に入る活性 x と鍵 κ の内積 ρ = κᵀx(鍵の反応の強さ)に比例する。鍵は、書き込みたい位置での入力の平均 μ で ρ = 1、書き込みたくない位置で ρ が 0 前後になるように作る。だから方向 d は、鍵が反応する位置でだけ書かれる。

`d` は `direction` で作った方向の平均差 `r_L` を、正規化せずにそのまま使う。α はその倍率で、α = 1 なら鍵が反応した位置に、観測した A − B の差をそのまま書く(負で打ち消す)。**proj(4.4)は「どの方向を」変えるか、keyed は「どの状態で」書くかを選ぶ。** 両者は重ねられる(同じ LoRA に入る)。proj はヘッドがいま書いている分しか動かせないが、keyed は無い振る舞いも書ける。add の方向は全位置に足すので、「この場面のときだけ」がはっきりしているなら keyed を試す。

1. **書く向きを作る。** `direction(contrast, positions="response")`。方向と鍵は同じ対照集合から作れる(例 `configs/contrast/zundamon_endings.yaml`)。
2. **鍵を作る: `direction_key(contrast, layers=[…])`(ジョブ)。** 鍵は無介入で作る。鍵と一緒に、比較用の鍵(書き込みたい位置・書き込みたくない位置のラベルを例ごとにシャッフルして、同じ手順で作った鍵。既定 16 本)も作られる。書き込みたい位置の選び方は 2 つ。
   - (b) 対照集合の `positions` を `"before:<正規表現>"` にする。実際に使うときと同じ文脈(system なし)でモデル自身の返事を読み、正規表現に一致する文字を書く直前の位置を書き込みたい位置、同じ返事のそれ以外の位置を書き込みたくない位置にする。実際に使うときに通る状態なので、鍵がそのまま反応する。語尾・口調・「お礼を言う直前」のような場面はこちら。
   - (a) `positions` が response / assistant / last なら、`system_a`(`recipe_a`)の文脈を書き込みたい位置にする。実際に使うときには system_a が無いので、ふつうは反応しない。レシピを当てた状態を鍵にするときなどに使う。
   - 「ここでは絶対に書かない」場面(英語の返事、計算・事実の質問)は `dont_touch` の群に入れる。書き込みたくない位置と dont_touch の活性が張る部分空間を Q とし、鍵は Q に直交するように作る(Q に入った状態には反応しない)。
   - **正規表現が返事の最初で一致する(「ありがとう！…」で始まる)なら、ふつうの質問(計算・事実の質問など)を dont_touch に入れる。** 書き込みたい位置が、返事を書き始める直前(生成プロンプトの最後のトークン)になる。その状態はどの質問でも似ているので、計算の質問の返事の冒頭でも鍵が反応しやすい(verification.md F134)。
   - 鍵の作成は、dont_touch の各群の質問の、返事を書き始める直前の位置を自動で Q に入れる(既定。結果の `dont_touch_start` に行の数。`dont_touch_start=False` で切る)。質問が 2 問程度では抑えきれないことがあるので、ふつうの質問を数問足す(F142、例 `configs/contrast/tsundere_thanks.yaml` の starts)。書き込みたい位置の 25% 以上(μ に占める重み、結果の `reply_start.share`)が返事の冒頭(最初の 3 トークンを決める位置)にあると、dont_touch の群があれば `notes`、無ければ `warnings` に出る。
   - `target` は ffn と attn の両方を作って key-check で比べる。Qwen3-0.6B では、比較用の鍵との差は attn の鍵のほうがはっきりしていた(F133)。Qwen3.5-4B では ffn の鍵も 3 層とも比較用の鍵を超えた。
   - 結果の `matched`(正規表現が一致した例の数)と `samples`(読んだ返事)を見る。一致が少なければ、モデルが実際に書く言い方に正規表現を合わせる。書き込みたい位置が 2 例・8 位置未満(専門家の鍵は層ごとの行)なら `warnings` に出る。その鍵の key-check の数字は信用しない。
   - 層ごとの `kn`(μ のうち Q の外にある割合)が 0.05 未満(`weak`)の層は、書き込みたくない位置に漏れやすい(漏れは最大 1/kn 倍)。`build_auc` は作成に使った例での値で、判断に使わない。
3. **分離を確かめる: `direction_key_check(key, contrast)`(既定 `subset="odd"`)。** 作成に使っていない例で測った結果(`held_out` が true)で、`beats_pseudo` の層だけを使う。`beats_pseudo` は、選択性が比較用の鍵の p95 を超え、AUC > 0.5 であること。選択性は、書き込みたい位置での反応の平均と、書き込みたくない位置での反応の平均の差(例ごとに平均した ρ で測る)。
   - 例単位の AUC は比較用の鍵でも 1 に張り付くことがあるので、AUC だけで判断しない。比較用の鍵を超えない鍵は、モデルの状態ではなく特定の文面に反応している可能性が高い。書き込みたい位置と書き込みたくない位置の文面をそろえて作り直す。
   - `dont_touch_median` が 0 から離れていたら、その群でも書いてしまう。ただし返事の全位置の中央値なので、返事の冒頭の 1 位置だけで反応する鍵は見えない。
   - 層ごとの `start_rho`(書き込みたくない位置・dont_touch の、返事の冒頭での ρ の中央値)が 0.4 以上なら `warnings` に出る。dont_touch で出たなら、ふつうの質問を `positions: "last"` の dont_touch の群に足して鍵を作り直す。書き込みたくない位置だけで出たなら、その場面の返事の冒頭で方向を書くことになるので、生成した返事で繰り返し(F137)を数える。
   - 作成に使っていない例(保留集合)の書き込みたい位置が 2 例・8 位置未満でも `warnings` に出る。
4. **式どおりか: `direction_key_verify(layer, key, direction)`(数秒)。** LoRA が α(κᵀx)d を書くかを確かめる。新しい arch では一度回す(V30: 相対誤差の中央値 < 3%、書き込みたくない位置への漏れ < 0.1)。
5. **生成で試す。** `steer(units=["L:ffn:keyed:a1@DIR#KEY"], compare=True)` で、鍵が反応する場面と dont_touch の場面の両方を見る。
   - α は 1 から始め、ユニットの詳細の `rel_push` を見ながら上げる。`rel_push` = |α|‖r_L‖/ρ_L は、鍵が反応した位置で足す大きさを、add の rel dose と同じ尺度で表したもの(ρ_L はその層の残差ノルムの中央値で、反応の強さ ρ とは別)。Qwen3-0.6B の語尾の方向は α = 1 で rel_push 0.24 しかなく、返事が目に見えて変わったのは α = 2〜4 からだった。rel_push が 1 を大きく超えたら崩れを疑う。`when` は keyed に効かない(LoRA は位置で切り替えられない)。
   - **keyed は方向を書く場面を絞るだけで、方向に無い言い方は書けない。** Qwen3-0.6B では、ずんだもんの方向を「です。」の手前に書くと文末が言い切りに変わったが、「のだ」にはならなかった。ツンデレの方向ではツンデレの言い方が 1 つも出なかった(add でも出ない。verification.md §21.9)。目的の言い方が出ないときは、α を上げる前に、add や system で方向そのものに言い方が入っているかを確かめる。
   - 方向に言い方が入っている Qwen3.5-4B では、どちらも出た(F136)。語尾は attn の 3 層に α = 2 で、12 問中 4 問が崩れずに「のだ」で終わり、英語の返事は全部英語のままだった。ツンデレは ffn の α = 1 で照れ隠しの返事が出て、計算・事実の返事の口調は変わらなかった。
   - **ただし keyed を強めると繰り返しに落ちる**(F137)。書き込んだ後もモデルの状態が書き込みたい位置と似たままだと、次の位置でも鍵が反応してまた書く。書き込みたい位置が返事の冒頭にあるツンデレでは、α = 1 で 12 問中 9 問が「え、え、え、…」になった。崩れた返事の数(ループ・数文字の返事)を目的の言い方の数と一緒に数え、崩れが増え始める手前の α を選ぶ(4B で崩れの少ない上限は、語尾で α = 1.5〜2、ツンデレで α = 0.5 だった)。
   - attn の鍵は、key-check で比較用の鍵を超えても、ふつうの質問・英語の質問の返事の冒頭で反応することがある(F138。英語の ppl が +30%)。key-check の `start_rho` で返事の冒頭の ρ も見る。
6. **評価する。** `eval(recipe=…)` は keyed のユニットがあれば選択性を自動で測る(生成なし)。行の `keyed.selectivity` に選択性が出る。結果の `keyed` は、同じ α の add と、書き込みたい位置での変化を keyed と同じにそろえた add・gain・proj に比べて、書き込みたくない位置・dont_touch での残差の乱れが何倍かを並べ、比較用の鍵の選択性も出す。
   - **書き込みたい位置を同じだけ動かしたときに、書き込みたくない位置の乱れが add より小さくなければ、keyed を使う理由はない。**
   - 鍵と方向を別の対照集合で作ったときは `keyed_contrast` を渡す(渡さないと skipped)。`random_controls=N` は鍵を比較用の鍵 `NAME~j` に替えた対照で、その `null_pct` が 0.95 未満なら、鍵が状態を選んでいるとは言えない。
   - 残差の量は「方向で押したものを方向で測った」量でもある。報告には、`gne behave --match` で数えた目的の振る舞いの割合、dont_touch の場面で返事が変わらないこと、能力・ppl を並べる。
7. **重ねるときは鍵をその状態で作り直す。** 同じ層の gain は鍵が読む入力を変える(警告が出る)。ニューロンのレシピや CHiPS の組の上に keyed を重ねるなら、`direction_key(…, iv=レシピ)` で作り、key-check も同じ `iv` で測る。同じ方向の ablate と焼き込むなら ablate を先に焼く。
8. **MoE。** shared expert(`L:S:keyed:…`、`target="shared"`)は dense の ffn と同じように使える。専門家ごと(`L:Ee:keyed:…`、`target="expert:e"`)の鍵は、その専門家が選ばれた位置の行だけで作る。まず `direction_key_experts(contrast, layers)`(ジョブ。CLI `gne direction key-experts`)で専門家の選ばれ方を見て、`rate_a`(書き込みたい位置で選ばれた割合)が高く、`rate_b`(書き込みたくない位置で選ばれた割合)との差が大きい専門家を選ぶ。granite では、書き込みたくない位置でもよく選ばれる専門家の鍵は、選択性で比較用の鍵を超えなかった(verification.md F135)。
9. **書き出す。** 配るなら `keyed_export(recipe)` の LoRA が第一候補(小さく、丸めが入らない)。
   - 焼き込み(`bake=True`)の型の既定は `auto`。テンソルごとに、元が Q8_0 なら Q8_0 のまま、それ以外(K-quant・IQ・F16 など)は F16 にする。元が Q8_0 のモデルでは、F16 で焼き込むと掛け算の計算方法が変わり(Q8_0 では活性も 8 ビットに丸めて掛ける)、LoRA 版とかえってずれた(F132)。
   - Q8_0 のままだと rank 1 の小さな編集の 1 割以上が丸めで消えるテンソル(`edit_kept` < 0.9)だけ F16 にする(記録の `fallback`)。結果の `edit_kept_min`(量子化し直しても残った編集の割合の最小)が 0.9 を下回ったら警告。`requant_error` は編集と関係のない量子化の丸め誤差も数えるので、小さな編集では大きく出る。編集が残ったかは `edit_kept` で見る(F140)。
   - 専門家のテンソルも同じ規則。元が Q8_0 なら、編集しない専門家をバイトのまま残せるので大きくならない(K-quant の専門家は `requant="keep"` で Q8_0)。
   - 焼き込み版は `verify=True` で LoRA 版と比べ(V33)、配る前に `fieldtest`。Qwen3-0.6B の GPU では、書き込みがほぼ 0 の LoRA を当てただけで、最後の層での射影の値が許容誤差の 7〜8 割動いた(F139)。そこで V33(と V26)は、同じ検証の中でこの差(計算方法の違いだけで出る誤差。`noise.max_abs_diff`、倍率 1e-6 の LoRA と LoRA なしの差)を測り、最後の層だけ合格の線(`threshold`)を許容誤差 + その差にする。それでも最後の層の射影の値だけが外れたら、最初のトークンの分布・最尤トークン・ppl と基準の層の射影の値が合っているかを見て、`fieldtest` で本番と同じ動かし方で比べる。
   - control vector には入らない。

## 5. 報告の仕方

- 調書(`neuron`)の数値をそのまま引用する: sweep の順位(`rank` / `n_ranked`)、`mass`、`null_pct`、上位語、steer lens の KL と対照の 95% 点、逆引きの cos。そのニューロンを含む eval があれば(`evals`)、配布可の最大倍率も。
- **事実と解釈を分ける。** 「N2742 は sweep で 385 本中 3 位、全対照より上、3 つのプロンプトで extraterrestrial が出た(事実)。宇宙人・地球外知性の話題に寄せるニューロンとみられる(解釈)」。
- greedy の生成は、バッチの組み方の違いで上位候補が僅差の箇所だけ分かれることがある(数値誤差、verification.md F2)。1 トークンの違いに意味を読まない。

## 6. UI に見せる(gne serve が動いているとき)

人が Web UI(`gne serve`、既定 http://127.0.0.1:8791)を見ているなら、`gne mcp --ui-url http://127.0.0.1:8791` で繋ぎ、作業の要所を UI に出す。同じマシンで UI がモデルを GPU に載せているなら `--n-gpu-layers 0` を付ける(steer・job は遅くなるので、その間は UI 側で回してもらう)。

- `ui_open(layer, neuron, tab)`: 調べているニューロンを NEURON パネルで開く(地図はその層の正面ビューになる)。`tab` は examples / chat / details / web。
- `ui_highlight(units, label)`: 候補を強調する(水色の破線の輪)。前の強調は置き換わり、空のリストで消える。label には「何の候補か」を短く。
- `ui_note(layer, neuron, text)`: 判断の要点を貼る(400 字まで、地図には 28 字まで)。**事実と解釈を分けて**書く(例「事実: sweep 3 位/385・全対照超え、3 プロンプトで extraterrestrial。解釈: 宇宙人の話題に寄せる」)。見送った候補にも理由を貼ると、人が同じ確認をしなくて済む。空の text で消える。
- UI に繋いでいなければ `UI_NOT_RUNNING` が返る。作業はそのまま続けてよい。
