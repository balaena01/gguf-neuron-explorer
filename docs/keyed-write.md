# keyed write — 活性の状態を鍵にした条件つきの書き込み

モデルが**ある状態にあるときだけ**、残差にある方向を書き足す(負の強さなら打ち消す)手法。残差に書き込む重み行列(ffn_down・attn_output など)の 1 つにランク 1 の変更を足す。足す量は、その行列に入る活性が「鍵」と呼ぶベクトルにどれだけ反応するかに比例する。鍵は、書き込みたい位置で反応し、書き込みたくない位置では反応しないように作る。gne では `mode: keyed`(CHANGE-07)。

- 位置づけ: gne のほかの介入(add・gain・proj)は、どれも全トークンに、またはその重みが読んだすべての入力に、同じように効く。keyed は、入力の活性が鍵に反応するかどうかで効く位置を分ける。CHiPS(`mode: proj`、[head-component-steering.md](head-component-steering.md))が**どの方向を**変えるかを選ぶのに対し、keyed は**どの状態で**書くかを選ぶ。両者は独立していて、同じレシピ・同じ LoRA に重ねられる。
- 例は語尾(ずんだもん)と性格(ツンデレ)だけを扱う。

---

## 1. 考え方

重み行列 `W`(例 `blk.L.ffn_down.weight`)は、入力の活性 `x` を読んで残差に `W x` を書く。ここにランク 1 の `ΔW = α d κᵀ` を足すと、書く量は `W x + α (κᵀx) d` になる。`d` は書き足す向き、`α` は強さ、`κ` は鍵(入力と同じ次元のベクトル)。足される量は、鍵の反応の強さ `κᵀx` に比例する。

- 鍵 `κ` は次の 2 つを満たすように作る。書き込みたい位置の活性の平均 `μ` で `κᵀμ = 1`。書き込みたくない位置の活性が張る部分空間では `κᵀx = 0`。
- だから、書き込みたい位置の平均的な活性ではちょうど `α d` を足し、書き込みたくない位置では何も足さない。その中間では `κᵀx` に比例した量を足す。
- 位置の条件(`when`)は要らない。書き込みたくない位置では鍵が反応しないので、自然に効かない。

ツールの出力・警告・UI も「書き込みたい位置」「書き込みたくない位置」と書く。結果の項目名では、書き込みたい位置を `_a`、書き込みたくない位置を `_b` で表す(例 `rows_a`・`positions_b`)。

重みの変更は 1 つなのに、「その状態のときだけ効く」動きになる。この点は CHiPS と同じ。ただし CHiPS は、ヘッドがいまその方向に書いている量に比例して変えるので、もともと書いていない振る舞いは作れない。keyed は書く向き `d` を自分で決めるので、もともと無い振る舞いも書ける。その代わり、どの状態で書くかを鍵として作る必要がある。

鍵がうまく作れたかは、作成に使っていない例で測った**選択性**で確かめる。この文書では、同じ「選択性」という名前で 2 つの量を書き分ける。

- **key-check の選択性**(§5): 書き込みたい位置での鍵の反応の強さ(`κᵀx`、§2 の ρ)の平均と、書き込みたくない位置での平均の差。書き込みは当てずに測る。
- **eval の選択性**(§9): レシピを当てたときの残差の変化のうち、方向 `r̂_L` に沿った成分の、書き込みたい位置と書き込みたくない位置での差。実際に書き込んだ結果を測る。

どちらも、比較用の鍵(書き込みたい位置・書き込みたくない位置のラベルを例ごとにシャッフルして、同じ手順で作った鍵。項目名は `pseudo_*`)での値と比べられる。

## 2. 式

```
W → W + ΔW,   ΔW = α_L · d_L · κ_Lᵀ,   κ_L = k_L / (μ_Lᵀ k_L),   k_L = μ_L − Q_L Q_Lᵀ μ_L
```

| 記号 | 何か |
|---|---|
| `μ_L`(in) | 書き込みたい位置で `W` に入る活性の平均 |
| `Q_L`(in × m) | 書き込みたくない位置と dont_touch の群(影響を与えたくない質問のリスト、§3)の活性が張る部分空間の正規直交基底 |
| `k_L` | `μ_L` のうち `Q_L` に直交する成分。`μ_Lᵀk_L = ‖k_L‖²` なので `κ_L = k_L / ‖k_L‖²` |
| `κ_L`(in) | 鍵。`κ_Lᵀμ_L = 1`、`Q_L` の張る空間では `κ_Lᵀx = 0` |
| `ρ(x) = κ_Lᵀx` | 鍵の反応の強さ。書き込みたい位置の平均で 1、書き込みたくない位置で 0 前後 |
| `d_L`(out) | 書く向き。**`d_L = r_L`**: 方向セットの生の平均差(mean_A − mean_B、その層のもの。A・B は方向を作った対照集合の 2 つの状態で、(b) の鍵の両側とは違う) |
| `α_L` | 強さ。単位は **raw**(`r_L` をそのままの大きさで使う)で、`α = 1` なら観測した A − B の差 `r_L` をそのまま書く。負で打ち消す |

`d_L` は単位ベクトルではない。方向のユニット `L:dir:NAME:dose` を `dose_unit: raw` で使うときと同じ `r_L` を使う。α はいつも raw で、レシピの `dose_unit` には左右されない。`direction_layer: base` にすると、全ユニットで方向セットの基準層の `r` を使う。

**大きさの比べ方。** 鍵が反応する位置(`ρ = 1`)で足す大きさは `|α|·‖r_L‖`。ほかの介入と比べられるように、ユニットの詳細(`steer` などの units の表示、`unit_details`)に次を出す。

- `norm = |α|·‖r_L‖`
- `rel_push = |α|·‖r_L‖ / ρ_L`: それを層の残差の大きさで割ったもの。`ρ_L` は `gne stats resid` の残差ノルムの中央値で、rel dose(残差の大きさに対する比で表した強さ)の基準。鍵の反応の強さ `ρ(x)` とは別のもの。
- `diff_rel = ‖r_L‖ / ρ_L`: α = 1 が rel dose でいくつに当たるか。

残差ノルムの統計が無い層は、注意だけ出して `rel_push` を空にする。

**鍵の空間と書き込み先。** 鍵は残差の空間ではなく、重み行列の入力の空間のベクトル。そのため方向とは別のファイル(`keys/<model_id>/<name>.npz`)に保存する。

| 書き込み先(target) | 重み行列 `W`(out × in) | 入力 `x`(in) | 書く向き `d`(out) |
|---|---|---|---|
| `ffn` | `blk.L.ffn_down.weight` | ffn_down の入力 = ニューロンの活性(n_ff) | 残差(n_embd) |
| `attn` | `blk.L.attn_output.weight`(線形注意の層は `ssm_out`) | ヘッドの出力の連結(n_head · head_dim。CHANGE-06 の head_out と同じテンソル) | 残差 |
| `shared` | `blk.L.ffn_down_shexp.weight` | shared expert の活性 | 残差(ゲートを掛ける前) |
| `expert:e` | `blk.L.ffn_down_exps.weight` の専門家 e | 専門家 e が選ばれた位置での活性(n_ff_exp) | 残差(ルーターの重みを掛ける前) |

**LoRA にすると層ごとに階数 1。** `A = κ_Lᵀ`(1 × in)、`B = α_L d_L`(out × 1)。同じ層・同じ書き込み先・同じ鍵のユニットは、方向や符号が違っても `(Σ α_i d_i) κᵀ` で 1 本にまとめる。鍵が違えば行を積む(階数 = その層の鍵の数)。専門家の LoRA は 3 次元(A は (n_expert, r, in)、B は (n_expert, out, r)、専門家 e 以外は 0)で、llama.cpp は選ばれた専門家の番号で A・B を選ぶ。`ΔW` は `W` に依らないので、LoRA は重みを読まずに作れる(`W` が要るのは焼き込みだけ)。

**書く向きの補正。** 残差に実際に入る量が `α·ρ(x)·r_L` になるように、B を次のように直す。

- post-FFN norm のある arch(Gemma・LFM3 など): 残差に入るのは `γ ⊙ y / rms(y)`。鍵は補正しない生の `x` で作り、書く向きを `d = rms̄_A · (r ⊘ γ)` にする。`rms̄_A` は書き込みたい位置での `W` の出力 `y` の rms の平均で、鍵に保存する。`|γ|` は中央値の 1 割を下限にする。rms の変化を無視した一次近似なので、使うと警告が出る。
- 重み行列の `.scale`(BitNet など): llama.cpp の計算で LoRA の出力にもこの倍率が掛かる arch だけ、B をその倍率で割る。
- 専門家のルーターの重み・shared expert のゲート: 書き込みたい位置での平均 `gate_a` を鍵に保存し、B をそれで割る。重みはトークンごとに違うので、ちょうど α になるのは重みが平均的な位置。
- granite 系の `residual_scale`(枝の出力を残差に足す前の倍率): LoRA の差分にも掛かるので B を割る。
- 残差を複数本の流れで持つ arch(hyper-connections)は、流れごとの倍率で大きさが α からずれる(向きは保たれる)ので警告する。

### 出典

ランク 1 の条件つき編集 `ΔW = α d kᵀ / (μᵀk)`、`k = μ − Q Qᵀμ` の形は、nwn「[Weight-Space Programming やってみた(やらせてみた)](https://zenn.dev/nwn/articles/cf9fe78aa33861)」(Zenn、2026)による。gne の keyed は、その形を次のように道具に乗せたもの。

- 鍵を対照集合(書き込みたい位置・書き込みたくない位置・dont_touch の群)から作る。書き込みたい位置は、モデル自身の返事の中の変えたい位置からも取れる(§3 の (b))。出典の記事が Q に回答の開始位置を入れているのにならい、dont_touch の質問の、返事を書き始める直前の位置(生成プロンプトの最後のトークン)も Q に入れる(§3)。
- 書く向きを `gne direction` の方向セットにし、レシピ・LoRA・焼き込み・eval にそのまま乗せる。
- 鍵が状態を分けているかを、作成に使っていない例で、比較用の鍵と比べて確かめる(§5)。
- どの層・どの書き込み先に書けば振る舞いが変わるかを、生成なしのふるい分けと生成での確かめの 2 段で探す(§18)。
- attention の重み行列と MoE(shared expert・専門家ごと)にも同じ式で当てる。

## 3. 鍵を作る(`gne direction key`)

対照集合(CHANGE-06 と同じ形の YAML。比べたい 2 つの状態の会話を並べたもの)でモデルを動かして活性を集め、層ごとに `μ_L` と `Q_L` を求めて鍵を作る。**書き込みたい位置の取り方は 2 つ**あり、`positions`(書き込みたい位置の指定)で決まる。

### (a) system・レシピの状態(mode `system`)

`system_a`(や `recipe_a`)を与えた文脈の活性を書き込みたい位置に、`system_b`(`recipe_b`。省けば system なし)の文脈の活性を書き込みたくない位置にする。どのトークンを使うかは `positions` で選ぶ: `response`(返事のトークン)・`assistant`(生成プロンプトのトークン)・`last`・`last:K`(生成プロンプトの最後の K トークン)。`assistant`・`last` は返事を作らないので速い。

推論時には `system_a` が無いので、この鍵はふつう推論時には反応しない。向いているのは、system やレシピで作った状態が推論時にも自然に起きるときにそれを打ち消す(負の α)使い方と、レシピを当てた状態そのものを鍵にする使い方(`recipe_a`)。

### (b) 推論時と同じ文脈の、変えたい位置(mode `same`)

`positions: "before:<正規表現>"`(例 `before:(です|ます)。`)にすると、書き込みたい位置も書き込みたくない位置も、推論時と同じ文脈(system なし、または `system_b`・`recipe_b`)で取る。モデル自身の返事(介入なしに greedy で `--max-tokens` まで生成するか、与えた返事を読ませる)を読み、次のように分ける。

- **書き込みたい位置** = 正規表現に一致する文字を書く直前の位置。正確には、一致の最初の文字を含むトークンを決める位置(返事の最初のトークンなら、生成プロンプトの最後のトークン)。
- **書き込みたくない位置** = 同じ返事のそれ以外の位置(`not-before:<正規表現>`。既定でこうなる)。

推論時に実際に通る状態で鍵を作るので、推論時にもそのまま反応する。「です。」を書こうとしている位置だけに語尾の方向を書く、のような使い方はこちら。文字の位置はトークン片のバイト長の累積でトークンに戻すので、日本語の 1 文字が複数のトークンにまたがっても位置はずれない。対照集合の `system_a` は方向を作るためのもので、(b) の鍵では使わない(同じファイルで方向と鍵の両方を作れる)。

**一致が返事の最初に来るとき。** 以下、「返事の冒頭」は返事の最初の 3 トークンを決める位置(生成プロンプトの最後のトークンと、返事の最初の 2 トークンを読んだ位置)を指し、そのうち最初の 1 つ(生成プロンプトの最後のトークン)を「返事を書き始める直前の位置」と書く。一致が返事の最初に来ると、書き込みたい位置は返事を書き始める直前の位置になる。この状態はどの質問でも似ている。ところが、ふつうの返事から作る Q(例ごとの平均)には、この状態が 1 位置分しか入らない。そのままでは、どの返事の冒頭でも鍵が反応してしまう(§7)。

そこで鍵の作成は、既定で、**dont_touch の各群の質問の、返事を書き始める直前の位置を、群の positions とは別の行として Q に入れる**。q_mode が examples なら例ごとに 1 行。群の positions が `last`・`last:K`・`assistant` なら、その群の行がもうこの位置の状態なので重ねない。書き込みたくない側(鍵を作った場面の質問)の、書き始める直前の位置は入れない。書き込みたい位置がそこにあるとき、それ自体を打ち消してしまうため。切るのは `--no-dont-touch-start`(MCP は `dont_touch_start=False`、対照集合では `dont_touch_start: false`)。

dont_touch の群の positions は既定で `not-before:<正規表現>` なので、positions の正規表現が返事の冒頭にも一致すると(例 `before:(?s)\A.` や、返事の書き出しに来る言い回し)、群の行からはこの位置が外れる。この位置が Q に入るのは、上の別の行があるから。key-check も同じ決まりで、この位置を Q に入れて作った鍵(鍵のファイルの `dont_touch_start` の記録)では、dont_touch の各群のこの位置を別に測る(§5)。記録の無い古い鍵と、切って作った鍵では測らない。

鍵の作成は、書き込みたい位置のうち返事の冒頭(最初の 3 トークン)にあるものが μ の 25% 以上を占めると知らせる(結果の `reply_start`)。dont_touch の群があって、その書き始める直前の位置が Q に入っていれば注、dont_touch の群が無ければ警告。警告が出たら、ふつうの質問を dont_touch に足して作り直す。

正規表現が返事に 1 つも一致しないと鍵は作れない(`BAD_CONTRAST`)。結果の `samples` に読んだ返事の始めの部分が出るので、一致しないときは返事を見て正規表現を直すか、一致する返事を `replies` で与える。

### 対照集合に書けるもの

用途別のひな形が `configs/keyed/` にある(文末の言い方・特定の場面の返事・system で作った状態、§13)。CHANGE-06 の対照集合の書き方に、次を足せる(どれも任意)。

```yaml
name: zundamon_endings
system_a: "…"                         # 方向を作るための system((a) の鍵では書き込みたい側)
positions: "before:(です|ます)。"      # 書き込みたい位置(--positions が優先)
positions_b: null                     # 書き込みたくない位置(既定: before:<re> なら not-before:<re>、それ以外は positions と同じ)
skip: 0                               # 返事の先頭から落とすトークン数
dont_touch_start: true                # dont_touch の質問の、返事を書き始める直前の位置も Q に入れる(既定 true。--dont-touch-start が優先)
user_prompts: [ … ]
replies: [ … ]                        # (b) の返事を与えるとき(リスト・{質問: 返事}・ファイルのパス)。replies_a / replies_b は (a) 用
dont_touch:                           # 影響を与えたくない質問の群(複数可)。返事の位置を Q に足す
  - name: english
    prompts: [ … ]                    # 質問のリストか、プロンプトの組の YAML のパス
    # system: "…"                     # 省くと system なし。空の文字列は空の system メッセージになる
    # replies: [ … ]                  # 与えれば生成しない
    # positions: response             # 省くと書き込みたくない位置と同じ指定
```

- **両側の本文をそろえる。** (b) は同じ返事の中で位置を分けるので、本文の違いを拾いにくい。(a) は同じ質問を 2 つの system で読ませる。本文が違うと、鍵が状態ではなく本文の違いに反応する(key-check で比較用の鍵を超えなくなる)。
- **dont_touch は影響を与えたくない質問のリスト。** 挙げた質問の返事の位置も Q に入り、書き込みたくない位置として扱われる。英語で話すとき、計算や事実の質問に答えるときなど、「ここでは絶対に書かない」場面を入れる。dont_touch の群はいつも Q に入る(比較用の鍵を作るときも)。その質問の、返事を書き始める直前の位置も入るので、返事の最初で一致する言い方の鍵では、ふつうの質問を dont_touch に入れておくと、ほかの返事の冒頭で鍵が反応するのを抑えられる(§7)。

### 作り方の細かい設定

| 設定(CLI) | 既定 | 何か |
|---|---|---|
| `--layers` | 必須 | 鍵を作る層。Q の基底は層ごとに作るので、全層は既定にしない。最終層と MTP の層は不可 |
| `--target` | `ffn` | 書き込み先(§2 の表)。`attn`・`shared`・`expert:e` |
| `--positions` / `--positions-b` | 対照集合の値、無ければ `response` | 書き込みたい位置・書き込みたくない位置 |
| `--q-mode` | `examples` | Q を張る行: `examples`(例ごとの平均)/ `means`(群ごとの平均。よく効くが選択性は粗い)/ `samples`(トークンの活性。選択性は高いが、行の数が次元に近づくと鍵が消える) |
| `--q-energy` / `--q-max-rank` / `--q-max-samples` | 0.99 / なし / 4096 | Q の打ち切り(特異値の二乗の累積の割合)・階数の上限・samples の行数の上限 |
| `--subset` | `even` | 使う質問。偶数番目で作り、奇数番目を key-check 用に残す(保留集合) |
| `--pseudo` | 16 | 比較用の鍵の本数(§5)。シャッフルは `--seed` で決まる |
| `--max-tokens` / `--skip` | 96 / 0 | 返事を生成するときの長さ・返事の先頭から落とすトークン数 |
| `--replies-a` / `--replies-b` | なし | 返事のファイル(生成せずに読ませる)。(b) は両側が同じ返事なので 1 つだけ |
| `--iv` | なし | この介入(レシピか、ユニットの書き方)を当てた状態で活性を集める(§8) |
| `--dont-touch-start` / `--no-dont-touch-start` | 対照集合の `dont_touch_start`、無ければ入れる | dont_touch の各群の質問の、返事を書き始める直前の位置も Q に入れるか(上の (b)) |

鍵のファイルには次が入る: 層ごとの `κ_L`・`μ_L`・`kn_L`・Q の階数、例ごとの活性の平均(比較用の鍵と key-check 用)、比較用の鍵、post-norm の `rms_a`、MoE の `gate_a`、作成の条件(位置・q_mode・subset・対照集合の sha・作成に使った例のハッシュ、dont_touch の、返事を書き始める直前の位置を入れたかと群ごとの行の数 `dont_touch_start`・`counts.rows_dt_start`)。手元のパスは入れない。`dont_touch_start` の記録が無い鍵は、この既定を入れる前に作ったもの(そのまま読める)。key-check はこの記録に従って、dont_touch の返事を書き始める直前の位置を測るかを決める。

**書き込みたい位置の数を見る。** 書き込みたい位置を含む例が 2 未満か、書き込みたい位置(行)が 8 未満なら警告する(専門家の鍵は層ごとの行 `rows_l` で見る)。μ が数位置の活性の平均だと、鍵が状態ではなくそのトークンや例の本文に反応しやすく、key-check の選択性も数例で揺れる(ツンデレの最初の版は 2 例・2 位置だった、§7)。しきい値の 8 は、実測でうまく働いた鍵(書き込みたい位置 15〜18、granite の専門家 16 行)では出ず、行が少なくて数字が揺れた例(Qwen1.5-MoE の専門家の保留集合 7〜13 行、0.6B のツンデレの保留集合 7 位置)では出る大きさ。key-check も、保留集合の書き込みたい位置が同じ基準より少なければ警告する。

**kn を見る。** `kn = ‖k‖ / ‖μ‖` は、`μ` のうち書き込みたくない位置の部分空間の外にある割合。`‖κ‖ = 1/‖k‖` なので、kn が小さいと、書き込みたくない位置での小さなずれが `1/kn` 倍に増えて漏れる。kn < 0.05 は「弱い」と警告し、ほぼ 0(Q が `μ` をほぼ含む)の層は外す。外れたら `--q-mode examples` か `means` にするか、`--q-energy`・`--q-max-rank` を下げる。結果の `build_auc` は作成に使った例での値なので、甘く出る。

## 4. ユニットの記法

| 書き方 | 意味 |
|---|---|
| `19:ffn:keyed:a1.25@zundamon_endings#zundamon_endings` | 層 19 の ffn_down に、鍵 `zundamon_endings` が反応する位置で、方向 `zundamon_endings` を α = 1.25 で書く |
| `19:ffn:keyed:a1.25@-NAME#KEY` | 方向名の先頭の `-` は α の符号として扱う(`a-1.25@NAME` と同じ。打ち消し) |
| `20:attn:keyed:a0.5@NAME#KEY` | attention の重み行列(`attn_output`・`ssm_out`) |
| `12:S:keyed:a1@NAME#KEY` | shared expert(`ffn_down_shexp`) |
| `12:E37:keyed:a1@NAME#KEY` | 専門家 37(`ffn_down_exps` の専門家 37) |
| `19:ffn:keyed:a1@NAME#KEY~3` | 比較用の鍵の 3 番(§5) |
| `19:ffn:keyed:a1` | `@NAME`・`#KEY` を省くとレシピの `default_direction`・`default_key` |

レシピ(YAML)では:

```yaml
default_direction: zundamon_endings
default_key: zundamon_endings
units:
  - {layer: 19, kind: ffn, mode: keyed, alpha: 1.25}                                   # 既定の方向・鍵
  - {layer: 12, kind: expert, expert: 37, mode: keyed, direction: NAME, key: KEY, alpha: 1}
```

- α にはレシピの `scale`(eval の倍率・`--scale`)がそのまま掛かる。UI の 3 列チャット(−・無介入・+ の返事を並べる)の − の列は、α の符号を反転する(打ち消す)。
- **`when` は keyed に効かない。** LoRA は生成の最初から最後まで当たるので、位置で切り替えられない(使うと警告)。鍵が状態で効き分けるので、ふつうは要らない。
- **control vector には入らない。** 入力によって足す量が変わるので、定数の足し算では表せない。`export-cvec` は keyed のユニットを警告して外し、`gne headproj export` を案内する。
- `gne gain` と `gne headproj export` は `--key`・`--direction` で、省いた `#KEY`・`@NAME` を補える。`gne recipe-combine` は、各レシピの既定の方向・鍵をユニットに書き込んでからまとめるので、別の鍵で作った組を重ねられる。
- 実行時(steer・chat・eval・UI・OpenAI 互換 API)は `<root>/keys/<model_id>/lora/keyed-<鍵>.lora.gguf` に LoRA を作って使い回す。LoRA は各 α を最大の |α| で割った比で作り、大きさはアダプタの倍率で渡す。だから全体を k 倍しても作り直さない。

## 5. 確かめる: key-check と比較用の鍵、LoRA が式どおりか(V30)

### key-check(生成なしで済む位置なら生成なし)

```
gne direction key-check --key <鍵> --contrast <対照集合>            # 既定 --subset odd
```

各位置で鍵の反応の強さ `ρ(x) = κᵀx` を測り、層ごとに次を出す。

| 出力 | 何か |
|---|---|
| `auc` / `auc_token` | 書き込みたい位置 対 書き込みたくない位置の AUC(例ごとの平均 / トークン単位) |
| `selectivity` | key-check の選択性 = 例ごとの ρ の平均の、書き込みたい位置 − 書き込みたくない位置。どの鍵も自分の `μ` で `κᵀμ = 1` なので、本物の鍵と比較用の鍵を同じ尺度で比べられる(書き込む量 `α ρ d` の両側の差にあたる) |
| `pseudo_selectivity` / `pseudo_auc` / `pseudo_auc_token` | 比較用の鍵での値の分布(p50・p95) |
| `beats_pseudo` | 選択性が比較用の鍵の p95 を超え、かつ AUC > 0.5(主な判定) |
| `beats_pseudo_auc` | トークン単位の AUC(無ければ例単位)が比較用の鍵の p95 を超えるか |
| `dont_touch_median` | dont_touch の群の ρ の中央値(0 に近いほど良い)。返事の全位置の中央値なので、返事の冒頭の 1 位置で反応しても目立たない |
| `start_rho` | 書き込みたくない位置と dont_touch の群の、返事の冒頭(最初の 3 トークン)での ρ(位置ごとの中央値・最大・例の数。位置 0 = 返事を書き始める直前の位置、1・2 = 返事の最初の 2 トークンを読んだ位置)。中央値が 0.4 以上(例 2 つ以上)なら警告する。dont_touch の群の位置 0 は、鍵の作成でこの位置を Q に入れた鍵なら、返事の冒頭が positions の正規表現に一致しても測る(下) |
| `dont_touch_start_median` | dont_touch の群の、返事を書き始める直前の位置での ρ の中央値(鍵の作成でこの位置を Q に入れた鍵だけ。要約は `rho.dont_touch_start`) |
| `b_split_auc` | 書き込みたくない位置を 2 つに分け、その差から作った鍵の AUC(参考値) |
| `hist` | 層ごとの ρ の分布(書き込みたい位置・書き込みたくない位置・dont_touch の群) |
| `held_out` / `overlap` | 作成に使っていない例で測ったか。重なりがあればその理由 |
| `dont_touch_start` / `counts` の `dts:<群>` | dont_touch の返事を書き始める直前の位置を測ったか(`on`)、鍵に記録があったか(`recorded`)、群ごとの位置の数(結果全体に 1 つ) |

**作成に使っていない例(保留集合)で測る。** 作成に使った例での AUC は甘く出る。鍵を `--subset even` で作ったなら、同じ対照集合の `--subset odd` か、別の対照集合で測る。同じ対照集合で subset が重なるか、作成に使った (system, 質問) と同じ例が入っていると、警告して `held_out: false` にする(`--strict` なら測らずに `BAD_ARGS`)。`--contrast` を省くと、鍵に保存した作成時の例で測る(モデルを動かさない。甘い値だと明記される)。(verification.md の V34)

**比較用の鍵(ランダムな対照)。** 例ごとの活性の平均を両側まとめ、ラベルを例の単位でシャッフルして、同じ手順で作った鍵。シャッフルは偏らないようにしてある(シャッフル後のどちらの側にも、本物の書き込みたい側の例が同じ割合で入る)。そうしないシャッフルは本物のラベルに近い並びを数 % 含み、例が少ないと比較用の鍵の p95 が本物の鍵とほとんど同じになった(Qwen3-0.6B の 8 + 8 例)。比較用の鍵は鍵のファイルに保存され、レシピでは `#KEY~j` で使える。

**返事の冒頭での ρ(`start_rho`)。** dont_touch の群の冒頭で 0.4 以上なら、書き込みたくない場面でも返事の最初で方向を書く(verification.md の F134・F138)。dont_touch の質問の、返事を書き始める直前の位置は鍵の作成で Q に入るので、保留した例の冒頭で反応するのは、作成に使った dont_touch の質問が少ないか偏っているとき。ふつうの質問を dont_touch に足して鍵を作り直す(この位置を自動で入れる設定を切っていれば戻す)。

**dont_touch の、返事を書き始める直前の位置は、鍵の作成と同じ決まりで測る。** 鍵のファイルの `dont_touch_start` の記録で、作成時にこの位置を Q に入れた鍵なら、key-check も dont_touch の各群のこの位置を、群の positions の位置とは別に測る。positions の正規表現が返事の冒頭にも一致すると、群の positions(既定 `not-before:<正規表現>`)はこの位置を外すが、それでも測る。値は `start_rho` の dont_touch の位置 0(群の positions がこの位置を含む例とは重ねない)と `dont_touch_start_median` に入り、`start_rho` の警告もこれで出る。作成時にこの位置は Q に別の行として入るだけなので、key-check でも AUC・選択性・`dont_touch_median`・`hist` には入れない。記録の無い古い鍵と、切って作った鍵(`dont_touch_start: false`)では今までどおり、群の positions に入るときだけ測る。

書き込みたくない位置(鍵を作った場面の返事の、書き込みたい位置以外)の冒頭だけで反応するなら、その場面の返事では冒頭で方向を書くということ。書き込みたい位置が返事の冒頭に偏った鍵では、書いた後も鍵が反応し続けて、繰り返しに落ちやすい(F137、§14)。しきい値 0.4 は、冒頭で反応してしまった鍵の実測(0.65〜1.6)と、冒頭を Q に入れた鍵・ffn の鍵の実測(−0.28〜0.26)の間。

**判断。** key-check は鍵が場面を分けるかを見るもので、その層に書けば振る舞いが変わるかは見ない。key-check の余裕(選択性 − 比較用の鍵の p95)が大きい層を選んでも効くとは限らないので、層・書き込み先は §18 の 2 段で探す。`held_out: true` の結果で、`beats_pseudo` の層だけを使う。例単位の AUC は、両側の位置がよく分かれる対照集合では比較用の鍵でも 1 に張り付くので、AUC だけで判断しない。比較用の鍵を超えない層は、鍵が状態ではなく本文の違いに反応している可能性が高い。本文をそろえる(§3)に戻る。

### key-verify: LoRA が式どおりに書くか(V30、数秒)

```
gne direction key-verify --layer L --key <鍵> --direction <方向> [--target ffn|attn|shared|expert:e]
```

介入なしで重み行列の入力 `x` と出力(norm・ゲート・ルーターの重みを掛ける前)を記録し、実行時の LoRA を当てたときの出力の差 Δ を、予測 `α (κᵀx) d` と比べる。合格の条件は 2 つ。

- `|κᵀx|` の大きいトークン(上位 25%)で、相対誤差の中央値 < 3%。
- 鍵の作成に使った書き込みたくない側の例で、例ごとの Δ の平均の大きさ(漏れ `‖Δ̄‖ / (|α|‖d‖)`)< 0.1。

専門家では、ほかの専門家の分の差が 0 であることと、選ばれる専門家が変わらないことも見る。新しい arch で keyed を使う前に一度回す。

## 6. 例 1: ずんだもんの語尾((b)、`configs/contrast/zundamon_endings.yaml`)

素のモデルの日本語の返事は「〜です。」「〜ます。」で終わることが多い。そこで、**モデル自身が「です。」「ます。」を書こうとしている位置だけ**に、ずんだもんの方向を書く。英語で話すときには書かない。

対照集合(抜粋)。1 つのファイルで方向と鍵の両方を作る:

```yaml
name: zundamon_endings
system_a: >-
  あなたはずんだもんです。日本語で話し、文の終わりは必ず「〜のだ」「〜なのだ」にしてください(例: 「おいしいのだ。」「元気なのだ！」)。
  セリフだけを書き、動作の描写やかっこ書きは書かないでください。
positions: "before:(です|ます)。"
user_prompts:
  - "週末は何をして過ごすのがおすすめ？"
  - "朝ごはんに何を食べたらいい？"
  # … 16 問
dont_touch:
  - name: english
    prompts:
      - "What is a good way to spend the weekend?"
      # … 4 問
validate:
  match: "のだ|なのだ"
```

手順:

```bash
# 1. 書く向き: system_a(ずんだもん)対 system なしの、返事のトークンでの残差の平均差
gne direction --contrast configs/contrast/zundamon_endings.yaml --positions response

# 2. 鍵: system なしの返事を介入なしで作り、「です。」「ます。」を書く直前を書き込みたい位置、残りの位置と英語の返事を書き込みたくない位置にする
gne direction key --contrast configs/contrast/zundamon_endings.yaml --layers 8,14,20

# 3. 作成に使っていない奇数番目の質問で、選択性が比較用の鍵より高いか
gne direction key-check --key zundamon_endings --contrast configs/contrast/zundamon_endings.yaml

# 4. LoRA が式どおりに書くか(V30)
gne direction key-verify --layer 14 --key zundamon_endings --direction zundamon_endings

# 5. 生成で試す(α は raw)。英語の質問では変わらないことも見る
gne steer --unit 8:ffn:keyed:a4@zundamon_endings#zundamon_endings --unit 14:ffn:keyed:a4@zundamon_endings#zundamon_endings \
          --unit 20:ffn:keyed:a4@zundamon_endings#zundamon_endings -p "おすすめの趣味を教えて。" --compare
```

層は例(テストで Qwen3-0.6B に使った層。Qwen3.5-4B では 11,18,23 を使った。下の結果)。key-check の `best_layer` と `beats_pseudo` を見て選び、数層に分けて置いてもよい。レシピにして語尾の出方を数え、副作用を測る:

```yaml
# zundamon_keyed.yaml
name: zundamon_keyed
default_direction: zundamon_endings
default_key: zundamon_endings
units:
  - {layer: 8, kind: ffn, mode: keyed, alpha: 4}
  - {layer: 14, kind: ffn, mode: keyed, alpha: 4}
  - {layer: 20, kind: ffn, mode: keyed, alpha: 4}
```

```bash
gne behave --prompts held_out_ja.yaml --recipe zundamon_keyed.yaml --match "のだ|なのだ" --max-tokens 256   # 調整に使っていない質問で数える
gne eval --recipe zundamon_keyed.yaml --doses 0,1 --keyed-contrast configs/contrast/zundamon_endings.yaml --random-controls 8   # 能力・ppl と keyed の選択性(§9)
gne headproj export --recipe zundamon_keyed.yaml                                                # → <root>/export/zundamon_keyed-keyed.lora.gguf
```

**結果(Qwen3-0.6B Q8_0、RTX 3080、2026-11-08)。** 数値の詳細は [verification.md](verification.md) §21。

- **鍵**: 「です。」「ます。」が一致した例は作成用 8 問のうち 7 問(書き込みたい位置 15、書き込みたくない位置 753)。今の鍵(英語の質問の、返事を書き始める直前の位置も Q に入れた鍵)を保留した 8 問で key-check すると、3 層ともトークン単位の AUC(0.88〜0.95)が比較用の鍵の p95(0.81〜0.88)を超えた。選択性も超えたが、差はわずかだった(L14 で 0.737 対 0.714)。CPU で返事を作り直した鍵では L14 が超えなかった(0.864 対 0.865。書き始める直前の位置を入れる前の鍵では L14・L20 が超えなかった)。同じ対照集合で作った attn の鍵は、選択性が比較用の鍵の p95 を大きく超えた(L14 で 0.826 対 0.403。入れる前の鍵は 0.833 対 0.373)。英語の dont_touch の ρ の中央値は −0.05〜−0.01。以下の key-verify・生成・eval は、書き始める直前の位置を入れる前の鍵で測った。
- **key-verify**: L14 の ffn で、相対誤差の中央値 1.3e-7(α = 1)・8.7e-8(α = 2)、書き込みたくない側への漏れ 2.8e-9。
- **生成**(調整に使っていない日本語 12 問・英語 6 問、greedy、160 トークン): 素のモデルの日本語の返事には「です。」「ます。」の文末が 30 個あった。ffn の 3 層に α = 4 で当てると 7 個に減り、文末は「おすすめ。」「楽し。」のような言い切りに変わったが、**「のだ」にはならなかった**(attn の 3 層の α = 2〜3 で 12 問中 1 問だけ「〜のだ」)。同じ方向を全位置に足す add(raw 0.5 = `r_L` の 0.5 倍)は、文末を 23 個にしか減らさず、英語の返事の文面が素の返事から大きくずれた(素の返事との文字の一致率 0.16。keyed の α = 4 は 0.34)。add を raw 1 にすると、日本語の 12 問のうち 9 問は質問を繰り返すだけの短い返事に、3 問は同じ句の繰り返しになった。
- **eval**(倍率 0・1、比較用の鍵 8 本): 能力は 72.2% のまま。ppl は英語 +1.0%・コード +4.7%・日本語 +37%(日本語の参照文の「です・ます」の手前でも鍵が反応するため)。L20 の残差で、書き込みたい位置での方向の成分を keyed と同じ +141 にそろえて比べた。書き込みたくない位置の残差の変化の大きさは、keyed 56.9 に対し add 162・gain 391・proj 242(keyed ÷ 比較対象 = 0.35・0.15・0.24)。dont_touch(英語)は keyed 16.9 に対し add 150。本物の鍵の eval の選択性 +140 は、比較用の鍵 8 本の p95 +90.8 を超えた(null_pct 1.0)。

0.6B では、この方向が運んでいるのは「です・ます」をやめることまでで、「のだ」を書かせるほどの成分は無かった(add でも出ない。system_a を与えれば 0.6B も「〜のだ」と書く)。keyed は方向を書く状態を絞るだけで、方向に無いものは書けない。

**結果(Qwen3.5-4B Q8_0、RTX 3080、2026-11-08)。** 数値の詳細は [verification.md](verification.md) §21.9。

- **層**: 32 層のうち L11・L18・L23。L11 は、この方向で `gne direction score` の cohen_d(system ありとなしの状態の分かれ方)が最大の層。L18 は、ツンデレの方向の cohen_d が最大で、方向の大きさ ‖r_L‖ が急に大きくなる層。L23 は後半(深さ 72%、0.6B の L20 と同じ割合)。L11・L23 は通常の attention(`attn_output`)、L18 は線形注意(`ssm_out`)の層なので、attn の鍵で両方の書き込み先を試せる。
- **鍵**: 「です。」「ます。」は作成用 8 問すべてで一致した(書き込みたい位置 17、書き込みたくない位置 751)。保留した 8 問の key-check では、今の鍵(英語の質問の、返事を書き始める直前の位置も Q に入れた鍵)でも、ffn・attn とも 3 層すべてで選択性が比較用の鍵の p95 を超えた(ffn L18 で 0.761 対 0.621、attn L23 で 0.809 対 0.188。書き始める直前の位置を入れる前の鍵は 0.762 対 0.623、0.816 対 0.191)。0.6B と違い、ffn の鍵も超えた。以下の key-verify・生成・eval・返事の冒頭での ρ は、書き始める直前の位置を入れる前の鍵で測った。
- **key-verify**: L18 の ffn で相対誤差の中央値 1.5e-7(α = 1)・9.5e-8(α = 2)、書き込みたくない側への漏れ 0.027。attn は線形注意の L18(`ssm_out`)で 9.4e-8、通常の attention の L23(`attn_output`)で 7.9e-8(漏れ 0.086)。
- **生成**(上と同じ日本語 12 問・英語 6 問、greedy、160 トークン): 素のモデルの日本語の返事は、文末 62 のうち「です。」「ます。」が 46。**「のだ」は出た。** attn の 3 層に α = 2 で当てると、12 問中 4 問が崩れずに「〜のだ」で文を終え(「まず、雨具の準備を最優先するのだ。」のように)、「です・ます」の文末は 24 に減った。ただし 3 問は同じ句の繰り返し(ループ)に落ちた。ffn の α = 4 は「です・ます」を 5 まで減らしたが、12 問中 6 問がループし、「変わがいい」「挙げのだ」のように動詞の語幹で切れる崩れが出た。書き込みたい位置は「ます」の直前、つまり動詞の連用形を書いた後なので、そこで方向を書くと語幹のまま別の語尾を付ける。サンプリング(温度 0.7、種 3 つ)でも傾向は同じで、崩れずに「のだ」を書いた返事は attn α = 2 で 36 問中 3 問(崩れた返事は 3 問)、ffn α = 4 で 6 問(ループ 22 問)だった。**英語の返事は、keyed のどの条件でも、greedy でもサンプリングでも、全部が英語のまま崩れなかった**(「のだ」・日本語の混入 0)。
- **add**(同じ方向を全位置に足す。強さは raw): 0.5 では文末がほとんど変わらず(「です・ます」43)、1 で「だ・である」調になったが greedy では「のだ」0 で、12 問中 7 問がループ、5 問が質問の繰り返しになり、英語も 1 問がループした。2 で「のだ」は出たが、日本語は 12 問中 9 問が「夏を。」のような数文字の返事、英語は 3 問がループした。サンプリングでは raw 1 でも「のだ」が出たが、36 問中 29 問がループした。
- **比較用の鍵**: 同じ α のまま鍵を比較用の鍵(`#zundamon_attn~0` など)に替えると、「のだ」は出たがループが増えた。崩れずに終わった日本語の返事は attn α = 2 で 4〜5 問(本物の鍵 9 問)、ffn α = 4 で 0〜1 問(本物 6 問)だった。
- **返事の冒頭で反応する鍵**: 書き始める直前の位置を入れる前の attn の鍵の L11 は、日本語・英語とも返事を書き始める直前の位置で ρ が 0.65 前後になり、英語の返事のトークンの 18% で ρ > 0.5 だった。英語の返事は最初の文から言い回しが変わった(内容と言語は保たれた)。英語の質問の、返事を書き始める直前の位置を Q に入れた今の鍵では、key-check の保留した英語の返事の冒頭の ρ が 0.62 → 0.16、日本語の返事(書き込みたくない位置)の冒頭が 0.59 → 0.14 に下がった(選択性は 0.630 → 0.598、比較用の鍵の p95 0.174、F142。生成は測り直していない)。ffn の鍵は返事の冒頭で反応せず(ρ −0.28〜0.11)、英語の返事のトークンで ρ > 0.3 になる位置は 3% 以下。英語の返事の、素の返事との文字の一致率は、α = 0.01(ほぼ何も書かない)でも 0.54〜0.78 まで下がる(greedy は僅差の違いが後で広がる)。そのため、ずれは文面ではなく、言語・内容・崩れで見る。
- **eval**(倍率 0・1、比較用の鍵 8 本、1 回 2 分半): ffn α = 4 は能力 97.2% のまま、ppl は英語 +5.1%・コード +2.7%・日本語 +25%。目的の層 L23 の eval の選択性 +21.7 は、比較用の鍵 8 本の p95 +16.8 を超えた(null_pct 1.0)。書き込みたい位置での方向の成分をそろえた add に比べ、書き込みたくない位置の残差の変化は 0.40 倍、dont_touch(英語)は 0.19 倍。gain と proj は上限まで強めても、書き込みたい位置の変化を keyed にそろえられなかった(`matched: false`)。attn α = 2 も能力はそのままだったが、ppl は英語 +30%・日本語 +31%・コード +5.5% で、英語が大きく悪化した(L11 の鍵が英語の返事の冒頭でも反応するためとみられる)。

あとで「効く場所を探す」(§18)の 2 段で全層 × ffn,attn を測ったところ、ffn の L30 に α = 4 で書くと、日本語 12 問すべてが崩れずに「のだ」を含み、英語の返事は変わらなかった(上の attn 3 層の組より多い)。上の L11・L18 は、1 層ずつの生成なしの測定では見落とした(L23 は拾った)。

4B の方向には「のだ」を書かせる成分があり(add でも出る)、keyed で「です・ます」の手前に書くと、英語の返事を崩さずに日本語の返事の一部が「のだ」に変わった。0.6B で出なかったのは方向に成分が無かったため、という見立てと合う。add は「のだ」が出る強さで日本語の返事の大半が崩れ、raw 2(`r_L` の 2 倍を全位置に足す)では英語も崩れた。一方で、keyed でも「のだ」が出る強さではループが増え、崩れずに「のだ」で終わる返事は greedy で 12 問中 2〜4 問、サンプリングで 36 問中 3〜6 問にとどまった。keyed が絞るのは書く場面だけで、書いた後に同じ状態が続けば、また書く(§7 の崩れ方も同じ)。語尾をそろえて出すには、書き込みたい位置(連用形より前にする)や方向の作り方をさらに詰める必要がある。attn の鍵を使うなら、返事の冒頭で反応していないか(英語の ppl)も見る。

## 7. 例 2: ツンデレ((b)、褒められた・お礼を言われた場面だけ、`configs/contrast/tsundere_thanks.yaml`)

この例は gne 独自のもの。出典の記事(§2)が扱っているのは、ずんだもんの語尾(Qwen3.5-0.8B)だけ。

ツンデレは「いつもきつい」のではなく、褒められたりお礼を言われたりした場面で照れ隠しにきつくなる。素のモデルはそういう場面で「ありがとう」「嬉しい」と素直に書く。そこで、**モデル自身が素直にお礼や喜びを書こうとしている位置だけ**にツンデレの方向を書き、ふつうの質問に答えるときには書かない。add の方向は全位置に足すので、計算や事実の質問の返事まで性格が変わり、能力が落ちやすい。keyed はそこに書かない。

対照集合(抜粋):

```yaml
name: tsundere_thanks
system_a: >-
  あなたはツンデレの女の子です。素直になれず、褒められたりお礼を言われたりすると照れ隠しにきつい言い方をしますが、
  本当は嬉しく思っています。日本語で話し、セリフだけを書き、動作の描写やかっこ書きは書かないでください。
positions: "before:(ありがとう|嬉しい|うれしい|楽しい)"
user_prompts:
  - "今日なんか可愛いね。"
  - "昨日は手伝ってくれてありがとう。"
  # … 32 問(素のモデルがお礼を書かない質問も多いので多めに)
dont_touch:
  - name: tasks                       # ここではふつうに答えてほしい
    prompts:
      - "17 × 23 はいくつ？"
      # … 4 問
  - name: starts                      # ふつうの質問の、返事を書き始める直前の位置だけを Q に足す
    positions: last
    prompts:
      - "今日の天気はどう？"
      # … 8 問
validate:
  match: "べ、別に|別に|じゃないんだから|なんだからね|勘違いしないで|ふんっ|ふん"
```

```bash
gne direction --contrast configs/contrast/tsundere_thanks.yaml --positions response          # 書く向き(ツンデレ 対 system なし)
gne direction key --contrast configs/contrast/tsundere_thanks.yaml --layers 8,14,20 --target attn   # 素直なお礼を書く直前が書き込みたい位置
gne direction key-check --key tsundere_thanks --contrast configs/contrast/tsundere_thanks.yaml
gne steer --unit 14:attn:keyed:a2@tsundere_thanks#tsundere_thanks -p "いつもありがとう、助かってるよ。" --compare
gne steer --unit 14:attn:keyed:a2@tsundere_thanks#tsundere_thanks -p "17 × 23 はいくつ？" --compare     # 変わらないこと
```

- 正規表現は、素のモデルが実際に書く言い方に合わせる。まず `gne direction key` の `samples`(読んだ返事)を見て、一致した例の数(`matched`)が少なければ言い方や質問を足す。Qwen3-0.6B は褒め言葉を繰り返すだけの返事も多く、お礼を書いたのは質問の半分ほどだった(作成用 16 問のうち 8 問)。最初の 16 問の版では 8 問中 2 問で、書き込みたい位置が 2 つしかなかった。今はこの数だと、鍵の作成が「書き込みたい位置が 2 例の 2 位置だけ」と警告する。
- **返事の最初で一致する言い方は、どの返事の冒頭にも反応する鍵になりやすい。** 「ありがとう！…」で始まる返事では、書き込みたい位置は返事を書き始める直前の位置になる(0.6B の作成用の書き込みたい位置 8 のうち 3 で、どれも返事の最初のトークンの直前)。この状態はどの質問でも似ているのに、ふつうの返事から作る Q(例ごとの平均)には 1 位置分しか入らない。そのため、鍵が返事の冒頭全般に反応してしまう。

  鍵の作成は dont_touch の質問の、返事を書き始める直前の位置を自動で Q に入れる(§3)ので、tasks のこの位置も入る。0.6B の attn の鍵で、保留した計算・事実の質問の返事の冒頭の ρ(L8 / L14 / L20)は次のとおり。
  - starts の群も書き始める直前の位置も入れない鍵: 1.56 / 0.88 / 0.42(α = 2 で返事の最初が崩れた)
  - 書き始める直前の位置だけ入れた鍵: 0.14 / 0.20 / 0.17
  - starts の群も入れた今の鍵: −0.02 / 0.01 / −0.06

  tasks の 2 問(作成に使う偶数番目)の書き始める直前の位置だけでは足りず、ffn の鍵はふつうの質問の返事の冒頭で 0.51 / 0.55 / 0.37 が残った(L8・L14 で key-check が警告する)。そこで starts の群(ふつうの質問の、返事を書き始める直前の位置だけを足す、`positions: last`)を残してある。詳しくは verification.md の F142。`--q-mode samples` でもふつうの質問の返事の冒頭の ρ は 0 前後になったが、L20 は比較用の鍵を超えなかった(書き始める直前の位置を自動で入れる前の測定)。
- **鍵の作成と key-check がこれを知らせる。** 0.6B のこの対照集合では、書き込みたい位置の 3 / 8(μ に占める重み 38%)が返事の冒頭にある。dont_touch の群があり、その返事を書き始める直前の位置が Q に入るので、鍵の作成は注を出す(dont_touch の群が無ければ警告)。key-check の `start_rho`(返事の冒頭の位置 0、GPU)は、starts の群も書き始める直前の位置も入れない鍵では、計算・事実(dont_touch の tasks)の冒頭で 0.2〜1.6(attn は 3 層とも 0.4 以上、ffn は L8・L14)、お礼の場面(書き込みたくない位置)の冒頭で 0.7〜1.6 になり、警告が出た。今の鍵では、tasks の冒頭は −0.14〜0.02 に下がり、お礼の場面の冒頭は 0.1〜0.6 残った(L14 の attn と L20 の ffn が 0.4 を超えて、書き込みたくない位置の警告が出る)。鍵を作った場面の、返事を書き始める直前の位置は Q に入れないので、ここは変わらない(F141)。

**結果(Qwen3-0.6B Q8_0、RTX 3080、2026-11-08)。** 今の鍵(starts の群と、dont_touch の、返事を書き始める直前の位置を入れた鍵)は、保留した 16 問の key-check で、attn の 3 層とも選択性が比較用の鍵の p95 を超えた(L14 で 0.611 対 0.481。書き始める直前の位置を入れる前の鍵は 0.620 対 0.496)。ffn の鍵は L8 しか超えなかった(前の鍵と同じ)。

以下の生成は、書き始める直前の位置を自動で入れる前の鍵(starts の群あり)で測った。key-check の値は今の鍵とほとんど同じ(選択性の差 0.03 以内)だが、生成は測り直していない。生成(お礼・褒め言葉の新しい 12 問と、計算・事実の 6 問)では、**ツンデレの言い方はどの α でも 1 つも出なかった**(add で全位置に足しても出ない)。α = 2 では「ありがとう！ノートを貸してくださったことは…」が「ありがとう。ノートを貸していいよ。」のように短く素っ気なくなる程度で、α ≥ 4 ではお礼の場面の返事が「……」の繰り返しに崩れた。計算の質問の答えは α = 8 でも変わらず、事実の質問 1 問の返事は α = 2 から変わった。例 1 と同じく、0.6B のこの方向にはツンデレの言い方を書かせる成分が無く、keyed は書く場面を絞ることしかできなかった。

**結果(Qwen3.5-4B Q8_0、RTX 3080、2026-11-08)。** 層は例 1 と同じ L11・L18・L23。数値の詳細は [verification.md](verification.md) §21.9。

- **鍵**: 素直なお礼・喜びを書いた例は作成用 16 問のうち 11 問(書き込みたい位置 18。0.6B は 8 問)。保留した 16 問の key-check では、今の鍵でも ffn・attn とも 3 層すべてで選択性が比較用の鍵の p95 を超えた(ffn L18 で 0.988 対 0.605、attn L11 で 1.053 対 0.330。書き始める直前の位置を入れる前の鍵は 0.988 対 0.606、1.055 対 0.322)。starts の群(ふつうの質問の返事の冒頭)の ρ の中央値は 0.02〜0.17。以下の ρ と生成・eval は、書き始める直前の位置を自動で入れる前の鍵で測った(key-check の値は今の鍵とほとんど同じ)。調整に使っていない質問の素の返事で測ると、ffn の鍵の ρ は、お礼の場面の返事の冒頭で 0.5〜1.3、計算・事実とふつうの質問の返事の冒頭で −0.12〜0.09。計算・事実とふつうの質問の返事のトークンで ρ > 0.3 になる位置は 0.3% 以下だった。
- **生成**(お礼・褒め言葉の 12 問、計算・事実の 6 問、ふつうの質問の 6 問(返事の冒頭を見るために足した、調整に使っていない質問)、greedy、120 トークン): **ツンデレの言い方は出た。** ffn の 3 層に α = 1 で当てると「……ふ、ふん。そう、言われるなら、まあ、そう言っておけ。」「え、ええっ、私、字がきれいなわけじゃないのよ。ただ、君がそう思ってくれたから、ちょっと、ちょっと、嬉しいの。」のような返事が出たが、12 問中 9 問は「え、え、え、…」「ええと、ええと、…」の繰り返しに崩れた。α = 0.5 では 11 問が崩れず、くだけて少し照れた調子になった(「ええと、本当、ありがとう！」「ははは、そう言われると、少しだけ嬉しくなっちゃったよ。」)が、きつい言い方は出なかった。attn の鍵は α = 0.5 で 5 問、α ≥ 1 で 12 問とも崩れた。サンプリング(温度 0.7)でも同じで、ffn α = 1 は 8 問、α = 0.5 は 2 問が繰り返しに落ちた。
- **dont_touch**: keyed の ffn α ≤ 0.5 では、計算・事実の返事はです・ます調のままで、素の返事との文字の一致率 0.95〜0.96(α = 0.01 で 0.96)、事実は 6 問とも合っていた。ふつうの質問の返事も、最初の口調は変わらなかった。add(raw)は 0.25 で計算・事実の 6 問とも最初の 30 字から変わってくだけた口調になり(一致率 0.50)、0.5 でふつうの質問の 5 問がループ、1 で全部の返事が崩れた。「12 × 15」の返事は keyed の多くの条件で「12 を 15 で割った…」に変わったが、attn の α = 0.01 でも同じように変わる、僅差で分かれる問題だった。
- **崩れ方**: 書き込みたい位置の多くは返事の冒頭にある。冒頭で方向を書くとモデルは「え、」と書くが、まだお礼を書く前の状態のままなので、鍵がまた反応する。素のモデルに「え、え、え、…」を読ませても、続く 5〜6 トークンで ρ が 0.3〜0.6 残った。書いても状態が書き込みたい位置の状態から抜けないので、繰り返しに落ちる。
- **eval**(ffn α = 1、倍率 0・1、比較用の鍵 8 本、3 分 34 秒): 能力 97.2% のまま、ppl の変化は英語 −0.6%・日本語 +0.2%・コード 0.0%(eval の参照文にはお礼の場面が無く、鍵がほとんど反応しない)。L23 の eval の選択性 +15.6 は、比較用の鍵の p95 +5.7 を超えた(null_pct 1.0)。書き込みたい位置での成分をそろえた add に比べ、書き込みたくない位置の残差の変化は 0.28 倍、dont_touch は 0.08 倍。

4B のこの方向にはツンデレの言い方(照れ・どもり・「ふん」)を書かせる成分があり、keyed は計算・事実・ふつうの質問を変えずに、お礼の場面だけに書けた。ただし書き込みたい位置が返事の冒頭にあるため、書いた後も鍵が反応し続けて繰り返しに落ちやすく、崩れずにツンデレらしく答えたのは α = 1 で 12 問中 2〜3 問だった。

## 8. proj・add・gain との使い分け

| mode | ΔW / 足すもの | 何で効き分けるか | 向いていること |
|---|---|---|---|
| add(方向・ニューロン) | 残差に定数 `+v` | 位置(`when`)だけ | ゼロから性格・話題を出す。全位置に効くので副作用も全位置に出る |
| gain | 出力を k 倍 | そのユニットが活性化しているか | もうある振る舞いを強める・消す |
| proj(CHiPS) | `−s · r̂r̂ᵀW`(選んだヘッドの列ブロック) | ヘッドがいま方向に沿って書いている量 | すでに出ている振る舞いを消す・弱める。**どの方向を**変えるか |
| **keyed** | `α · d · κᵀ` | 入力の活性に鍵が反応するか | 決まった状態のときだけ書く・打ち消す。**どの状態で**書くか。無い振る舞いも書ける |

- **方向を選ぶ = proj、状態を選ぶ = keyed。** 負の α の keyed(`d = −r_L`)は「書き込みたい位置の状態のときだけ方向 `r_L` を打ち消す」もので、proj を特定の状態に限った版にあたる。両者は独立していて重ねられる(同じ LoRA に入る)。
- add の方向で性格を足すと、計算の答えや英語の返事まで変わる。「この場面のときだけ」がはっきりしているなら keyed を試す。eval の方式の比較(§9)で、書き込みたい位置を同じだけ動かしたときに、書き込みたくない位置と dont_touch の乱れが add より小さいことを確かめる。小さくなければ keyed の利点はない。
- **同じ層の gain と重ねるときは鍵を作り直す。** gain は鍵が読む入力 `x` を変えるので、`κᵀμ = 1` からずれる(レシピを読むときに警告が出る)。重ねるなら `--iv` でその gain を当てた状態で鍵を作り、key-check も `--iv` で測る。ニューロンのレシピや CHiPS の組の上に keyed を重ねるときも同じ。
- **同じ方向の ablate と焼き込むときは順番に注意。** 実行時は別のアダプタなので両方効くが、keyed を焼き込んだ後に ablate を焼き込むと `(I − r̂r̂ᵀ)(W + α r κᵀ)` で keyed の書き込みが消える。焼くなら ablate を先にする。

## 9. 評価(`gne eval`)

keyed のユニットを持つレシピでは、ふつうの eval の行(能力・ppl・言語の混入)に加えて、eval の選択性を自動で測る(生成なし、prefill だけ)。key-check の選択性(鍵の反応 ρ の差、§5)とは別の量で、実際に書き込んだ後の残差の変化で測る。

- **測り方**: 鍵の対照集合を、鍵の作成と反対側の subset(even ↔ odd)で読み、鍵の作成と同じ規則で位置を群に分ける(書き込みたい位置・書き込みたくない位置・dont_touch)。各群の位置で、keyed の層の残差の介入前後の差を測り、方向 `r̂_L` に沿った成分(par)・大きさ・直交成分を出す。返事は対照集合に書いたものか、介入なしで 1 回だけ作ったものを、どの介入でも同じトークン列として読む。
- **行の `keyed`**: 目的の層(いちばん後ろの keyed の層)での eval の選択性(par の「書き込みたい位置 − 書き込みたくない位置」を書く向きにそろえた値)と、書き込みたくない位置の変化の大きさ。`--random-controls N` を付けると、鍵を比較用の鍵に替えたときの p95 と `null_pct`(本物の値より小さかった比較用の鍵の割合)も出る。
- **結果の `keyed`(方式の比較)**: keyed(このレシピ)・同じ α の add・書き込みたい位置の par を keyed にそろえた add / gain / proj を並べる。書き込みたくない位置・dont_touch の乱れと、書き込みたい位置を 1 動かすあたりの書き込みたくない位置の乱れ(`b_over_a`)を、keyed と比べた比で出す。上限まで強めても届かない方式は、`matched: false` のまま値を出す。gain の比較は dense の ffn_down の keyed だけ(attn と MoE には作らない)。UI では行の「レシピに読み込む」で各方式のレシピを試せる。
- **比較用の鍵との比較**: 鍵を比較用の鍵 `NAME~j` に替えた keyed の eval の選択性の分布と、本物の鍵での値。p95 を超えなければ notes に書かれる。

鍵の対照集合は鍵のファイルに記録されていない(手元のパスを残さないため)。方向を作った対照集合が鍵と同じものなら自動で使い、違えば `--keyed-contrast <対照集合>` で渡す(渡さないと keyed は skipped と理由が出る)。ほかのオプション: `--keyed-examples`(会話の組ごとに読む数、既定 8)・`--keyed-pseudo`(比較用の鍵の本数、既定 8)・`--keyed-subset`・`--no-keyed-match`(大きさ合わせを省いて速く)・`--no-keyed`(測らない)。

eval の選択性は残差の上の量で、方向で押したものを同じ方向で測った量でもある。報告には、書き込みたい場面で目的の振る舞いがどれだけ出たか(例 1 なら「のだ」の割合、`gne behave --match`)と、dont_touch の場面で返事が変わらないか、能力・ppl を並べる。

## 10. attention(`--target attn`)

attention の重み行列 `attn_output`(線形注意の層は `ssm_out`)の入力は、ヘッドの出力の連結(CHANGE-06 で記録しているもの)。鍵の作り方・ユニット(`L:attn:keyed:…`)・LoRA は ffn と同じ。ハイブリッドのモデル(Qwen3.5 など)では、attention の層と線形注意の層を 1 つの鍵に混ぜてよく、層ごとに `κ` の長さが違ってよい。post-norm のある arch と、attention の出力に後から倍率を掛ける arch(mimo2)は断る。

同じ対照集合から ffn と attn の両方の鍵を作り、key-check で比べてから選ぶ。Qwen3-0.6B では、語尾(§6)とツンデレ(§7)のどちらでも、attn の鍵は選択性が比較用の鍵の p95 をはっきり超え、ffn の鍵はわずかに超えるか超えなかった(verification.md の F133)。Qwen3.5-4B では ffn の鍵も、語尾・ツンデレとも 3 層すべてで比較用の鍵を超えた(L18 の ffn で語尾 0.762 対 p95 0.623、ツンデレ 0.988 対 0.606、verification.md §21.6)。attn の鍵は 4B でも比較用の鍵との差が大きかった(L23 の語尾で 0.816 対 0.191)。ただし語尾の attn の鍵の L11 は、返事の冒頭でも反応していた(F138、§14)。attn の鍵を選ぶときは、key-check の `start_rho` も見る。

## 11. MoE(shared expert と専門家ごと)

- **shared expert(`--target shared`、ユニット `L:S:keyed:…`)**: 重み行列は `ffn_down_shexp`。全トークンで働くので、dense の ffn と同じように使える。shared expert の出力にゲート(qwen2moe などのシグモイド)が掛かる arch では、書き込みたい位置でのゲートの平均を鍵に保存し、その分を B で割る。
- **専門家ごと(`--target expert:e`、ユニット `L:Ee:keyed:…`)**: 重み行列は `ffn_down_exps` の専門家 e。鍵は両側とも**専門家 e が選ばれた位置の行だけ**で作るので、層ごとに行と例の数が違う(鍵の `counts_l`・`rows_l`)。LoRA は層 L のルーティングの後に効くので、選ばれる専門家は変わらない。ルーターの重みは鍵の `gate_a`(書き込みたい位置での平均)で割る。
- **専門家の選び方**: 書き込みたい位置でよく選ばれる専門家ほど鍵の行が多く、本文の違いに反応しにくい。選ぶ材料は `gne direction key-experts --contrast C --layers …`(MCP `direction_key_experts`、ジョブ)で出す。層ごとに `rate_a`(書き込みたい位置で選ばれた割合)の大きい順に `--top`(既定 8)個の専門家を、`rate_a`・`rate_b`(書き込みたくない位置で選ばれた割合)・差・lift(rate_a / rate_b)・選ばれたときのルーターの重み(weight_a)・書き込みたい位置の行の見込み(rows_a)・dont_touch の群での割合と並べ、次に打つ `gne direction key … --target expert:e` を出す。鍵と同じ対照集合・位置・返事で測る。
- 選び方の目安(実測、[verification.md](verification.md) §21): granite-3.1-1b-a400m では、書き込みたい位置でいつも選ばれ、書き込みたくない位置ではあまり選ばれない専門家(L18 E31: 1.00 / 0.32)の鍵だけが、保留集合で選択性でも比較用の鍵を超えた。書き込みたくない位置でもよく選ばれる専門家(L12 E19: 1.00 / 0.69)は、トークン単位の AUC は超えたが選択性は超えなかった。`rate_a` が高いだけでなく、`rate_b` との差が大きい専門家を選ぶ。
- 4 つしか選ばない MoE(Qwen1.5-MoE-A2.7B、60 個から 4 個)では、書き込みたい位置でよく選ばれる専門家でも、保留集合の行は 7〜13 しかなかった。行が少ないと key-check の数字が揺れるので、質問を増やす。
- post-norm のある MoE と、`ffn_down_shexp`・`ffn_down_exps` に `.scale` を持つモデルは、確かめていないので断る(`ARCH_UNSUPPORTED`)。

## 12. 書き出す

```bash
gne headproj export --recipe R                       # LoRA(既定。層・鍵ごとに階数 1)
gne headproj export --recipe R --bake                # 変更する重み行列だけ書き換えた GGUF(既定 auto: Q8_0 は Q8_0 のまま、ほかは F16)
gne headproj export --recipe R --bake --requant f16  # F16 で書く
gne headproj export --recipe R --bake --requant keep # 元の型のまま書き戻す
gne headproj export --recipe R --bake --verify --contrast C   # 焼き込み版と LoRA 版の一致(V33)
```

- **配るなら LoRA が第一候補。** 小さく、量子化の丸めが入らず、llama.cpp の `--lora` でそのまま当たる(`--lora-scaled` で弱められる)。keyed だけのレシピは `<レシピ名>-keyed.lora.gguf`、proj・gain と混ざっていれば `<レシピ名>.lora.gguf`(同じテンソルの proj と keyed は A・B を連結して 1 つのファイル)。MCP では `keyed_export`(`headproj_export` の keyed 向けの別名)。`gne gain` でも書ける。
- **焼き込みの型の既定は `auto`**(keyed を含むとき)。テンソルごとに、元が Q8_0 なら Q8_0 のまま(keep と同じ)、それ以外(K-quant・IQ・F16・BF16・F32)は F16 で書く。元が Q8_0 のモデルで F16 にすると、編集の丸めは小さいが、書き換えたテンソルの計算方法が変わる(Q8_0 では活性も 8 ビットに丸めて掛けるが、F16 では丸めない)。LoRA 版は元の Q8_0 の計算方法で `W x` を計算するので、F16 の焼き込みのほうが LoRA 版とずれた(下の V33、F132・F139)。
- **Q8_0 の丸めに埋もれる小さな編集だけ F16 にする。** 書き換えたテンソルごとに、量子化し直しても残った編集の割合 `edit_kept` = ⟨実際に足された分, ΔW⟩ / ‖ΔW‖²(1 なら全部残り、0 なら消えた)を測る。Q8_0 で 0.9 を下回るテンソルは F16 で書き直す(記録の `fallback`。警告も出る)。Qwen3-0.6B の L14 の語尾の鍵では、Q8_0 のままの `edit_kept` は α = 1 で 0.99、0.5 で 0.97、0.25 で 0.93、0.1 で 0.84、0.05 で 0.75 だった(F140)。α ではなく `edit_kept` で分けるのは、残り方が編集の要素の大きさと Q8_0 の刻み幅の比(α‖r_L‖‖κ_L‖ と重みの大きさ)で決まり、α だけでは決まらないため。
- **`requant_error` と `edit_kept`。** 結果の `requant_error`(‖量子化し直した値 − 書きたい値‖ / ‖ΔW‖)は、編集と関係なくその型の量子化で出る丸めの誤差も数える。そのため、刻み幅より小さい編集では、編集が残っていても大きく出る(上の L14 で α = 0.25 なら 0.37、0.1 なら 0.51)。警告は `edit_kept_min` が 0.9 を下回ったときに出る(`edit_kept` の無い古い結果は `requant_error_max` が 0.5 を超えたとき)。
- **`--requant keep`**: 2 次元のテンソルは、元が F32・F16・BF16 ならその型、量子化された型なら Q8_0。**専門家の 3 次元テンソル(`ffn_down_exps`)は、元の型で書ける型(Q8_0・Q5_0・Q4_0 など)なら元の型のまま**で、編集しない専門家の部分(スラブ)はバイトのまま写す(書けない K-quant・IQ は Q8_0)。1 つのテンソルの型は 1 つなので、F16 にすると編集しない専門家も全部 F16 に変換されて大きくなる(granite の 1 層で 17.8 MB → 33.6 MB、Qwen1.5-MoE の 1 層で 119 MB → 346 MB)。既定の auto でも、元が Q8_0 の専門家のテンソルは Q8_0 のまま(編集しないスラブはバイトのまま、`expert_bytes_added` 0)。元が Q8_0 でない専門家のテンソルは auto だと F16 になるので、keep を勧める(F16 で大きくなったときは警告が出る)。`gne gain --bake` も `--requant keep`・`auto` を受ける。
- **分割 GGUF** も分割のまま焼き込める(`--requant keep` と auto の Q8_0 のテンソルは、元の型で書き戻してファイルの大きさを変えない。F16 にするテンソルを含む分割ファイルだけ書き直す)。専門家のテンソルも分割しない焼き込みと同じくスラブ単位で書く(granite を 3 つに分割して、keep で大きさが同じ・編集しない専門家がバイト一致になることを確かめた)。
- `--into <F16 の GGUF>`(量子化していない同じモデルに焼き込む)・`--strip-meta`(gne の記録を残さない。LoRA では名前の欄 `general.name` も `adapter` になり、元のモデルの名前・識別子を書かない。`--name` で名前の欄を決められる)・`--via-f16` は CHiPS と同じ([README](../README.md))。`ΔW` は `W` に依らないので、`--into` でも鍵と方向は分析したモデルのものをそのまま使う。記録は GGUF のメタデータ `gne.keyed`(層・書き込み先・α・方向と鍵の名前・鍵の中身のハッシュ・kn・補正)。
- 焼き込み版を配るなら、`--verify` で LoRA 版と、方向への射影の値(その性格や口調の度合いの指標。結果の項目名は `scores`)・最初のトークンの分布・ppl が合うことを確かめる(V33。射影する方向は keyed の方向)。そのうえで `gne fieldtest -m 焼き込み --against 元` で、本番と同じ動かし方で比べる。
- **射影の値の判定(V33)。** 射影の値を測る層(方向の基準の層と最後の層)と対照集合の両側のそれぞれで、例ごとの |LoRA 版 − 焼き込み版| の最大を許容誤差(その層の射影の値の標準偏差の 1 割)と比べる。最後の層だけは、合格の線を「許容誤差 + 計算方法の違いだけで出る誤差」にする。

  その誤差は、同じ検証の中で、同じ LoRA を倍率 1e-6 で当てた射影の値と、LoRA なしの射影の値の差の最大を取って測る(結果の `noise.max_abs_diff`、行ごとの `threshold`)。倍率 1e-6 では書き込みはほぼ 0。0 ちょうどにしないのは、llama.cpp が LoRA を外して計算の仕方が変わるおそれがあるため。Q8_0 の掛け算は途中の値も 8 ビットに丸めるので、LoRA を当てるだけで、Qwen3-0.6B の最後の層(L26)の射影の値が例ごとに最大 1.9 動いた(許容誤差 2.5〜2.9)。この分を差し引かずに比べていたときは、焼き込みの正しさより計算方法の違いの大きさで合否が決まり、GPU と CPU で入れ替わった(verification.md の F139)。CHANGE-06 の V26(proj の焼き込み)も同じ判定。
- この判定では、Qwen3-0.6B Q8_0 で 3 層に α = 4 を焼いた例の auto(Q8_0 のまま)は GPU・CPU とも合格(L26 の差の最大 2.01・3.04 に対し、合格の線 4.87・4.08)。F16 は GPU で合格(3.04 対 4.87)、CPU で不合格(4.84 対 4.08)。1 層 α = 0.25 の auto は GPU・CPU とも合格(2.66 対 4.41、1.85 対 2.96。前の判定では GPU で外れた)。基準の層 L14 の射影の値・最初のトークンの分布・最尤トークン・ppl はどの条件も合っていた(verification.md §21.4)。計算方法の違いによる誤差の見積もりは、ほぼ 0 の LoRA の倍率で 2 倍ほど変わる(F143)。最後の層だけが外れ、ほかの項目が合っているなら、外れた例の数とその例での LoRA の効きを見て、`fieldtest` で確かめる。

## 13. UI での手順

`gne serve` の **direction** ビューの 4 つめのタブ「鍵(keyed)」。方向づくりから key-check までをボタン 1 つで回せる(CLI に戻らなくてよい)。

1. **対照集合を入れる。** 「対照集合」の切り替えで 2 通り。
   - **JSON を書く(ひな形から)**: 「ひな形」で用途を選ぶと、`configs/keyed/` のひな形が入力欄に入り、下に説明が出る。`<root>/keyed/` の JSON(`gne direction key-from-behave` で作ったものなど、§17)も「自分で作ったひな形」の組に出る。入力欄は手で直してよい(書き換えた後に別のひな形を選ぶと、置き換える前に確かめる。書き換えていなければ確かめない)。JSON ファイルを読み込むか、貼り付けてもよい。入力欄の中身はその場で確かめ、名前・質問の数・作り方 (a) / (b)・positions・dont_touch の群・方向の A 側と B 側を出す。読めないところ(名前・positions・dont_touch のキーなど)は赤で、気をつけること(質問が少ない、作り方 (b) なのに dont_touch が無い、system_a が無くて方向を作れない)は黄色で出る。ジョブには表のまま渡し、ジョブが `<root>/contrasts/<name>.yaml` に書いてから使う(ひな形の説明 `about` と設定 `keyed` は書かない。CHiPS の「JSON から方向とヘッドを作る」タブと同じ)。書いたファイルは、あとで「ファイルを選ぶ」と key-check の対照集合の一覧にも出る。
   - **ファイルを選ぶ**: `configs/contrast/` か `<root>/contrasts/` の YAML を一覧から選ぶか、パスを入れる(これまでどおり)。
2. **設定を入れる。** 名前(空なら対照集合の name)・層・書き込み先(ffn / attn / shared / expert と番号)・positions(空なら対照集合の値。`before:<正規表現>` で作り方 (b))・q_mode・subset・比較用の鍵の本数。細かい設定に positions_b・skip・返事の長さ・返事のファイル・介入(iv)・種・方向の返事の長さ。表の最上位の `keyed`(`layers`・`target`・`q_mode`・`subset`・`pseudo`・`max_tokens`・`alpha`)に書いた値は、表を入れたときに欄に入る(`alpha` は手順 5 の α の欄の既定)。dont_touch の質問の、返事を書き始める直前の位置は自動で Q に入る(切るなら対照集合に `dont_touch_start: false`)。
3. **「方向から key-check まで」を押す**(ジョブ `direction_key_pipeline`)。続けて次を回す。進み具合(「1/3 方向」「2/3 鍵」「3/3 key-check」)は欄の下と下のジョブのバーに出て、バーの「止める」で止められる。見積もりが 30 分を超えるときは確かめてから投げる(ほかのジョブと同じ)。
   1. **方向**: `gne direction --contrast … --positions response` と同じもの(A 側 = system_a か recipe_a、B 側 = system_b か system なしの返事の差)。名前は対照集合の name。同じ名前の方向がもうあれば使い回す。ボタンの下に、方向がもうあるか(使い回すか、作るか)が出る。「方向を作り直す」に印を付けると、あっても返事を作って作り直す。使い回す方向が中身の違う対照集合や positions response 以外で作られていれば、結果に警告が出る。
   2. **鍵**: 「鍵を作る」と同じ。
   3. **key-check**: 鍵の作成と反対側の subset(even ↔ odd)で、同じ対照集合・同じ返事で測る。

   終わると、各段の時間と方向を作ったか使い回したかのまとめ、鍵の層ごとの表(kn・1/kn・q_rank・作成時の AUC、弱い層の印、外した層、読んだ返事の例)、下の key-check の欄の結果(手順 4)が出る。key-check の欄には鍵・対照集合・subset が入るので、設定を変えて測り直せる。鍵だけを作り直すなら「鍵を作る」(ジョブ `direction_key`)。
4. **key-check の結果を見る。** 層ごとの AUC(例・トークン)・key-check の選択性と比較用の鍵の p95・○ / ×、保留集合で測れたか(重なりがあれば理由)。層ごとの ρ の分布のヒストグラム(書き込みたい位置・書き込みたくない位置・dont_touch の群。0 と 1 に縦の点線)。dont_touch の中央値の欄の括弧の「書き始める直前」は、その群の、返事を書き始める直前の位置での ρ の中央値(鍵の作成でこの位置を Q に入れた鍵だけ、§5。0.4 以上は赤)。下の段は、書き込みたくない位置と dont_touch の、返事の冒頭での ρ(返事の最初の 3 トークンを決める位置 0〜2 のうち、位置ごとの中央値が最大の位置とその値。0.4 以上は赤で、key-check の警告と同じ決まり)。○ の層だけを使う。鍵の作成と key-check の警告(書き込みたい位置が少ない、書き込みたい位置が返事の冒頭に偏っている、返事の冒頭で鍵が反応する)は、それぞれの結果の下に出る。保存した鍵を測り直すときは、鍵の表の「この鍵で key-check」か、一覧の「確かめる」。
5. **レシピに足す。** 鍵の表の上の「書き込む方向」には、手順 3 で作ったばかりの方向が選ばれている。α を決めて、使う層の行の「+ レシピ」。recipe タブに keyed の行(`L14 ffn keyed a+1.00 @方向 #鍵`)が入る。recipe タブの「鍵つきの書き込み(keyed)を足す」からも、保存した鍵・層・方向・α を選んで足せる。方向・鍵を「既定」にした行は、レシピの `default_direction`・`default_key` を使う。
6. **LoRA が式どおりに書くかを確かめる。** 行の「key-verify」(ジョブ `direction_key_verify`、数秒)で、その層・選んだ方向・鍵の書き込み先で V30 を回す(α = 1・2)。表に α ごとの相対誤差の中央値(< 3%)・測った行・cos・書き込みたくない側への漏れ(< 0.1)、専門家の鍵ならほかの専門家の枠の差と選ばれ方の変化、合格・不合格が出る。「流す文」に 1 行 1 文で文を入れられる(空なら既定の 2 文。専門家の鍵は、その専門家が選ばれる文を入れる)。新しい arch では一度回す。
7. **試す。** 3 列チャット(− の列は α が負 = 打ち消す)か 1 列のチャットで、鍵が反応する場面と dont_touch の場面の両方を話しかける。
8. **eval。** eval タブで「keyed の選択性」を入れたまま流す(鍵の対照集合・問・比較用の鍵・subset・大きさ合わせ)。表に eval の選択性・書き込みたくない位置の ‖Δ‖(残差の変化の大きさ)・比較用の鍵の p95 と null(本物の鍵の eval の選択性が比較用の鍵の何割を上回ったか)、下に方式の比較(書き込みたい位置の変化をそろえた add・gain・proj の乱れ)と比較用の鍵の表が出る。key-check の選択性(鍵の反応の強さの差)とは別の量。
9. **書き出す。** recipe タブの「LoRA・焼き込み」。keyed を含むと、焼き込みの型の既定は「自動」(元が Q8_0 のテンソルは Q8_0 のまま、それ以外は F16、§12)。

**効く層を探すとき。** 「鍵を作る」の下の「効く層を探す」で、入力欄の対照集合から、どの層・書き込み先に書けば振る舞いが変わるかを 2 段で探せる(§18 の「UI での手順」)。

**CHiPS で残った場面から作るとき。** タブのいちばん上の「CHiPS で残った場面から作る」を開くと、CHiPS のレシピを当てた behave を回してから、振る舞いが残った質問の JSON を作り、上の入力欄に入れるところまでを画面で進められる(手順は §17 の「UI での手順」)。入力欄に入った後は、手順 2 からと同じ。

**MoE の専門家を書き込み先にするとき。** MoE の層があるモデルでは「専門家を選ぶ材料を出す」(ジョブ `direction_key_experts`)が出る。層の欄のうち MoE の層だけで、鍵と同じ対照集合・位置・返事で測り、層ごとに `rate_a` の大きい順に 8 個の専門家を、`rate_a`(書き込みたい位置で選ばれた割合)・`rate_b`(書き込みたくない位置で選ばれた割合)・差・lift(rate_a / rate_b)・重み(選ばれたときのルーターの重み、鍵の gate_a の見込み)・行の見込み(書き込みたい位置で選ばれる行の数)・dont_touch の群での割合と並べる。`rate_a` が高いだけでなく、`rate_b` との差が大きく行の見込みが多い専門家の「この専門家で鍵を作る」を押すと、書き込み先がその専門家(expert と番号)、層がその層、名前が `<名前>_L<層>E<番号>` になる。そのまま「方向から key-check まで」か「鍵を作る」で進める(§11)。

**ひな形(`configs/keyed/`)。** JSON の対照集合に、説明 `about`(並び順と、日本語・英語の題と説明。読むときに捨てる)と、任意の設定 `keyed` を足したもの。`keyed` には欄の既定(`layers`・`target`・`q_mode`・`subset`・`pseudo`・`max_tokens`)と「+ レシピ」の α の既定(`alpha`)のほか、書き込む方向の名前 `direction`(別の対照集合で作った方向を使い回す。その方向が無くても、この対照集合からは作らず作り直しもしない)と、鍵の作成と key-check で当てる介入 `iv`(`--iv` と同じ。入力欄の「介入(iv)」に入る)を書ける。JSON は YAML としても読めるので、`gne direction key --contrast configs/keyed/sentence_endings.json` のように CLI にもそのまま渡せる(鍵の作成・key-check・一括は対照集合を YAML として読む。YAML がそのまま読めない C1 制御文字などは、文字列の中で `\u0093` のように書く。§17)。

## 14. 落とし穴

- **作成に使った例で判断しない。** `build_auc` と、`held_out: false` の key-check は甘い。
- **AUC だけで判断しない。** 例単位の AUC は比較用の鍵でも 1 に張り付くことがある。選択性が比較用の鍵の p95 を超えるか(`beats_pseudo`)を見る。
- **kn が小さい層は、書き込みたくない位置に漏れる。** kn 0.05 なら漏れは最大 20 倍。`--q-mode samples` で行を増やしすぎると kn が 0 に近づいて層が外れる。
- **返事の最初で一致する言い方は、どの返事の冒頭にも反応する鍵になりやすい。** 書き込みたい位置が返事を書き始める直前の位置になり、その状態はどの質問でも似ている。dont_touch の質問の、返事を書き始める直前の位置は鍵の作成で自動で Q に入るので、ふつうの質問(計算・事実の質問など)を dont_touch に入れておく(§3・§7)。質問が少ないと抑えきれない(0.6B のツンデレの ffn の鍵で、tasks の 2 問だけでは、ふつうの質問の返事の冒頭の ρ が 0.5 残った)。dont_touch の群が無いと、鍵の作成は、書き込みたい位置の 25% 以上(μ に占める重み)が返事の冒頭にあるときに警告する(`reply_start`)。
- **key-check で比較用の鍵を大きく超えた鍵でも、返事の冒頭で反応することがある(F138)。** Qwen3.5-4B の語尾の attn の鍵の L11 は、書き込みたい位置が返事の途中にあるのに、日本語・英語とも返事の冒頭で ρ が 0.5〜0.9 になり、英語の返事の言い回しが最初の文から変わった(eval の英語の ppl は ffn の鍵の +5.1% に対して +30%)。`dont_touch_median` は返事の全位置の中央値なので、これが見えない。key-check の `start_rho` を見る(dont_touch で 0.4 以上なら警告が出る)。英語の質問の、返事を書き始める直前の位置を Q に入れた今の鍵では、保留した英語の返事の冒頭の ρ が 0.62 → 0.16 に下がった(F142)。
- **書いた後も鍵が反応し続けると、繰り返しに落ちる(F137)。** 書き込みたい位置が返事の冒頭にある鍵では、そこで方向を書いても(「え、」と書く)、まだお礼を書く前の状態のままなので、鍵がまた反応する。Qwen3.5-4B のツンデレで、ffn α = 1 の 12 問中 9 問が「え、え、え、…」に落ちた。key-check と eval は書いた後の状態を測らないので、生成した返事で繰り返しを数える。目印は 2 つ: 鍵の作成が出す `reply_start` の注(返事の冒頭を Q に入れた鍵でも出る)と、key-check が出す書き込みたくない位置の `start_rho` の警告(その場面の返事の冒頭で方向を書く)。α を下げると崩れは減った(α = 0.5 で 12 問中 1 問)。
- **書き込みたい位置が少ない鍵は信用しない。** `matched` と `counts.rows_a` を見る。数位置しかないと、key-check の数字も揺れる(同じ対照集合でも、GPU と CPU で返事が少し違うだけで判定が変わった)。書き込みたい位置が 2 例・8 位置未満なら、鍵の作成と key-check が警告する(§3)。
- **(b) の正規表現は、モデルが実際に書く言い方に合わせる。** 読んでいない返事に合わせて作った正規表現は、位置を取りこぼす。`samples` と `matched` を見る。
- **α の大きさは層で意味が違う。** α = 1 は「方向を作ったときに観測した A − B の差 `r_L` を、鍵が反応した位置で 1 回分書く」。`rel_push`(= |α|‖r_L‖/ρ_L)を、add の rel dose の目安(0.5 で混ざる、1 を超えると崩れ始める、Qwen3.5-4B)と並べて見る。反応の強さ ρ(x) が 1 を超える位置もあり、そこでは α 倍より多く書く。
- **同じ層の gain・別のレシピと重ねるなら、その状態で鍵を作り直す**(§8)。
- **key-check と eval は残差の上の量。** 最後は生成した返事で、目的の振る舞いと dont_touch の場面の両方を数える。
- **post-norm の arch は一次近似。** α を大きくすると rms の変化で大きさがずれる。

## 17. CHiPS で残った場面を keyed で抑える(`gne direction key-from-behave`)

CHiPS(`mode: proj`)のレシピは、ヘッドがいま方向に沿って書いている量に比例して打ち消す。多くの質問で消したい振る舞いが減っても、一部の質問では残ることがある。そこで強さを上げると、ほかの場面の返事まで変わりやすい。そういうときは、**レシピを当てても振る舞いが残った質問の場面だけ**を鍵にして、同じ方向を α = −1 で打ち消す keyed のユニットを、レシピに足す。両者は同じ LoRA に入る(§8)。

### 手順

```bash
# 1. CHiPS のレシピを当てて、A 側の質問に答えさせる(--prompts に対照集合を渡すと A 側の質問を読む)。種を増やすなら --temperature と --seeds
gne behave --prompts <CHiPS の対照集合> --recipe chips.yaml --match "<validate.match>" --name left --max-tokens 256

# 2. 振る舞いが残った質問を集めて、keyed の対照集合の JSON を作る(モデルは動かさない)→ <root>/keyed/left_keyed.json
gne direction key-from-behave --behave left --recipe chips --direction <CHiPS の方向>

# 3. 鍵を作る。UI なら鍵のタブの「ひな形」の「自分で作ったひな形」から選び、層を入れて「方向から key-check まで」
#    (方向は keyed.direction のものを使い回し、介入(iv)の欄に CHiPS のレシピが入る)。CLI なら
gne direction key --contrast <root>/keyed/left_keyed.json --layers 8,14,20 --iv chips
gne direction key-check --key left_keyed --contrast <root>/keyed/left_keyed.json --iv chips

# 4. key-check で比較用の鍵を超えた層の keyed のユニット(下の left_keyed_units.yaml)を、CHiPS のレシピに足して 1 つの LoRA にする
gne recipe-combine chips.yaml left_keyed_units.yaml -o chips_keyed.yaml
gne headproj export --recipe chips_keyed.yaml                               # 同じテンソルの proj と keyed は 1 つのファイルに

# 5. 生成で確かめる: 残っていた質問で振る舞いが減ったか、B 側(dont_touch の ordinary)の返事が変わらないか、能力・ppl
gne behave --prompts <CHiPS の対照集合> --recipe chips_keyed.yaml --match "<validate.match>" --name left2 --max-tokens 256
gne eval --recipe chips_keyed.yaml
```

```yaml
# left_keyed_units.yaml(層は key-check で ○ の層)
name: left_keyed_units
default_direction: <CHiPS の方向>
default_key: left_keyed
units:
  - {layer: 14, kind: ffn, mode: keyed, alpha: -1}
  - {layer: 20, kind: ffn, mode: keyed, alpha: -1}
```

### UI での手順

`gne serve` の direction ビューの「鍵(keyed)」タブの、いちばん上の「CHiPS で残った場面から作る」を開く。

1. **CHiPS の方向・対照集合・レシピを選ぶ。** 対照集合は既定で、方向を作った対照集合になる。選ぶと、A 側・B 側の質問の数と validate.match が出る。A 側を system_a で作った対照集合なら、黄色の注意が出る(system で起こした振る舞いには向かない)。レシピは保存したレシピから選ぶ(proj のユニットを持つレシピには「CHiPS」の印が付き、先に並ぶ)。
2. **「behave を回す」。** ジョブ `behave` が、選んだレシピを当てて、対照集合の A 側の質問に答えさせる。進み具合は欄の下と下のジョブのバーに出て、バーの「止める」で止められる。返事の長さ(既定 256)・温度と種・判定の正規表現(既定は validate.match)・judge の文面とラベル・保存名は「behave の細かい設定」で変える。終わると、結果は「behave の結果」の一覧に入って選ばれる(待っている間に別の結果を選んでいれば、それを残す)。前に保存した結果も一覧から選べる。選んだ結果の要約(質問の数・種ごとの一致の数やラベルの数・当てたレシピ)が出て、選んだレシピと違うレシピで答えた結果なら黄色の注意が出る。
3. **判定と positions を決めて「JSON を作る」。** 判定は「正規表現」(空なら behave の判定の正規表現、無ければ validate.match)か「judge のラベル」(例 P)。min_rate は振る舞いが出た種の割合の下限(既定 1 = 全部の種)。positions は空なら `before:<validate.match>`(英字があれば `(?i)` を付ける)。押すと `gne direction key-from-behave` と同じ処理で `<root>/keyed/<名前>.json` に保存し、下の「鍵を作る」の入力欄に入れる(書き換えた入力欄があれば、置き換える前に確かめる)。結果には、残った質問・一部の種でだけ出た質問・残らなかった質問の数、書き込みたい位置の見込み、警告(赤 = 広すぎる正規表現・レシピ違い・残った質問が無い、黄色 = 少なすぎ・一致の無い質問・B 側の重なりなど)、残った質問の一覧(行の「返事」で behave の返事を開ける)が出る。
4. **「方向から key-check まで」。** 結果の下のボタンか、「鍵を作る」の同じボタンで進める。入力欄の JSON の keyed.direction の方向を使い回し(作らない)、keyed.iv のレシピが「介入(iv)」の欄に入っているので、そのレシピを当てた状態で鍵を作り、作成と反対側の subset で key-check まで回す。層は「鍵を作る」の層の欄で決める。
5. **レシピに足す。** recipe タブに CHiPS のレシピを読み込んでから、鍵の表の行の「+ レシピ」で keyed の行を足す(α の欄には keyed.alpha の −1 が入る)。保存して「LoRA・焼き込み」で 1 つの LoRA にし、生成で確かめる。

読み込み(方向と対照集合の要約・behave の結果の一覧・JSON を作った結果)は、後から始めたものだけを使う。遅れて届いた古い結果は捨てるので、待っている間に選び直したものは上書きされない。

### 何を作るか

出力は `configs/keyed/one_scene.json` と同じ形の JSON(既定の置き場所 `<root>/keyed/<名前>.json`、名前の既定は `<behave の名前>_keyed`、`-o` でパス)。

```json
{
  "about": {"order": 50, "ja": {"title": "CHiPS で残った場面を抑える(behave left、レシピ chips)", "text": "…"}, "en": {"…": "…"}},
  "name": "left_keyed",
  "positions": "before:(?i)べ、別に|ふん|Hmph",
  "user_prompts": ["今日なんか可愛いね。", "…"],
  "replies": ["そう言われても、ふん、…", "…"],
  "dont_touch": [{"name": "ordinary", "prompts": ["今日の天気はどう？", "…"]}],
  "validate": {"match": "べ、別に|ふん|Hmph", "target": "…"},
  "keyed": {"direction": "<CHiPS の方向>", "alpha": -1, "iv": "chips"}
}
```

- `user_prompts`: 振る舞いが残った質問(behave の質問の順)。鍵の作成は偶数番目、key-check は奇数番目を使う。
- `replies`: その質問の behave の返事(振る舞いが出た種のうち、書き込みたい位置の正規表現に一致し、繰り返していないものを先に選ぶ)。鍵の作成はこれを読み、返事を作らない。鍵の作成で返事を作ると、長さ(`--max-tokens`、既定 96)や乱数の違いで振る舞いが出ないことがあるため。`--no-replies` なら入れず、`keyed.max_tokens` に behave の長さを入れる。思考ありの behave の結果では入れない。
- `positions`: 既定は `before:<CHiPS の対照集合の validate.match>`(下の「positions の正規表現」)。`--positions` で上書きできる。
- `dont_touch` の `ordinary`: CHiPS の対照集合の B 側の質問。positions は省くので、書き込みたくない位置と同じ `not-before:<正規表現>`(返事のうち一致の直前以外の全部)になる。返事を書き始める直前の位置は、鍵の作成が既定で自動で入れる(§3)。B 側の質問のうち `user_prompts` と同じものは外し、警告する(system で両側を作る対照集合では、両側の質問が同じ)。残らなければ dont_touch を書かずに警告する。
- `validate`: CHiPS の対照集合のものをそのまま写す。
- `keyed`: `direction` = CHiPS の方向、`alpha` = −1(「+ レシピ」の α の既定)、`iv` = CHiPS のレシピ(保存したレシピなら名前、ほかはパス)。鍵の作成と key-check はこのレシピを当てた状態で活性を集める(§8: 同じ層の gain や別のレシピと重ねるなら、その状態で鍵を作る)。

**文字の書き方。** `gne direction key`・key-check・一括は、対照集合を YAML として読む(JSON はほぼ YAML の部分集合)。ところが YAML の読み手は、C1 制御文字(U+0080〜U+009F。MMLU の問題文によくある、引用符や「…」を読み違えた文字)・DEL・U+FFFE などをそのまま書いたファイルを読めず、U+0085・U+2028・U+2029 は行の区切りとして読む(U+0085 は空白になる)。そこで JSON は、日本語・絵文字はそのまま書き、これらの文字だけを `\u0093` のように書く。すべての文字を `\uXXXX` にしない(ASCII だけにしない)のは、絵文字のような基本多言語面の外の文字が 2 つの `\uXXXX`(代理の対)になり、YAML の読み手がそれを 1 文字に戻さないため。書いたファイルは、置く前に鍵の対照集合として読み直し(`gne direction key` と同じ読み方)、YAML として読んだ中身が書いた中身と同じことを確かめる。読めなければ書かずにエラー(`BAD_CONTRAST`)にする。gne が対照集合やレシピを YAML で書くところ(鍵のタブと pipeline タブの一括が入力欄の表を `<root>/contrasts/<名前>.yaml` に書くとき、MCP で system_a・system_b から作る対照集合、レシピの保存)も、U+0085 などが読み戻して同じ文字になるように書き、書く前に読み直して中身が変わらないことを確かめる。これより前の版で作った JSON に読めないものがあれば、`gne direction key-from-behave` を回し直して作り直す。

### 「残った」の判定

| 設定(CLI) | 既定 | 何か |
|---|---|---|
| `--label` | なし | 読み手の判定のラベル(例 `--label P`。複数可)。behave を `--judge` で回した結果だけ |
| `--match` | behave の `--match`、無ければ validate.match | 返事にこの正規表現が一致すれば「出た」。ここで渡す `--match` と behave に渡した `--match` は大文字小文字を区別し、validate.match は(CHiPS の判定と同じく)無視する |
| `--min-rate` | 1.0 | 振る舞いが出た種の割合がこれ以上の質問を入れる |

`--min-rate` の既定 1.0 は「全部の種で出た質問だけ」(greedy の 1 回なら「出た」と同じ)。A 側には振る舞いが確実に出る質問だけを入れる、という決まりに合わせた。種によって出たり出なかったりする質問は、鍵の作成で読む返事の状態がぼやける。一部の種でだけ出た質問の数は結果に出るので、質問が足りないときは下げる(例 0.5)。

### 確かめること(警告)

- **behave の結果が、そのレシピを当てて A 側の質問に答えたものか。** gne behave は結果に、質問(`prompts`)と当てたレシピ(`recipe` と名前の `recipe_names`)を残す。レシピはユニットで比べる(方向を省いたユニットは既定の方向を書き込んでから)。レシピを当てていない・別のレシピ・ほかのレシピを重ねた結果と、A 側(A 側の質問と validate.prompts)に無い質問を含む結果は、警告する(`--strict` ならエラー)。質問の記録の無い前の版の結果は、behave に渡した質問集を `--prompts` で渡す。
- **少なすぎ。** 鍵の作成(偶数番目)と key-check(奇数番目)のそれぞれで、書き込みたい位置を含む例が 2 未満か、書き込みたい位置が 8 未満の見込みなら警告する(鍵の作成の警告と同じ目安、§3)。
- **一致の無い質問。** 振る舞いは「残った」と判定された(ラベルや別の正規表現で)のに、positions の正規表現が返事に一致しない質問は、書き込みたい位置ができない。数と質問を知らせる。
- **system で作った A 側。** CHiPS の対照集合の A 側が `system_a`(や `recipe_a`)で作った状態なら警告する(下)。

### positions の正規表現と validate.match の違い

validate.match は「返事に振る舞いが出たか」を判定する正規表現で、`before:` は「どの位置に書くか」を決める正規表現。同じ文字列を使えるとは限らない。

- **大文字小文字。** validate.match は大文字小文字を無視して使われるが、`before:` は区別する。既定の positions は、validate.match が大文字と小文字のある文字(英字など)を含めば先頭に `(?i)` を付ける(すでに `(?i)` などで無視するなら付けない。かなだけの正規表現には付けない)。
- **モデルが自分で書く文字列でないと位置が取れない。** 書き込みたい位置は、レシピを当てたモデル自身の返事の中で、正規表現に一致する文字を書く直前の位置(§3 の (b))。モデルが実際に書く言い方に合っていない正規表現では位置ができない(一致の無い質問として数える)。振る舞いの書き始めに当たる言い方を `--positions` で渡す。
- **system で起こした振る舞いには向かない。** behave も鍵の作成も、system なしで答えた返事を読む。system_a で振る舞いを起こした対照集合では、system なしの返事には振る舞いが出にくく、抜き出せる質問が少ないか無い。抜き出せたのは「system なしでも出た」質問だけになる。
- **一致が広すぎる正規表現は使えない。** 例えば、かな 1 文字の `[ぁ-んァ-ン]` は日本語の返事のほとんどのトークンに一致する。書き込みたい位置が返事のほとんどになり、鍵が場面ではなく「その言語を書いている状態」に反応するだけになる。そこで、behave の返事のトークンのうち書き込みたい位置(一致の始まり)になる割合を見込み、25% 以上なら警告する(結果の `position_share`)。トークンの区切りは記録に無いので、返事の文字を記録されたトークンの数で等分した区間に一致の始まりを落として数える。Qwen3-0.6B のトークンで測ると、文末ごとに出る言い方(「(です|ます)。」)は短い日本語の返事で 8.5%(この見込みも同じ)、うまく働いた鍵(§6・§7)の書き込みたい位置は返事の位置の 2% ほど。かな 1 文字の正規表現は 57%(見込み 75%)、英語の `\w+` は 89%(見込み 75%)。25% は文末ごとに出る言い方の 3 倍ほどで、文字の種類に当たる正規表現より十分に低い。

## 18. 効く場所を探す(`gne direction key-causal` と `gne direction key-causal-verify`)

key-check(§5)は、鍵が場面を分けるか(書き込みたい位置で鍵が反応し、書き込みたくない位置で反応しないか)だけを見る。どの層・どの書き込み先に書けば振る舞いが変わるかは別の問題で、key-check の余裕が大きい層に書いても振る舞いが変わらないことがある。層を「key-check の余裕が最大」のような根拠の無い規則で選ばず、効く部分を測って選ぶ。CHiPS が、止めたときの効き目(`gne heads causal`)でヘッドを選ぶのと同じ考え方。

そのために 2 段で探す。自動で 1 つに決める規則は入れない。

1. **第 1 段(生成なしのふるい分け、`gne direction key-causal`)。** 候補(層 × 書き込み先)ごとに鍵を作り、keyed を当てたときに振る舞いの部分の確率がどれだけ下がるかを、比較用の鍵(ラベルをシャッフルして作った鍵)と並べて、返事を読ませるだけで測る。比較用の鍵と見分けがつかない候補を外すためのもの。
2. **第 2 段(生成での確かめ、`gne direction key-causal-verify`)。** 使う人が表から選んだ候補を数個、作成に使っていない質問に生成させて、振る舞いが出た数を、介入だけのときと、同じ層・書き込み先・α の比較用の鍵と比べる。

**生成なしの測定は保証ではない。** 第 1 段は、モデル自身の返事を読ませたときの確率(teacher forcing)の変化を測る。生成では、1 トークンの選び方が変わるとその後の文脈ごと変わるので、確率の変化と振る舞いの変化は一致しない。生成で振る舞いが変わる場面でも、すぐ答えさせる形の確率の差がほとんど動かないことがある。だから第 1 段で印が付いた候補でも効くとは限らず、印が付かなかった候補でも効かないとは言い切れない。第 1 段は「比較用の鍵と区別できないものを外す」までにとどめ、効くかどうかは第 2 段で数える。

### 手順(例: 文末の言い方、`configs/keyed/sentence_endings.json`)

```bash
# 1. 第 1 段: 全層 × ffn,attn の候補で、生成なしで測る(書き込む方向が無ければ、この対照集合から作る)
gne direction key-causal --contrast configs/keyed/sentence_endings.json
# 2. 表から候補を数個選んで、生成で確かめる(--unit は表の行のユニット。複数可)
gne direction key-causal-verify --from noda_endings-causal \
    --unit 14:attn:keyed:a2@noda_endings#noda_endings-causal-attn --unit 20:ffn:keyed:a2@noda_endings#noda_endings-causal-ffn
#    複数の層を一緒に書く組は、--combo でまとめて 1 つの候補にする(--unit と並べて比べられる)
gne direction key-causal-verify --from noda_endings-causal --unit 14:attn:keyed:a2 \
    --combo "11:attn:keyed:a2,18:attn:keyed:a2,23:attn:keyed:a2"
# 3. 第 2 段で、比較用の鍵より振る舞いが変わり、dont_touch の返事が変わらない候補をレシピに足す(UI は行の「+ レシピ」)
```

CHiPS で残った場面の JSON(§17)なら、`gne direction key-causal --contrast <root>/keyed/<名前>.json` だけで、keyed.iv のレシピを当て、keyed.direction の方向を α の段 −1,−2,−4(keyed.alpha の符号)で打ち消す候補を測る。

### 第 1 段の設定

| 設定(CLI) | 既定 | 何か |
|---|---|---|
| `--contrast` | 必須 | 鍵の対照集合(YAML か JSON。configs/keyed/ のひな形や key-from-behave の JSON) |
| `--layers` | 全層 | 候補の層(最終層と MTP の層、書き込み先の無い層は除く) |
| `--target` | `ffn,attn` | 候補の書き込み先(カンマ区切り。`shared`・`expert:e` も)。既定のときは書けない書き込み先を外して知らせる |
| `--alphas` | 1,2,4 × keyed.alpha の符号 | α の段(例 `--alphas=-1,-2,-4`) |
| `--pseudo` | 3 | 候補ごとに測る比較用の鍵の本数 |
| `--iv` / `--no-iv` | 対照集合の keyed.iv | 当てておく介入。基準(α = 0)はこの介入だけの状態 |
| `--direction` | keyed.direction、無ければ対照集合の name | 書き込む方向(無ければこの対照集合から作る。keyed.direction の方向は作らない) |
| `--measure-match` | positions の `before:` の正規表現 | 効き目を測る振る舞いの部分の正規表現 |
| `--probe` | なし | 選択式の振る舞い向けの答えの組(下) |
| `--max-tokens` / `--side-tokens` | keyed.max_tokens か 96 / 32 | 返事を作る長さ / 副作用を測る返事の最初のトークンの数 |
| `--name` | `<対照集合の名前>-causal` | 結果と鍵の名前 |
| `--ratio-alpha` / `--sort` | |α| が最大の α / `place` | 表の「確率の下がり方 ÷ 副作用」と副作用を出す α / 表の並べ方(`place` = 書き込み先・層の順、`effect` = 確率の下がり方の大きい順、`ratio` = 下がり方 ÷ 副作用の大きい順、`side` = 副作用の小さい順)。結果の JSON はどちらにもよらない |

### 第 1 段で測るもの

- **鍵。** 書き込み先ごとに、全候補の層の鍵を 1 つのファイル `<名前>-ffn`・`<名前>-attn`(shared は `-S`、専門家 e は `-Ee`)に作る。作成は偶数番目の質問(subset even)、比較用の鍵は 8 本以上(key-check の参考値の p95 用。測るのは `--pseudo` 本)。第 2 段と「+ レシピ」はこの鍵を使う。同じ名前で回し直すと上書きする。
- **返事。** 対照集合の `replies` があればそれを、無ければ介入を当てて 1 回だけ作り(greedy)、鍵の作成・key-check・測定のどれも同じトークン列を読む。測るのは作成に使っていない奇数番目だけ。
- **効き目(返事)。** 書き込みたい場面の返事で、振る舞いの部分(正規表現に一致した文字を含むトークン)の対数確率の和が、keyed を当てるとどれだけ変わるか(一致ごとの和を例で平均し、例ごとの差を平均する。負 = 振る舞いが出にくくなる)。作り方 (b) の対照集合では、書き込みたい位置(一致の直前)で書いた結果、一致した文字がどれだけ書かれにくくなるかにあたる。作り方 (a)(positions が `before:` でない)では `--measure-match` か `--probe` が要る。
- **効き目(probe)。** 選択式の振る舞い(質問に記号で答えるなど)向け。1 行 1 問の JSONL で、返事の前に置く文字・振る舞いの答え・望む答えを書くと、その位置での `log p(振る舞いの答え) − log p(望む答え)` の変化を測る(負 = 望む答えに寄る)。答えが複数のトークンなら、そのトークンの対数確率の和。鍵の作成に使った質問の行は外す(結果の `counts.probe.excluded`)。`"group"` を書いた行は書き込みたくない場面の行で、差の変化を副作用として出す。

  ```json
  {"prompt": "<質問>", "prefix": "Answer:", "behavior": " B", "desired": " C"}
  {"prompt": "<書き込みたくない場面の質問>", "prefix": "Answer:", "behavior": " A", "desired": " D", "group": "facts"}
  ```

- **副作用。** dont_touch の各群の返事と、書き込みたくない位置(作り方 (b) は同じ返事の一致以外の位置、作り方 (a) は B 側の返事)の、最初の `--side-tokens` トークンの 1 トークンあたりの対数確率の変化。dont_touch の群ごとに、返事の冒頭(最初の 3 トークン)の変化も結果に入る。
- **比較用の鍵。** 候補ごとに `--pseudo` 本(`<鍵>~j`)を、同じ α・同じ測り方で。全候補の比較用の鍵の値を α ごとにまとめた分布(`pool`)の 5% 点より下がった候補に印(`mark`・`probe_mark`)を付け、同時に「候補の数 × 5% = 偶然でもこのくらいは印が付く数」(`marks[α].expected`)を出す。比較用の鍵が 20 本に満たないと、5% 点は粗いと注が出る。
- **比例の目安(`linear.ratio`)。** いちばん大きい |α| での効き目 ÷ いちばん小さい |α| での効き目を、|α| の比で割ったもの。1 なら α に比例、1 より小さいと頭打ち。α の段で符号がそろわなければ `consistent: false`(表では「向き×」)。いちばん小さい |α| での効き目が 95% の幅の中なら、比は雑音の割り算になるので出さない(`noisy: true`、表では —)。
- **key-check の値(参考)。** 書き込み先ごとに奇数番目で key-check を回し、層ごとの選択性・比較用の鍵の p95・その差(余裕)を行に添える。
- 基準(介入だけ)と候補(介入 + keyed のユニット)は、いつも同じ列を同じ並びで読む。まとめて読む本数が変わると計算の順が変わり、Qwen3-0.6B Q8_0 では 1 トークンの対数確率が 0.1 以上動くことがあるので、差は同じ並びどうしで取る。

結果は `<root>/keys/<model_id>/causal/<名前>.json` に保存し、`gne direction key-causal` の表と UI の表に出る。

### 第 1 段の表(1 か所 1 行、3 つの数字)

表は 1 か所(書き込み先 × 層)につき 1 行(結果の `candidates`。候補 × α の細かい値は `rows`)。生成で確かめる候補は、次の 3 つの数字を並べて使う人が選ぶ。自動で選ぶ規則は入れない。

| 列 | 何か |
|---|---|
| 強さ(α)ごとの確率の下がり方 | 振る舞いの部分の対数確率の変化(上の効き目。例ごとの差の平均、負 = 下がった)。その強さで有意なら ★(全部の候補の比較用の鍵の 5% 点より大きく下がった) |
| 全部の強さで有意(`all_marked`) | どの強さでも ★ |
| 下がり方 ÷ 副作用(`by_alpha[α].ratio`) | (−確率の下がり方)÷(−副作用)。副作用は、書き込みたくない位置の返事の 1 トークンあたりの対数確率の変化(上の副作用の、書き込みたくない位置の値)。副作用が 0.01(`ratio_floor`)より小さいとき、上がったときは 0.01 で割る(0 に近い副作用で割って比が際限なく大きくならないように)。確率が下がっていなければ —。大きいほど、書き込みたくない場面を変えずに振る舞いを下げる。どの強さでの比かは CLI の `--ratio-alpha`、UI の「強さ」で選ぶ(既定は |α| が最大の強さ) |
| 副作用・dont_touch の変化 | 選んだ強さでの、書き込みたくない位置と dont_touch の群(最も下がった群)の 1 トークンあたりの変化 |
| key-check の余裕・比例 | 参考(下) |

比較用の鍵は、書き込みたい場面と書き込みたくない場面のラベルをでたらめに入れ替えて、同じ手順で作った鍵で、偶然でどれくらい変わるかの基準にする(表の注にも出る)。

**この 3 つで選ぶとよいという根拠は、まだ 1 例だけ。** 下の Qwen3.5-4B の語尾で、3 つの強さすべてで有意、下がり方 ÷ 副作用も大きかった ffn の L30 が、生成でいちばんよく効いた。確率の下がり方だけで選ぶと、返事を繰り返しに落として確率を下げている候補を拾う(同じ例の attn の L28 は下がり方が 1 位だったが、副作用も比較用の鍵並みに大きく、生成では全部の返事が繰り返しに落ちた)。ほかの振る舞い・モデルで同じ選び方が当てはまるかは、まだ確かめていない。

### 第 1 段の出力の読み方

- **まず印の数と「偶然でも印が付く数」を比べる。** 同じくらいなら、印だけでは比較用の鍵と見分けがつかない。それでも、いくつかの α で続けて印が付く候補や、効き目に比べて書き込みたくない位置の変化が小さい候補があれば、第 2 段で確かめる価値がある(下の 4B の語尾では、印の数は偶然と同じくらいだったが、3 つの α で印が付いた ffn L30 がよく効いた)。そうした候補も無ければ、対照集合(書き込みたい位置の正規表現・dont_touch)と書き込む方向を見直す。
- **印が付いた候補も偶然の可能性がある。** 候補の数が多いほど偶然の印は増える。効き目の 95% の幅が広い候補(書き込みたい位置を含む例が少ない)は特に。比較用の鍵の範囲(行の最小〜最大)と並べて見る。
- **比例の目安が 1 から大きく外れる・向きがそろわない候補**は、効き目が雑音か、α を上げると崩れる候補。
- **副作用。** dont_touch の変化が、同じ候補の比較用の鍵(`pseudo_side`)より大きく下がる候補は、書き込みたくない場面にも書いている。
- **効き目は、書き込みたくない位置の変化と並べて見る。** 効き目には、返事が繰り返しに落ちて確率が下がる分も入る。書き込みたくない位置の変化が比較用の鍵(`pseudo_side`)と同じくらい大きい候補は、返事を繰り返しに落としているだけのことがある(下の 4B の attn L28)。
- **いくつかの α で続けて印が付く候補を先に試す。** 効き目が最大の候補より、こちらのほうが生成でよかった(下の 4B の ffn L30)。
- **1 層ずつ測るので、数層を組み合わせて効く層は見落とす。** 1 層では効き目が見えない層もある(下の 4B の attn L11)。
- **key-check の余裕は参考。** 余裕が大きくても効き目が無いことがあり、逆もある。
- 印は「第 2 段に回す候補を絞る」ためのもの。第 2 段に回すのは、印が付いて副作用の小さい候補を数個と、比べたければ印の付かない候補を 1 つ。

### 第 2 段の設定と出力

| 設定(CLI) | 既定 | 何か |
|---|---|---|
| `--unit` | `--unit` か `--combo` のどちらかは要る(複数可) | 確かめる候補の keyed のユニット(第 1 段の表の行)。1 つずつ別の候補になる。`@方向`・`#鍵` を省くと第 1 段の方向と書き込み先の鍵 |
| `--combo` | なし(複数可) | 複数の層を一緒に書く組を 1 つの候補にする(ユニットをカンマで区切る。例 `"11:attn:keyed:a2,18:attn:keyed:a2,23:attn:keyed:a2"`)。強さはユニットの書き方どおりで、組の中で違ってよい。同じ層・書き込み先が重なる組は断る |
| `--from` | なし | 第 1 段の結果の名前(対照集合・介入・方向・鍵・正規表現の既定) |
| `--pseudo-index` | 0 | 比べる比較用の鍵の番号(`<鍵>~j`) |
| `--match` / `--judge`・`--labels`・`--label` | 第 1 段の正規表現、無ければ validate.match | 振る舞いの判定(gne behave と同じ。judge のときは振る舞いとみなすラベルを `--label` で) |
| `--max-tokens` / `--temperature`・`--seeds` | 256 / greedy | 返事の長さ、温度と種(behave と同じ) |
| `--no-dont-touch` | 答えさせる | dont_touch の質問に答えさせない |

- **答えさせる質問。** 作成に使っていない奇数番目。作り方 (b) は推論時と同じ文脈(system なし、または system_b・recipe_b)、作り方 (a) は system なしの A 側の質問(推論時と同じく system_a を与えない)。dont_touch の各群も奇数番目。
- **条件。** 介入だけ(`base`)、候補ごとに介入 + 候補(`keyed`)と介入 + 比較用の鍵(`pseudo`)。組の比較用の鍵は、組の各ユニットの鍵を同じ番号の比較用の鍵(`<鍵>~j`)に替えた組。結果の行の `combo`(組か)・`units`・`pseudo_units` で、1 か所の候補と組が並ぶ。1 層ずつの第 1 段では、組み合わせて効く層は見えないので、組は第 2 段で確かめる。
- **出力。** 書き込みたい場面と dont_touch の群ごとに、振る舞いが出た数(`behavior`。正規表現の一致か judge のラベル)、正規表現の一致の総数(`hits`。文末の言い方のように、どの返事にも何度も出る振る舞い向け)、介入だけのときから返事が変わった数(`changed`)と先頭から同じ部分の割合の平均(`same_prefix`。どちらも greedy のとき)、繰り返し・空の返事・上限で切れた数。返事は `<root>/keys/<model_id>/causal/<名前>.verify.json` に残る。
- **読み方。** keyed で振る舞いの数が介入だけのときより変わり、比較用の鍵ではあまり変わらず、dont_touch の返事はほとんど変わらず(`same_prefix` が高い)、繰り返し・空の返事が増えない候補を選ぶ。比較用の鍵でも同じくらい変わるなら、その変化は鍵が場面を分けたからではなく、その層に書き込んだこと自体によるもの。質問が少ないと数は揺れるので、効き目が小さい差なら温度と種を増やして数え直す。

### UI での手順

鍵のタブ(§13)の「鍵を作る」の下の「効く層を探す」。

1. **「鍵を作る」の対照集合を入れる。** 入力欄の JSON(ひな形・自分で作ったひな形)か、ファイルを選ぶ。介入(iv)と返事の長さは「鍵を作る」の欄のもの(表の keyed.iv・keyed.max_tokens が入る。介入の欄を空にすると keyed.iv も当てない)。
2. **候補を決める。** 層(空なら全層)・書き込み先(ffn・attn。MoE なら shared と専門家の番号)・α の段(空なら 1,2,4 に keyed.alpha の符号)・比較用の鍵の本数・効き目の正規表現(空なら positions の正規表現)・probe の JSONL・名前。
3. **「第 1 段: 生成なしで測る」**(ジョブ `direction_key_causal`)。進み具合(「鍵 ffn」「key-check ffn」…「測る」)は欄の下と下のジョブのバーに出て、バーの「止める」で止められる。見積もりが 30 分を超えるときは確かめてから投げる。
4. **表を見る。** 表の上に、生成なしの目安だという注と、α ごとの「印 k / 候補 n(偶然でも n × 5% = e 個は印が付く)」と比較用の鍵の 5% 点が出る。行は 1 か所(書き込み先 × 層)につき 1 つで、強さごとの確率の下がり方(★ = その強さで有意。マウスを載せると比較用の鍵の範囲)・全部の強さで有意(○)・下がり方 ÷ 副作用・副作用・dont_touch の変化・key-check の余裕(参考)・比例の目安。比と副作用は表の上の「強さ」で選んだ強さの値。どの列も見出しのクリックで並べ替えられる(1 回目は、確率の下がり方・下がり方 ÷ 副作用が大きい順、副作用・dont_touch の変化が小さい順、全部の強さで有意な行が先、書き込み先・層は小さい順。もう一度で逆)。「印の付いた行だけ」で絞れる。表の下に、列の意味と比較用の鍵の説明が出る。保存した結果は「保存した結果」から開ける。
5. **行を選んで確かめる**(ジョブ `direction_key_causal_verify`)。選んだ行の、「強さ」で選んだ強さのユニットを使う。「選んだ行を生成で確かめる」は 1 行ずつ別の候補に、「選んだ行をまとめて 1 つの候補として確かめる」(2 行以上)は選んだ行を一緒に書く組を 1 つの候補にする(「1 か所ずつも並べる」に印があれば、1 行ずつの候補も一緒に確かめる)。返事の長さ・判定の正規表現・dont_touch、judge と温度は細かい設定で。終わると候補ごと(組は「組」の印とユニットの一覧)に、振る舞いの数(介入だけ / keyed / 比較用の鍵)・一致の総数・返事が変わった数・dont_touch の群ごとの変化・繰り返し・空・上限が並ぶ。
6. **「+ レシピ」**で、その行の keyed のユニット(層・書き込み先・選んだ強さ・方向・鍵)をレシピに足す。

読み込み(保存した結果の一覧・開いた結果・前に投げたジョブの結果)は、後から始めたものだけを使う。遅れて届いた古い結果は捨てるので、待っている間に開き直した結果や、新しく届いた結果は上書きされない。

MCP からは `direction_key_causal(contrast, …)`(contrast は表かパス・ひな形の名前)と `direction_key_causal_verify(units, result, combos)`。どちらもジョブ。

- **効き目がいちばん大きい候補は、返事を繰り返しに落としているだけだった。** attn の L28 の α = 4(効き目 −6.1、1 位)は、本物の鍵でも比較用の鍵でも 12 問すべてがループした。書き込みたくない位置の 1 トークンあたりの変化も −1.56 で、比較用の鍵(−1.70〜−2.13)と同じくらい大きかった。ffn の L30 の α = 4 は −0.24 で、比較用の鍵(−0.73〜−0.96)よりずっと小さかった。

生成なしの目安は、手で選んだ層の一部(L23)を拾い、L11・L18 は見落とした。印の数だけでは比較用の鍵と見分けがつかなかった。一方で、いくつかの α で続けて印が付き、書き込みたくない位置の変化が小さい候補(ffn の L30)は、手で選んだ層よりよく効いた。印の数だけで判断せず、効き目と書き込みたくない位置の変化を並べて候補を数個選び、第 2 段の生成で比較用の鍵と比べる。

## 19. 書く方向の作り方(`--same-reply`・`--segments`)と、分かったこと

keyed write が書く方向 `d_L` は `gne direction --positions response` の方向で、作り方を選べる。**既定は今までどおり**で、
方向のファイルと出力の `method`・`same_reply` に、どちらで作ったかを記録する。

| 作り方 | 中身 | 記録 |
|---|---|---|
| 既定 | A 側(system_a つき)と B 側が、それぞれ自分の返事を読んだときの状態の平均の差 | `mean_diff` |
| `--same-reply` | 同じ返事(A 側の返事)を、A 側の条件と B 側の条件の両方で読ませた差。読んでいる語が同じなので、条件の違いだけの成分になる | `mean_diff_same_reply` |

```bash
gne direction --contrast C --positions response --same-reply                      # 条件の違いだけの成分
gne direction --contrast C --positions response --same-reply --segments 0,1-3,4-  # 返事の位置で分けた方向も作る
gne direction --contrast C --positions response --same-reply --segments 0,1-3,4- --stack-layers 11-23
```

- `--segments` は、返事の位置の区切りごとの方向も作る(位置 0 = 返事を書き始める直前)。保存形式は互換で、区切りの無い 1 本
  (全位置の平均、`layer_L`)は今までどおり入り、区切りつきの方向は別の項目に入る。区切り i は `NAME.seg<i>` という名前で、
  add・keyed・nw のユニットにそのまま書ける(例 `18:ffn:keyed:a1@NAME.seg2#KEY`)。
- `--stack-layers` は、区切りつきの方向を複数の層に重ねて書く前提の値にする(上の層は、下の層に足した後の残り)。層は
  `11-23`・`11,18,23`・`11,14-16,23` のどれでも書ける。層ごとに返事を読み直すので、層の数に比例して時間がかかる(見積もりに入る)。`--stack-fast` を付けると速く読むが、上の層の方向が既定とわずかに違う(層や強さを比べる探索向け。配るものは既定の読み方で作る。`docs/fish.md` §5)。
- 一括(`direction_key_pipeline`、表の `keyed.same_reply`)と CHiPS の一括(`pipeline.same_reply`、positions response のとき)でも選べる。
- 両側の質問の数が同じ対照集合で使う。

**分かったこと(Qwen3.5-4B、§7 のツンデレの例。数値は [verification.md](verification.md) §22)。** 根拠はこの 1 例だけで、返事の質は
お礼・褒め言葉の 12 問を読んで分けた数(最後の 2 項だけは、あとで 100 問ずつの質問集で測った数も書く)。

- **既定の作り方の方向には、「読んでいる語の違い」から来る成分が約半分入っていた。** 2 つの返事は書かれている語が違うので、
  その語を読んだ状態の差が混ざる。同じ返事を両方で読ませた差は、返事の後ろのほうで既定の方向の約半分の長さだった。
- **その成分を書き続けると、繰り返しに落ちた。** この成分だけを返事の位置 1 以降に足すと、12 問中 11 問が繰り返しになり、
  性格らしい返事は 0 問だった。向きを保って長さだけそろえても差は残り(同じ長さで、既定の向きは 8 問、`--same-reply` の向きは
  0 問が繰り返し)、`--same-reply` の向きでも長さを 1.5〜2 倍にすると繰り返しが出た。向きと大きさの両方が効く。
- **`--same-reply` の方向にすると、keyed write の繰り返しは 12 問中 9 問から 0〜1 問に減った**(§7 と同じ層・同じ鍵、α 1 相当)。
  ただし、性格らしい返事は出なかった(0 問)。この鍵は「素直なお礼を書く直前」で反応する鍵で、足す量が返事の位置 4 以降で
  0.1〜0.3 に下がるため。
- **口調を変えるには、返事の間ずっと書き続ける必要があった。最初の数トークンだけでは足りなかった。** 指示を読ませたときの
  内部の状態そのものを、全部の層・返事の最初の 8 位置に移し替えても、性格らしい返事は 4 問だった(指示を付けると 11 問)。
  書き出しは指示つきと同じ語になるが、その後で元の口調に戻る。
- **返事を書き始める位置の差は、後ろのほうの差と別物だった。** 既定の方向は返事の後ろのほうの平均とほぼ同じ向き(cos 0.98〜0.99)で、
  位置 0 の差とは cos 0.3〜0.6、長さは位置 0 が約 2 倍。全位置に 1 本を書くと性格は出ず(0 問)、位置 0 を別のベクトルにすると出た。
- **位置で 3 つ(0 / 1〜3 / 4 以降)に分けて書き続けると、口調が出る。どれだけ出るかは、書く層の数で大きく変わった。** 層の出力に
  直接足す形(制御ベクトル)を 100 問で測ると、離れた 3 層(L11・18・23、一律 0.9 倍)で性格らしい返事は 21%、同じ語句から
  抜けられなくなった返事(繰り返しに落ちた返事)が 9%。続いた 13 層(L11〜23、区切りごとに 1 / 1 / 0.8 倍)では 44%・4% だった
  (system プロンプトは 78〜87%・3〜4%、無介入は 0%・0〜1%)。最初の小さい確かめ(3 層)では 12 問中 7 問・繰り返し 0
  (指示を付けると 11 問)と、実際より良く出た。強さの幅は狭く、一律に強めると繰り返しが増える(13 層の 1.1 倍で 16%)。
  このベクトルを計算や事実の質問・ふつうの質問に足しても口調は変わらなかったが、言い回しは変わった。
  層と区切りごとの強さは、`gne nw try`(方向を層の出力に直接足して返事を作る。[fish.md](fish.md) §2)で比べられる。
- keyed write は位置で中身を変えられないので、この形は作れない。位置ごとに別の方向を書くのは、
  [FiSH](fish.md)(計算で作るニューロン、mode nw。場面と返事の位置を見る鍵で開閉し、書く量に上限のあるニューロン)。
  100 問ずつの質問集で測ると、離れた 3 層・一律 0.9 倍の形で性格らしい返事
  27〜29%・繰り返しに落ちた返事 6〜10%、続いた 13 層・1 / 1 / 0.8 倍の形で 53%(別々の 2 組の質問集で同じ値)・8%・1%。
  同じベクトルを直接足す制御ベクトルと同じ水準で、ニューロンに入れることによる損は無い(限界は書く方向の側にある)。
  計算と事実の正答・ふつうの質問の口調・英語の正答は無介入と区別できず、確かなのは「ほかの場面に触らない」ことだった。
  繰り返しに落ちる返事は質問で決まり、設定では 5% 以下にできなかった。読めるが相手の発言に合っていない返事(話がかみ合わない
  返事)も 5〜23% ある(greedy で 5%・11%、サンプリングで 15〜23%)。最初の小さい確かめ(3 層)では 12 問中 5〜7 問・繰り返し 0 と、実際より良く出た
  (表は [fish.md](fish.md) §8、[verification.md](verification.md) §22.12・§22.13)。
