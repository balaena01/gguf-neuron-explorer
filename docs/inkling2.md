# Inkling 2(inkling2_loop)で gne を使う

**gne は Inkling 2 で、読み込み・情報(`gne info`)・マップ・会話に加えて、中を読む処理(`gne inkling …`)、CHiPS の流れ(方向 → 部品の順位づけ → 組 → レシピ)と残りから追加、LoRA の書き出し、元の大きさのままの焼き込み(同じモデルの別の量子化への焼き込みも)、評価を扱う。** FiSH・キー・lens などほかの方向を使う機能と、残差・ヘッドの統計の一部は、このモデルの構造に合わせた計算がまだ無いので、理由を書いて止まる(下の「使える機能と止まる機能」)。間違った値を出さないための扱い。確かめたのはおもに UD-IQ2_XXS と公開のひな形。

Inkling-2-Mini(Thinking Machines Lab、Apache 2.0)は、保存されている 24 層のうち 6〜17 を 3 回続けて実行する MoE の言語モデル。答えの前に思考(reasoning)を書く。

## 環境

公式の llama.cpp(ggml-org)は、2026-11-20 のコミット `29b52d3`(PR #32694)からこのモデル(arch `inkling2_loop`)を読める。その版は 2 回目・3 回目の段で専門家ごとの倍率(下の「構造」)を掛けずに計算していた。直す PR #32704(`model : inkling2_loop re-share the loop slots after the scale pass`)は 2026-11-21 に取り込まれた(マージのコミット `690b87d8`)ので、それ以降の llama.cpp をビルドする。ふだんの gne の環境(pip で入れた llama-cpp-python 0.3.36 の中の llama.cpp)は古くて読めないので、このビルドを読む llama-cpp-python を入れた専用の仮想環境を作る。

確かめた環境は Linux(WSL2)、CUDA 12.4、Python 3.12、RTX 3080 12 GB。GGUF は unsloth/Inkling-2-Mini-GGUF の、arch が `inkling2_loop` のもの(確かめたのは UD-IQ2_XXS、8.5 GB)。12 GB の GPU に載るのは 8〜9 GB の量子化まで。

### 1. llama.cpp をビルドする

gne を確かめたのは、`29b52d3` に PR #32704 のコミットを 1 つ当てたもの(取り込まれたものと同じ変更)。中を読む名前の patch(third_party/inkling2/0001)は、2026-11-22 の master(`44d50873`)にも `git apply --check` で当たる(数行のずれだけ。その master でのビルドと動作は確かめていない)。

```bash
git clone https://github.com/ggml-org/llama.cpp llama.cpp-inkling2
cd llama.cpp-inkling2                                               # 690b87d8(PR #32704 の取り込み)以降
git apply <gne>/third_party/inkling2/0001-inkling2-graph-names-for-gne.patch   # 中を読む処理・CHiPS の流れに要る(会話だけなら不要)
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON -DBUILD_SHARED_LIBS=ON -DLLAMA_USE_PREBUILT_UI=OFF -DLLAMA_OPENSSL=OFF
cmake --build build -j 8 --target llama ggml mtmd llama-completion llama-server
```

### 2. 専用の仮想環境と llama-cpp-python 0.3.36

[docs/sensenova_loop.md](sensenova_loop.md) の「2. 専用の仮想環境を作る」「3. llama-cpp-python 0.3.36 を直して置く」と同じ手順で、直しは `third_party/sensenova-loop/official/llama-cpp-python-0.3.36-llama-cpp-1.0.patch` をそのまま使う(この llama.cpp の `include/llama.h` は、直しが合わせた llama.cpp 1.0 の改造版と構造体が同じ。増えた関数 2 つ `llama_model_meta_arr_n`・`llama_model_meta_arr_str` は gne が使わない)。

`llama_cpp/lib/` のリンクは、必ずこの llama.cpp の `build/bin` を指す。llama-cpp-python の `_ggml.py` は、`LLAMA_CPP_LIB_PATH` ではなく `llama_cpp/lib/` から libggml を読むので、別の llama.cpp を指したままだと libggml が 2 つ読み込まれる。

```bash
export LLAMA_CPP_LIB_PATH=<llama.cpp>/build/bin LD_LIBRARY_PATH=<llama.cpp>/build/bin
<venv>/bin/gne info -m Inkling-2-Mini-UD-IQ2_XXS.gguf
```

## 構造

| 部分 | 中身 |
|---|---|
| 層 | 保存されている層 24(GGUF の `block_count`)。層 6〜17 を 3 回続けて実行するので、1 回の計算で 48 段。llama.cpp の `llama_model_n_layer` は 48 を返す |
| 繰り返し | 2 回目・3 回目は層 5 の出力からやり直す。前の回の流れ(下の流れ 1・2)を、学習された問いで混ぜた「メッセージ」にして、Q・K・V・MLP の入力に低ランク(ランク 64)のゲートで混ぜる: 入力 ← (1 − forget)·入力 + gain·メッセージ(gain・forget は入力とメッセージから計算する tanh) |
| 残差 | 1 本ではない。層 0・6・12・18 で新しい流れが始まり、それまでの流れは取っておかれる。各副層(attention・MLP)の入力は、それまでの流れと今の流れを RMS 正規化して、層ごとの学習された問い(`attn_res_query`・`ffn_res_query`)で重みづけして足したもの(深さ方向の注意)。最後の出力も同じ形で混ぜる(`output_res_query`) |
| attention | ヘッド 24(KV ヘッド 8)、幅 128。RoPE は無く、相対位置のバイアスを使う。窓つき(sliding window、1,024 トークン)の層が 20、全体を見る層が 4(層 5・11・17・23)。全体を見る層は Q・K・V の入力の正規化が別々 |
| 短い畳み込み | K・V・attention の出力・MLP の出力が、4 タップの畳み込み(チャンネルごと、時間方向)を通る。attention と MLP の出力は、畳み込みを通ってから流れに足される |
| MLP | 全層 MoE。専門家 128、1 トークンで 8 個、幅 1,152。ゲートとアップは 1 つのテンソル(`ffn_gate_up_exps`)。sigmoid で選び、選んだ重みを正規化して 8 倍する。活性化は SiTU |
| 専門家の重み | 量子化の型が層で違う(IQ2_XXS の GGUF では、ゲートとアップが IQ1_S・IQ2_XXS・IQ2_XS・IQ2_S、ダウンが Q2_0・NVFP4)。20 層に専門家ごとの倍率(`ffn_*_exps.scale`)があり、llama.cpp は専門家の行列の出力にそれを掛ける |
| 出力 | 最後のロジットに soft cap 30 |

## 段の番号

gne の表示の「段」は、実行の順(0〜47)。llama.cpp のキャッシュの番号(グラフのテンソルの名前の `-N`)は実行の順と違う:

| 段 | 層 | 回 | llama.cpp の番号 | 流れ |
|---|---|---|---|---|
| 0〜5 | 0〜5 | — | 0〜5 | 0 |
| 6〜17 | 6〜17 | 1 回目 | 6〜17 | 1(層 6〜11)、2(層 12〜17) |
| 18〜29 | 6〜17 | 2 回目 | 24〜35 | 1、2 |
| 30〜41 | 6〜17 | 3 回目 | 36〜47 | 1、2 |
| 42〜47 | 18〜23 | — | 18〜23 | 3 |

`gne info` にこの表が出る(`--json` では `meta.inkling.steps` に段ごと)。マップの層は保存されている 24 層で、各層の札に窓つきか全体を見る attention か、繰り返しの層なら何回・どの段で実行するかが出る。

## 会話

- `gne chat -p …`(レシピなし)は、無介入の 1 列で話す(ほかのモデルの `gne chat` は −/0/+ の 3 列で、レシピが要る)。
- `gne serve` では、地図の凡例の「会話する」で、無介入の 1 列のチャットが開く(くわしく見るの欄に、いまの層のニューロン 0 のチャットとして開く。介入の欄は出ない。応答の長さの既定は 1,024)。
- このモデルはいつも答えの前に思考(reasoning)を書く(`<|content_thinking|>` … の後に `<|content_text|>` 回答。`reasoning_effort` は system の 1 行を変えるだけで、none でも思考は書く)。
- 画面のチャット(3 列・1 列・レシピの「会話する」)は、思考を返事ごとに折りたたんで出す(見出しに思考のトークン数。押すと開く)。見えるのは回答。道具の欄の「思考を表示」で全部の返事の思考を開く(既定は閉じる。このブラウザに覚える)。読み上げは回答だけ。
- `gne chat` は、思考を `<think>` … `</think>` で囲んで出す(既定)。`--hide-reasoning` で思考は出さず、「(思考中… N トークン)」と回答だけを出す。`--json` の返事には `answer`(回答だけ)と `reasoning_tokens` も入る。会話の履歴には回答だけを入れる(前の思考は次のプロンプトに入れない)。
- `gne behave`・`gne eval` の一致・空の数・採点は回答だけで数える(思考は数えない。behave の `tokens` は思考を含む返事全体の長さで、思考の長さは `reasoning_tokens` に別に出す)。
- `gne serve --openai` の `/v1/chat/completions` は、思考を `reasoning_content`、回答を `content` に分けて返す(流すときも、`delta` の `reasoning_content` と `content` に分かれる)。
- llama.cpp(このモデルに対応したビルド)で動かすとき: `llama-server` は既定(jinja が有効)で思考を `reasoning_content`、回答を `content` に分ける(流すときも)。`--reasoning-format none` にすると、思考は `<|content_thinking|>…<|end_message|>` の印ごと `content` に入る。`--no-jinja` ではチャットの要求が「this custom template is not supported」で失敗する。`llama-cli` は思考を `[Start thinking]` と `[End thinking]` の間に出し、その後に回答を出す。焼き込んだ GGUF は、gne の記録を入れても入れなくても(`--strip-meta`)チャットテンプレートを元のまま写すので、同じように動く
- チャットテンプレートは、`reasoning_effort`(既定 0.9)を「Thinking effort level」として最初の system の欄に入れる。
- 思考の量: `gne chat --reasoning-effort low` のように渡す。テンプレートが受け付けるのは none(0)・minimal(0.1)・low(0.2)・medium(0.7)・high(0.9)・xhigh(0.99)・max(0.99)か、0〜0.99 の数。省くとテンプレートの既定(0.9)。UI のチャットの「思考の量」、OpenAI 互換 API の `reasoning_effort` も同じ。
- モデルの勧めるサンプリングは温度 1.0・top-p 1・top-k 0・min-p 0(`--temperature 1 --top-p 1 --top-k 0 --min-p 0 --presence-penalty 0`)。
- 答えの前に思考を書くので、`--max-tokens` は長めに取る(公開のひな形の質問で、思考と回答を合わせて平均 440 トークン前後)。

速さとメモリ(UD-IQ2_XXS、RTX 3080、`gne bench`): 生成 1 本 約 51 tok/s、4 本まとめて 約 116 tok/s。GPU のメモリは文脈 4,096 で約 9.8 GB(画面の分を除く)。

## 使える機能と止まる機能

| 使える | 止まる(理由を書いて止める) |
|---|---|
| `gne info`、`gne probe --list-names`(グラフのテンソルの名前だけ。番号は段)、`gne inkling read / check / mix / residuals / conv / experts`(中を読むだけ。0001 が要る。下の「中を読む」)、`gne chat`(`--reasoning-effort`。CHiPS のレシピも当てられる)、`gne serve` のマップ・会話・保存済みの一覧・CHiPS の画面、OpenAI 互換 API、`gne behave`(`--match`。思考の欄を除いた回答だけを数える。CHiPS のレシピも当てられる)、CHiPS の流れ(`gne heads pipeline`・`gne heads refine` → レシピ → `gne headproj export`。下の「CHiPS の流れ」)、`gne recipe-scale`、`gne eval`(返事は思考の後の回答で測る。下の「評価」)、`gne verify`(トークン化の V8 だけ。ほかは省く) | CHiPS の流れのほかの、中間のテンソルの捕捉(残差・ヘッド・ニューロン・専門家の値)、control vector、CHiPS の射影のほかの LoRA(gain・keyed・nw など)、重みの中身を読む処理(ニューロン・専門家・ヘッドの詳細、logit lens など)。これを使うコマンド(`gne stats`・`lens`・`sweep`・`direction`・`heads candidates` などの `heads …`・`experts …`・`nw …`・`steer`・`gain`・`ablate`・`bake` など)は止まる。`gne behave --judge`(読み手の判定)と `gne fieldtest` も止まる |

止まるときのエラーは `ARCH_UNSUPPORTED`。CLI では、使えるコマンド(`info`・`probe`・`verify`・`bench`・`chat`・`behave`・`worker`・`recipe-combine`・`recipe-scale`・`direction keys`・`heads pipeline`・`heads refine`・`headproj export`・`inkling …`)のほかは、モデルを読み込む前に止まる。画面と MCP のジョブは、CHiPS の流れ(`head_pipeline`・`heads_refine`・`headproj_export`)と `behave` のほかは、始める前に止まる。中間のテンソルの捕捉を通すのは `gne inkling …` の読むだけの処理だけ。

## 中を読む(読むだけ)

中の値を読むには、llama.cpp に `third_party/inkling2/0001-inkling2-graph-names-for-gne.patch` を当てる(名前を付けるだけで計算は変えない。当てる前と後で、公開のひな形の 4 問の最後の位置のロジットと貪欲に生成した 24 トークンが、CPU でも GPU でもビットまで一致した)。当て方は [third_party/inkling2/](../third_party/inkling2/README.md)。当てていない llama.cpp では、`gne inkling …` は理由と直し方を書いて止まる。

名前の番号は、gne が実行順の段に読み替える(`l_out-18` は段 18 = 層 6 の 2 回目)。`gne probe --list-names` もこの番号で出す。流れが始まる段(0・6・12・18・24・30・36・42)では、attention の出力が新しい流れの始まりになり、グラフでは `attn_out` の名前が `ffn_inp` に上書きされている(同じテンソル)。gne は `attn_out-<段>` を頼まれたら `ffn_inp-<段>` から返す。

| 名前 | 中身 |
|---|---|
| `l_out` | 今の流れの、その段までの和(流れの部分和) |
| `ffn_inp` | attention を足した後の今の流れ |
| `attn_out`・`ffn_out` | attention・MLP の書き込み(短い畳み込みの後。流れに足すもの) |
| `attn_wo`・`ffn_moe_out` | 同じ書き込みの、短い畳み込みの前 |
| `attn_mix`・`ffn_mix` | 副層が実際に読む入力: それまでの流れと今の状態を RMS 正規化し、深さ方向の注意の重みで足したもの。全体を見る層の `attn_mix` は Q・K・V の 3 行 |
| `attn_mix_w`・`ffn_mix_w`・`out_mix_w` | 深さ方向の注意の重み(並びは、取っておいた流れの新しい順、最後が今の状態) |
| `loop_msg`・`loop_msg_w` | 2 回目・3 回目: 前の回の流れから混ぜたメッセージ(Q・K・V・MLP の 4 行)とその重み |
| `loop_gain_{q,k,v,ffn}`・`loop_forget_{q,k,v,ffn}` | 2 回目・3 回目: ゲートの値。入力 ← (1 − forget)·入力 + gain·メッセージ |
| `attn_in_{q,k,v}`・`ffn_in` | 2 回目・3 回目: ゲートの後の入力(正規化の前) |
| `kqv_out`・`attn_gated` | ヘッドの出力(ゲートの前・後。`attn_gated` が W_o の入力) |
| `ffn_moe_argsort`・`ffn_moe_weights_scaled`・`ffn_moe_situ` | 専門家の選び方(大きい順の並びの先頭 8 個が選んだ専門家)・選んだ重み・専門家のニューロンの活性 |

| コマンド | 中身 |
|---|---|
| `gne inkling read --text … --names … --steps … --out x.npz` | 段ごとの値を .npz に書く |
| `gne inkling check` | 捕まえた値を別の計算と突き合わせる: 流れの和、混ぜ方(状態と重みから)、繰り返しのゲート、W_o の積、短い畳み込み、専門家の和(倍率 × W_down × 活性)、ゲート・アップと SiTU |
| `gne inkling mix --spec …` | 各段の深さ方向の注意の重み(どの流れをどれだけ読むか) |
| `gne inkling residuals --spec …` | 残差の定義(流れの部分和と、副層が読む混ぜた入力)ごとの A − B の方向の比べ、回どうしの向き、3 回目の方向に沿った各回のヘッド・副層の書き込み、深さ方向の注意の重みの A 側と B 側の違い、繰り返しのメッセージの強さ |
| `gne inkling conv --spec …` | 書き込みから方向を除いたとき、短い畳み込みの後に残る方向の成分 |
| `gne inkling experts --spec …` | 段ごとの専門家の選ばれ方と、同じ層の回どうしの重なり |

結果は `<root>/inkling/<model_id>/` に書く。方向も保存するが、方向で押す・射影する機能(CHiPS・FiSH・キー・lens など)は、残差をどちらの定義で読むか決まるまで止めたまま。`gne stats resid`・`gne stats act`・`gne heads attention` も、それぞれ決めることが残っているので理由を書いて止まる。

`gne inkling check` の結果(UD-IQ2_XXS、GPU、24 トークン、全 48 段): 流れの和・混ぜ方・ゲート・短い畳み込み・SiTU は相対誤差 3×10⁻⁸〜2×10⁻⁷(float32 の丸め)。W_o・専門家の行列の積は 5×10⁻³〜1×10⁻²(llama.cpp は量子化した重みとの積で活性も量子化する。gne の計算は重みを戻して float64 で掛ける)。

## CHiPS の流れ(`gne heads pipeline`)

ほかのモデルと同じ流れ(方向 → 全部の部品の書き込みの順位づけ → 上位を 1 個ずつ s=1 で確かめる → s=1 から組を作る → 応答での確かめ → レシピ)を、このモデルの形に合わせて流す。ひな形の JSON はほかのモデルと同じ形(`user_prompts` か `prompts_a` / `prompts_b`、`system_a` / `system_b`、複数ターンの会話、`validate`)。名前の patch(third_party/inkling2/0001)を当てた llama.cpp が要る。

- 方向: MLP が読む混ぜた入力の、A 側の平均 − B 側の平均を段ごとに(48 行。層 6〜17 の 2・3 回目は繰り返しのゲートの後)。最後に混ぜた出力の A − B も持つ(番号 48)。部品の射影の基準は、その層の最後の回(層 6〜17 は 3 回目)の段の方向
- 部品: ヘッド・attention 全体・MLP 全体・専門家のニューロン(`--unit-kinds` の既定はこのモデルだけ `all,layers`)。流れが始まる層(0・6・12・18)の attention は候補に入れない。層 0〜5 は既定で入れない(`--include-before` で入れる)。層 6〜17 の重みは 3 回の繰り返しで共有なので、その層の部品は 3 回すべてに効く(画面では部品の名前に ×3)
- 射影: 短い畳み込みの今のトークンの倍率で直した向き normalize(g ⊙ r) を引く。専門家のニューロンは `ffn_down_exps` の専門家ごとの列で、専門家ごとの倍率を差分に入れる
- 測る点: 各区分の最後の段(5・17・29・41・47)と最後に混ぜた出力。組は最後に混ぜた出力で A 側の値を目標(既定は A と B の平均の真ん中)まで下げるように作る
- 応答での確かめは思考の欄を除いた答えで数える(長さの既定はこのモデルだけ 1024 トークン)
- レシピの書き方はほかのモデルと同じ(`L:Hh:sS@方向`・`L:attn:sS@方向`・`L:ffn:sS@方向`)に、専門家のニューロン `L:Ee:Nn:sS@方向` を足す(Inkling 2 だけ。ほかのモデルでは止まる)。`gne chat --recipe`・`gne behave --recipe`・`gne recipe-scale`・画面のレシピの欄(強さの倍率・会話)で試す

### 方向を作る位置(`--positions`)

このモデルは答えの前に必ず思考を書く。質問の最後のトークンで作った方向は、思考と答えを書く位置では A と B の差が小さくなることがある(公開の海賊のひな形では、思考と答えの中で 1 割ほど)。答えの口調や書き方を狙うときは、答えの位置で作った方向も試す。

方向づくりにも、射影の値を測る段(順位づけ・確かめ・配分)にも、側ごとに `--max-examples`(このモデルの既定 32)の数の質問を等間隔に間引いて使う(ほかのモデルは方向づくりに全部の質問を使う)。返事を読む位置では質問 1 つごとに返事を書かせるため。使った数は結果に出る。

| positions | 読む位置 |
|---|---|
| `last`(既定) | 質問の最後のトークン |
| `answer` | 思考の後の、答えの始まり(区切り `<|content_text|>` の位置。その出力が答えの最初のトークンを決める) |
| `response` | 答えのトークン全部(答えのトークンを決める位置、96 トークンまで) |
| `reasoning` | 思考のトークン全部 |
| `after:<正規表現>` | 答えの文字の中の一致の直後 |
| `all` / `assistant` | 質問のトークン(ほかのモデルと同じ) |

`answer`・`response`・`reasoning`・`after` は、書き換える前のモデルに返事(greedy、1120 トークンまで)を書かせ、その上で方向を作り、組を測る(返事は `<root>/inkling/<model_id>/replies/` に覚えて使い回す)。長さの上限までに答えが始まらなかった会話は読まない(数を出す)。

### 書き出し(`gne headproj export`)

`gne headproj export --recipe <レシピ>` で LoRA、`--bake` で GGUF に焼き込む(画面ではレシピの欄の「LoRA・マージ」)。焼き込みの `--requant`:

- `auto`(既定): 元の型・元の大きさで書いて測り、次のテンソルだけ Q8_0 にする。(1) 編集の残り方が 0.9 より小さいテンソル(いくつかの方向なら方向ごとの最小。gne の keyed の焼き込みの auto と同じ決め方)。(2) MLP 全体の部品(`L:ffn`)を受ける専門家のテンソルで、方向に沿わない変化 ÷ 消した成分(編集する列全部でまとめた値)が 2.25 を超えるもの。2.25 は、方向 1 つを元の大きさで焼き込んで、GPU の比べで LoRA と合った組(層 9 の NVFP4・層 22 の Q2_0 の MLP 全体、強さ 1)の値(以前のやり方で 1.91・2.22)のうち大きいほう。ニューロンの部品だけのテンソルは変化が小さいので (1) だけで決める。attention の出力(Q8_0・K-quant)は llama.cpp の量子化で書き戻す(Q8_0 は大きさが変わらない)
- 専門家の `ffn_down_exps`(NVFP4・Q2_0、別の量子化では MXFP4・IQ4_NL も)の元の型での書き方: 量子化し直さず、元のコードとブロックの倍率をそのまま残し、編集する列(ニューロン)のコードだけを 1 段ずつ動かす(行列の 1 行に沿って量子化のブロックが並ぶので、1 つの列のコードを動かしても、ほかの列の値は変わらない)。目標は LoRA が足す変化(いくつかの方向の部品の和。方向は直交しない)で、方向が張る空間の中で列ごとにまとめて合わせる。コードを 1 段動かすと、方向の空間の中の残りがどれだけ減るか(gain)と、方向に沿わない変化のエネルギーがどれだけ増えるか(cost)を比べ、gain ÷ cost の大きい順に動かす(同じ量を少ない数のコードで動かすより、小さな段を多めに動かすほうが、方向に沿わない変化が小さい)。専門家はスレッドで並べて計算する(MLP 全体の部品の層 1 つで、CPU 6 スレッドで 1〜2 分)
- `keep`: いつも元の型。上の (1)・(2) にあたるテンソルがあれば、結果に注意を出す。`q8_0` / `f16`: 書き換えるテンソルをその型にする(専門家のテンソルは全部の専門家が変換され、層ごとに Q2_0 の層で +253 MiB・NVFP4 の層で +162 MiB(Q8_0)、+557 / +466 MiB(F16))
- 書く前に、元の大きさのまま書くテンソル(MLP 全体の部品の層は方向に沿わない変化 ÷ 消した成分)と、型を変えるテンソルとその理由、ファイル・VRAM の増え方を計算して知らせ(CLI は進み具合の行、画面はジョブの段の文。書き出しの欄の「予定を計算する(書かない)」で、書かずに同じ予定とテンソルごとの数を見られる。CLI は `--dry-run`)、いまの空きに入らなければ知らせる(ファイルは書く。空きは、いまのモデルを載せたままの値なので、焼き込んだ GGUF だけを読み込むときより小さく出る)。書き換えたテンソルとやり方は GGUF の `gne.patches` と `<GGUF>.chips.json` に残す。焼き込んだ GGUF は、名前の patch のない llama.cpp でも読み込める
- 書く前に、書き込み先のファイルシステムの空きを確かめ、焼き込んだ GGUF とゆとり(256 MiB)が入らなければ止める(同じ名前の古いファイルは書くときに切り詰めるので、その分も空きに数える)。予定の文に、書くファイルの大きさと空き(WSL の Linux 側のディスクならそのことも)を出す
- GPU を使わずに画面から焼き込む: `CUDA_VISIBLE_DEVICES= gne --n-gpu-layers 0 serve -m <レシピを作った GGUF>`(`serve` には自分の `--n-gpu-layers` が無いので、`serve` の前に共通オプションとして書く)。焼き込みとマージ先(`--into`)のジョブは、モデルを GPU に載せずに CPU で動く
- 元の型のまま書くときの残る誤差(公開のひな形 pirate_tone の方向、その質問 6 問の 305 トークンの活性化での見積もり。層の書き込みは短い畳み込みの前): 方向の成分は目標どおり(どの方向も残り 1.5% 未満)。方向に沿わない変化は、LoRA の変化に対して、NVFP4 の MLP 全体で 0.4〜1.3 倍(方向 1〜3 つ。以前のやり方では 1.0〜1.9 倍)、Q2_0 の MLP 全体で 1.6〜3 倍(Q2_0 は値が 4 段しかなく段が粗いので、以前のやり方とあまり変わらない)、層の書き込みに対しては 2〜8%。方向を 1 つずつ続けて書いていた以前のやり方では、後の方向で動かしたコードが先の方向の成分をずらし(方向の成分の誤差 10〜80%)、NVFP4 の 2 方向の層で層の書き込みの 14% ずれていた。Q8_0 にしたときは、書き換えたテンソル全体に重みの 0.5% ほどの丸めが入り、計算の経路も変わる
- `--verify`(焼き込みと LoRA の比べ)は同じ処理の中ではできない(2 つのモデルが同時に VRAM に入らない)。`gne inkling chips-bake-check --mode lora --recipe <レシピ> --save a.json` と、焼き込んだ GGUF での `--mode baked --direction <方向の .npz> --save b.json --against a.json` の 2 回で比べる

### 別の量子化に焼き込む(`--into`、画面の「マージ先」)

`gne -m <レシピを作った GGUF> headproj export --recipe <レシピ> --bake --into <同じモデルの別の量子化の GGUF> --out <GGUF>`。方向と部品はレシピを作ったモデルのもの、消す量(r̂ᵀW)と短い畳み込みの倍率は焼き込む先の重みから作り直す(量子化ごとに重みが少し違うため)。焼き込みではどちらのモデルも GPU に載せない(画面がモデルを載せていても使える)。焼き込む先は memmap で読み、テンソルを 1 つずつ書くので、大きなファイルでもメモリをあまり使わない。

- 焼き込む先が同じモデルかを確かめる: 構造(arch・層の数・幅)、Inkling 2 の層の並び、全部のテンソルの名前と形。違えば止まる。gne.patches と `gne.inkling_proj` に元と焼き込む先のファイル名を残す
- 元の型で書くときの型ごとのやり方(`auto`・`keep`): NVFP4・Q2_0・MXFP4・IQ4_NL は上の射影を意識した丸め(llama.cpp で IQ4_NL に量子化し直すと、MLP 全体の部品では編集が半分ほどしか残らなかった)、llama.cpp が imatrix なしで量子化できる型(Q8_0・BF16・Q6_K・Q5_K・Q4_K・IQ4_XS など)は量子化し直し(専門家のテンソルは編集した専門家だけ)、imatrix の要る型(IQ2_XXS・IQ2_XS・IQ1_S)は `keep` なら止まり、`auto` なら Q8_0。`auto` の決め方は上と同じ
- `--dry-run`: 書かずに、書き換えるテンソルと型・大きさ・残り方、部品ごとの消す量の違い(大きさの比・相対の差・cos)を出す。大きなファイルに書く前に、ディスクの空きと合わせて確かめる
- 消す量の違いの比が 1 から離れていると、レシピを作ったモデルで決めた強さの効き方が、焼き込む先で変わる。専門家のテンソルの型が二つのファイルで同じ層ではほぼ 1、型が違う層(Q2_0 と NVFP4 など)では MLP 全体の比は 1 に近くても、ニューロン 1 つずつでは 3 割ほど上下することがある。画面の結果には比の範囲と、1 から 1 割以上離れた部品が出る

### 残りから追加(`gne heads refine`、画面の「残りから追加」)

ほかのモデルと同じく、組(土台)を当てても元の方向・元の目標まで下がらない A 側の質問(残り)だけで、A と B の両側に土台を当てたまま方向を作り直し、土台に足す組を探す。表のどの行も、土台と足した組を合わせたレシピ(`<名前>_rK.combined-n<N>.yaml`)を元の方向・元の目標で測り直し、推す行・A 側が最も下がった行の印も、合わせたレシピの数で決める。重ねる(結果にもう一度残りから追加する)と、土台はその行の合わせたレシピ(前の回までの部品を全部残す)。推す行が無いときは土台のままが無難(候補の行は選べる)。足した組は単独では使わない。

- 返事を読む位置(`answer`・`response` など)の一括では、残りと表の数は、元の一括と同じく書き換える前のモデルの返事の上で測る。足す組を探す新しい方向と測定は、土台を当てたモデルが書いた返事の上で作る(ほかのモデルで、側をレシピで作る対照集合の返事の位置の方向と同じ)
- 部品の種類・層 0〜5 の設定・位置は元の一括のまま。足す組の部品の数の上限は `--new-heads`(既定 3,2,1)
- このモデルは応答を読んで決めるので、画面の結果の行と「代表の合わせたレシピ」に「3 列チャット」を置いた(土台 + 足した組でレシピを置き換えて、3 列チャットを開く)。CLI は `gne chat --recipe <名前>_rK.combined.yaml`

### 候補を 1 個ずつ足す(v0.10.1)

このモデルではヘッドの「くわしく見る」が止まっているので、組に入らなかった部品は CHiPS の結果の候補の表(順位・確かめの表)の「レシピに足す」か、レシピの欄の「ユニットを足す」(`17:E25:N389:s4@方向` など)、`gne recipe-add` で足します。強さと方向の決め方はほかのモデルと同じです(README)。層 6〜17 の部品には ×3 が付きます(重みは 3 回の繰り返しで共有)。足したレシピは、ほかのレシピと同じく 3 列チャットで LoRA を作って当てます。

### 評価(`gne eval`、画面の「評価」と CHiPS の結果の「評価へ送る」)

ほかのモデルの評価は最初に生成したトークンから読むが、このモデルでは最初のトークンが思考の始まりなので、返事を読む指標はすべて思考の後の回答(`<|content_text|>` の後)で測る。

- 能力(exact・format)・言語の混入・新語(persona)・judge・反応性・判定の一致率は、回答で測る。思考と回答を 1 本で生成し、長さの上限は「思考の上限(`--reasoning-tokens`、既定 512)+ その問題の回答の長さ」。回答はその問題の長さ(exact 32・format 96 など)で切って採点する。無介入とレシピの腕は、それぞれ自分の思考を書く(同じ問題に同じ条件で答えさせたときの差を見る)
- 壊れた返事の数を倍率ごとに出す: 回答が空・思考の途中で上限に達した(回答が始まらない)・ループ・回答の途中で全体の上限に達した、と思考の長さの中央値
- 返事の読み込み(返事lp低下): 無介入の腕が書いた返事(思考と回答)を、レシピを当てて teacher-forced で読ませたときの平均対数確率の下がり方。最初のトークンの KL の代わり(最初のトークンは思考の始まりなので、KL はほぼ 0 のまま返事が壊れることがあった)。回答だけを読むと、前の思考で答えがほぼ決まっていて確率がほぼ 1 になる(公開の問題で確かめた)ので、思考を含めて読む
- ppl は参照テキストをチャットの形にせずそのまま読む(思考は関係ない)
- 方向の指標(A 側の射影の下がり方・方向に沿わない向きのずれ)は、1 本の残差の代わりに、層 6〜17 の最後の段の MLP の入力と最後に混ぜた出力(点 48)で、方向の位置を読む(CHiPS の流れと同じ読み方)。判定の一致率の返事は 8 問まで(`--dir-max-examples` の方が小さければその数)
- 既定はこのモデルだけ軽くする: 問題は exact 8・format 4・mix 4・persona 4(`--items 8,4,4,4`、`all` で全部。等間隔に間引く)、倍率は 0 と 1。無介入の腕の返事は `<root>/inkling/<model_id>/eval/` に覚えて、同じ問題・同じ上限なら使い回す。始める前に見込み(思考と回答のトークン数と、GPU で 1 本ずつの速さの時間)を出す。既定のタスク集のまま全部(52 問 × 倍率 5)だと GPU で 30〜65 分
- まだ使えないもの(理由を出して止める): ランダムな対照(`--random-controls`・`--head-controls`。部品から同じ数のランダムな部品を作る方法がまだ無い)、`--compare-methods`・`--compare-ablation`(比べる方式をまだ当てられない)、`--when`・`--lora-when`(思考と回答のどちらに当てるかが決まっていない)。採点するモデル(`--judge-model`)に Inkling 2 は使えない(短い返事で数字を読めない)。`--alloc` は各組を 1 本の腕として測る
- 結果には `inkling`(回答で測ったこと・思考の上限・問題の数・見込み)が入り、CLI と画面の表に、壊れた返事と返事lp低下の列が足される
- 実測(UD-IQ2_XXS、RTX 3080、公開のひな形から作った方向 2 つのレシピ): 既定(問題 8,4,4,4、思考の上限 512)で倍率 0・1・4 は 270 秒(始める前の見込み 3 分)。壊れた返事(空・思考の途中で切れた・ループ)と返事lp低下は、倍率 0 で 2・2・0 と 0.000、倍率 1 で 1・1・0 と 0.012、強すぎる倍率 4 で 5・5・5 と 0.293(能力 −8.3pt、ppl +49%)。`--items all --reasoning-tokens 1024`(52 問、倍率 0・1)は 623 秒(見込み 5 分)で、思考の途中で切れた返事は倍率ごとに 3 問。見込みは実際の半分から 3 分の 2 ほどに短く出る

### まだ使えないもの

`--rank causal`、`--holdout`、側をレシピで作る対照集合(`recipe_a` / `recipe_b`)、`--verify-mode ablate`、`--candidate-layers`・`--select-layer`(組は最後に混ぜた出力で作る)は、理由を出して止まる。

### CHiPS の試し(`gne inkling chips-trial`、試しだけ)

ふつうの機能ではない。CHiPS の形の取り除きが、このモデルで応答の水準で効くかを、決まった格子で確かめるための入口。ほかの方向を使う機能は止めたまま。

- 方向: MLP が読む混ぜた入力の、最後のトークンの A − B。層 6〜17 は 3 回目の段、ほかの層はその 1 つの段で作り、層ごとの基準の方向にする。2 回目・3 回目は既定で繰り返しのゲートの後(`ffn_in`。`--gate before` でゲートの前の `ffn_mix`)。
- 部品: attention のヘッド(W_o の列)と attention 全体。流れが始まる層(0・6・12・18)の attention と、層 0〜5 は、既定で候補に入れない(`--keep-stream-start` で入れる。層 0〜5 は比べのための組だけ作る)。
- `--all-kinds`: ヘッドだけの組の後に、MLP 全体(`L:ffn`、選ばれた専門家の書き込みの和)と専門家のニューロン(層・専門家・ニューロン。書き込み = 選ばれ方の重み × 専門家ごとの倍率 × SiTU の活性 × down の列。選ばれなかったトークンでは 0)も同じ順位に入れ、ヘッド + 層全体(`hw_*`)と全部(`all_*`)の組を、ヘッドだけ(`heads_*`)と同じ部品の数と強さで流す。専門家の down の重みはタップごとの向きとの内積に前もって縮め(層ごと・専門家ごとに 1 枚ずつ読む)、全部の重みを一度にメモリに置かない。MLP の LoRA は `ffn_down_exps` の 3 次元(専門家ごとにランク 1)で、向きは MLP の短い畳み込みの今のトークンの倍率で直した normalize(g ⊙ r)。llama.cpp は専門家ごとの倍率(`ffn_down_exps.scale`、層 0〜19)を元の積にだけ掛けて LoRA の差分には掛けないので、倍率を差分に入れておく。組を流す前に、NVFP4 の層・Q2_0 の層・倍率の無い層で、LoRA の効き方を捕まえた値からの計算と比べる(合わなければ止まる)。
- 射影: 書き込み(W_o の出力、短い畳み込みの前)から normalize(g ⊙ r) を s 倍で引く(g = 短い畳み込みの今のトークンの倍率)。層ごとのランク 1 の LoRA にして、生成のときに当てる(`gne inkling chips-bake` で GGUF に焼き込むこともできる)。層 6〜17 の重みは 3 回で共有なので、書き換えは LoRA でも焼き込みでも 3 回すべてに効く。比べのために、いちばん良い組を素直な射影(r を引く)でも流す。
- 順位: 部品ごとの、基準の方向に沿った書き込み(短い畳み込みの後、最後のトークン)の A − B。繰り返しの層は 3 回目の値で並べ、1・2 回目の値も出す。
- 測るもの: 各段の MLP の入力と最後に混ぜた出力の、A − B の差がどれだけ残るか(応答に使う質問の最後のトークン)、書き換える前のモデルの続き 32 トークンを予想する位置での分布の差(KL と、いちばん確率の高いトークンが変わる割合)、応答(`validate.prompts`、思考の欄を除いた回答で `validate.match` を数える。空・繰り返し・長さの上限で切れた数も)。
- 組: ヘッドの上位 k(4・8・16・32)× 強さ s(1・2・4・8)、attention 全体の上位 2・4 層 × 1・2・4、層 0〜5 だけ・層 19〜23 だけの上位 8 ヘッドを、最後の出力の差を同じくらい縮める強さで。結果は `<root>/inkling/<model_id>/<名前>.chips/result.json`(流し直すと済んだ組は飛ばす)。 `--all-kinds` の組で部品がほかの組とまったく同じになったもの(ニューロンが上位に入らないと `all_*` と `hw_*` は同じ)は流し直さない。
- `--answer-check`: このモデルは答えの前に必ず思考を書くので、最後の質問のトークンで作った方向が、答えを決める位置で効いているとは限らない。1 回だけの確かめとして、強い組の応答を思考も含めて残し、最後の質問のトークンの方向への射影の A − B が書き換える前の応答(思考 → 回答)の中でどう続くかを位置の区切りごとに出し、回答の始まりの区切り(`<|content_text|>`)の位置で作った 2 つ目の方向との cos と、その方向でいちばん良い組を流し直した結果を出す。

### 焼き込み(`gne inkling chips-bake`、試しだけ)

`gne inkling chips-bake --name <試しの名前> --set <組> --out <GGUF>` は、試しの組を LoRA と同じ変化量で GGUF に書き込む(GPU は使わない)。gne のほかのモデルの焼き込みと同じく、書き換えるテンソルだけ型を変えてファイルを書き直し、ほかのテンソルはバイトのまま写す。

- 型(`--requant`): `auto`(既定)・`keep`・`q8_0`・`f16`。決め方と残る誤差は上の「CHiPS の流れ」の「書き出し」と同じ(`keep` は元の型・元の大きさのまま、専門家のテンソルは編集する列のコードだけを動かす。`auto` は `keep` と同じに書いて測り、編集が残らないテンソルと、MLP 全体の部品を受けて方向に沿わない変化が大きい専門家のテンソルだけ Q8_0。`q8_0`・`f16` は書き換えるテンソル全体の型を変える)。
- llama.cpp の量子化で元の型に書き戻す方法は、専門家のテンソルには使わない: NVFP4 では小さな編集の 3〜5 割が丸めで消え、Q2_0 はこの GGUF のブロックの倍率に負の値があるので、llama.cpp の量子化(倍率 = ブロックの絶対値の最大)では編集しない値の半分ほどが変わる。IQ2_XXS・IQ1_S などは imatrix が要る(この試しで書き換えるテンソルには無い)。
- 専門家ごとの倍率(`ffn_down_exps.scale`)はそのままにし、重みの変化量を倍率で割って入れる(実行時に倍率が掛かり、LoRA と同じ値になる)。
- 書き換えたテンソルと型は `<GGUF>.chips.json` に残す。
- 確かめの結果(UD-IQ2_XXS、専門家の層 3 つと attention の層 3 つを書き換えた組): 焼き込みと LoRA の中の値の差は、編集なしで型だけを変えたときに出る差と同じ大きさ(LoRA が動かした量に対して繰り返しの中で 4〜9%、繰り返しの後で 18〜28%。行列の積の計算の経路が変わるため)。貪欲の応答は数十トークン目から分かれる(型だけを変えたときも同じ)。名前の patch のない本家のビルドでも読み込めて、patch のあるビルドと同じトークンを出す。VRAM は書き換えた専門家のテンソルの増えた分だけ増える(この 3 層で Q8_0 +0.67 GB、F16 +1.3 GB)。生成の速さは元と同じ(LoRA を当てたままだと 4 割ほどに落ちる)。
- 確かめ: `gne inkling chips-bake-check --mode lora --set <組> --save a.json`(元のモデル + LoRA)と、`-m <焼き込んだ GGUF> gne inkling chips-bake-check --mode baked --trial <試しのフォルダ> --save b.json --against a.json` で、各段の MLP の入力と最後に混ぜた出力の方向への射影(最後の質問のトークン)と貪欲の応答を比べる。`--mode replies` は名前の patch を当てていない llama.cpp で読み込んで応答だけ出す。
